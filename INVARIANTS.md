# FastDocReader — hard-won invariants (full record)

The RULES live in `CLAUDE.md`, one line each, same numbering. This file is the EVIDENCE
behind them: the measurements that produced each rule, the designs that were built and
rejected with the numbers that killed them, and the procedures to reproduce either.

**Read the entry before touching its area.** Every one of these was paid for by a defect
that shipped, a night of measurement, or both — the one-line rule tells you what to do,
this file tells you why, and why the obvious alternative does not work.

1. **Scrollbar stability = media SIZE decoupled from PIXELS.** An `NSTextAttachment` with `image==nil` (not-yet-loaded / purged) collapses to ~0 height → total height and the scrollbar swing on scroll. `SizedAttachmentCell` owns `reservedSize` independent of the image. Loading/purging pixels must **redraw only, never touch layout** (`redrawGlyphs`) — size unchanged → do NOT call `storage.edited`/`ensureLayout`. Cost **4 debugging rounds**; keep the size/pixel split intact.

2. **Uncached docs must behave like cached ones.** On first open `prerenderAllDiagrams` renders every uncached web block — diagram OR formula — to the disk cache (bounded concurrency, `cap=min(3,…)`), then `presizeKnownMedia` reserves each exact area and lays out **once**. Sizes never change on scroll after that. Both engines ride this one pipeline via `WebBlock`; a separate formula path would have to re-earn the property (getting it wrong = formulas resizing mid-scroll).

3. **`invalidateDisplay` alone does NOT draw a newly-set attachment image** — needs `storage.edited(.editedAttributes, …)`. (Learned when diagrams went invisible.)

4. **The web-block cache lives in `FileManager.default.temporaryDirectory/fast-md-reader/mermaid`** (historical name; it holds BOTH mermaid and KaTeX PDFs, disambiguated by the engine's `cacheVersion` in the key), NOT `~/Library/Caches`. The app is sandboxed, so that resolves INSIDE the container — `~/Library/Containers/ai.ww-w.fast-md-reader/Data/tmp/fast-md-reader/mermaid`, **not** the `$TMPDIR` your shell sees. Test "uncached cold start" by clearing the CONTAINER path; clearing the shell's `$TMPDIR` copy looks like it worked and proves nothing. Bump the engine's `cacheVersion` (in `WebBlock`) when its capture changes — a stale PDF outlives the bug that made it.

5. **Fresh-DB/fresh-open tests are fake-green for the cache/migration class** — they create the target state directly and skip the render path. Test cold start by actually clearing the mermaid cache dir and relaunching.

6. **NSDocumentClass in Info.plist must be module-qualified**: `FastDocReader.MarkdownDocument` (SwiftPM executable, so NSDocumentController can't find a bare class name).

7. **Open Recent**: AppKit's automatic population does NOT attach to a code-built menu → populated manually by a menu delegate in `AppDelegate` reading `recentDocumentURLs`. macOS prunes deleted files (a deleted test file → "No Recent Files").
   - **Read `recentDocumentURLs` ONLY from `menuNeedsUpdate`** (when the user opens the menu). Sandboxed, each read can consume a limited pool of security-scoped extensions; apps that poll it (timers, `validateMenuItem`) exhaust the pool and then fail to reopen recent files. Apple's published workaround — cache the list, refresh on activation — is WORSE here, since that fires on every ⌘Tab. On-demand-only verified sandboxed across repeated relaunches; first suspect if recent files ever stop opening.

8. **Sandboxed WKWebView needs `com.apple.security.network.client`** even though mermaid loads only a bundled local JS file and the app makes zero network requests — WebKit runs out-of-process and renders nothing without it. Don't "clean up" that entitlement.

9. **Sandboxed = a document's sibling images are unreadable, and macOS NEVER prompts.** Measured: relative, absolute and `file://` paths all fail sandboxed while remote URLs load; the same binary unsandboxed loads them all. The sandbox denies before TCC is consulted, so no prompt appears, and there is no "Documents folder" entitlement to request (iMovie's Documents/Desktop/Downloads toggles come from its *media* entitlements). Full Disk Access does nothing — the sandbox still refuses. The only way through is `FolderAccess`: user picks the folder in an open panel, persisted as a security-scoped bookmark (what Marked 2 / iA Writer / MWeb do; Typora / Obsidian / IntelliJ skip the store instead). **Don't re-litigate: four plausible theories — temp path, ad-hoc signature, TCC identity, launch method — were each disproved.**

10. **A blocked image's placeholder is itself an image**, so its click check MUST come before the zoom check in `ReaderTextView.mouseDown` — otherwise clicking "Click to allow…" just enlarges that label.

11. **Remote images are presized by fetching only their header** (`Range: bytes=0-65535` → ImageIO), mirroring `prerenderAllDiagrams`: measure everything, then lay out ONCE. Never reserve a guess and correct it later — that reflows under the reader, which invariant 1 exists to prevent.

12. **Math is read from the SOURCE, never the parsed text.** `MarkdownRenderer.scanMathSpans` finds `$$…$$` in the raw markdown before the parser touches it, for two reasons: (a) markdown claims `_`/`^` as emphasis, so `$$a_1^2$$` parses to *a12* — silently wrong maths; (b) a `\\`-then-`=` line inside a matrix reads as a setext heading and shreds one formula across several nodes. A block becomes a formula only if it lies ENTIRELY inside a scanned span. ```` ```math ```` fences are verbatim, so they skip the dance.

13. **KaTeX fonts are inlined as data: URIs in `katex-inlined.min.css`.** The render page loads with `baseURL: nil`, so a relative `url(fonts/…)` resolves to nothing and every glyph silently falls back to a system font at the wrong metrics; inlining removes the resolution step. Snapshot only after `document.fonts.ready` — KaTeX lays out synchronously but the fonts arrive async, and snapshotting early bakes fallback metrics into the cached PDF forever. **The fonts are OFL-1.1, separate from KaTeX's MIT code** — `licenses/KaTeX-fonts-OFL-1.1.txt` + a notice in `THIRD-PARTY-NOTICES.md` are required, and `make-app.sh` copies both into the bundle (the licence must travel with the fonts).

14. **The reading-line band repaints the whole visible rect on every selection change** (`setSelectedRange` override → `setNeedsDisplay(visibleRect)`). A bare caret move only invalidates the thin caret sliver, so the band would smear — lit on the old line, dark on the new. Drawn in `drawBackground` beneath glyphs, and only when the selection is empty (an active selection is its own stronger highlight).

15. **Keyboard nav: fn+arrow arrives as Home/End/PageUp/PageDown (keyCodes 115/119/116/121), NOT as a bare arrow.** Matching a bare arrow (123/124) for the paragraph keys made plain ←/→ jump a paragraph instead of moving one character. Vertically, two tiers by heading rank: `fn` = top-level `#` only (the SHALLOWEST rank present, `topHeadingNav`) › `⌘` = every heading (`headingNav`) › `⌥` = page; `fn+⌘` (keyCode 116/121 WITH `.command`, so the `[.command]` cases must precede the catch-all `_`) = document start/end. Across the line: `fn` paragraph › `⌥` sentence › `⌘` line. ⇧ extends. Unit boundaries come from `TextNavigator`; paragraph/sentence stops also honour block starts (`MDAttr.blockId`) so a heading is never skipped. The page holds still and the cursor moves inside it — scroll follows only when the caret would leave the screen (`revealCaret`), never top-anchored. **The bare single-letter block keys (E/I/D/U/J/T) match by keyCode (e=14·i=34·d=2·u=32·j=38·t=17), NOT by character** — a non-Latin input source turns `e` into `ㄷ` and silently broke every bare-letter shortcut; keyCode is layout-independent. (⌘-modified equivalents already fall back to the Latin layout.)

16. **Every block operation goes through `applySourceEdit` — the single mutation path.** Add/delete/move each compute ONE (range, replacement) pair in `BlockEdit` and hand it over, so re-render, cursor reveal and undo are earned once and nothing can half-apply. A move is deliberately length-preserving (block A + the untouched gap + block B, reordered). Modeless popups and alert sheets re-resolve the block at confirm time — offsets move under them.

17. **Nothing reaches disk until ⌘S.** `applySourceEdit` changes memory and marks the document dirty; `data(ofType:)` is the only writer. Change tracking is left to NSDocument (it watches the undo manager), so undoing back to the original correctly reports clean — the undo group closes on the NEXT run-loop turn, so a test asking immediately is asking too early. ⌘R warns before discarding unsaved edits.

18. **A file is written back in the encoding it was READ in.** `String(decoding:as:UTF8.self)` never fails — it substitutes replacement characters and reports success — which is how a Windows CP949 file arrived as a wall of "?". Use `TextEncodingDetector`, and accept a guessed encoding only when re-encoding reproduces the original bytes exactly (the system's own guess for arbitrary input is Windows-Cyrillic, which doesn't reverse). Text the file's encoding can't represent is REFUSED with an explanation, never written lossily.

19. **An edit re-renders only the blocks it touched (`spliceRender`), not the document.** Full re-render measured 131ms on a 64k-character file and over a second on 1.2MB — paid again on every undo; the splice is 9–29ms. It is safe because a block renders the same alone as in context (verified per block kind in `FragmentRenderTests`); reference-style link documents take the full path. Two things it must keep doing: **lift the fragment's block ids clear of existing ones** (fragments number from zero, and two neighbours sharing an id merge into one stop for the reading cursor), and **run the fragment to where the NEXT block starts** so the following separator isn't spliced away. `SpliceRenderTests` asserts the result is identical to a full render after every operation — a divergence there is invisible on screen.

20. **In plain text a block is a LINE, blank ones included; in markdown it is a paragraph/heading/table/fence.** A blank line in a .txt is spacing the author typed, not structure — so it must be selectable, deletable and movable, and "add below" inserts exactly one line (the file's own ending, CRLF preserved) instead of copying the neighbouring gap. Because a blank line is nothing but its terminator, a plain-text block's RENDERED range includes that terminator while its SOURCE range stays content-only. `PlainTextRenderer` must also keep `output.string == source` exactly — a dropped trailing newline is a silent data change on the next save.

21. **Open Recent emptying after a rebuild is the AD-HOC SIGNATURE, not the code.** Measured 2026-07-20: the list survives quitting and relaunching the same binary, and disappears only when a freshly built bundle replaces it. macOS keeps recents in a SharedFileList keyed to the signing identity, and an ad-hoc signature's cdhash changes on every build, so each build looks like a different app. A Developer ID / App Store build keeps its list across updates — don't "fix" this in code. (The store is TCC-protected, so a shell can't read it; `defaults read ai.ww-w.fast-md-reader` won't show recents either.)

22. **Save is greyed out unless `CFBundleTypeRole` is `Editor`.** With `Viewer`, AppKit decides the app cannot write that type and disables `saveDocument:` — while `save(nil)` called directly still writes the file, so the save path looks fine and only the menu is dead. The two text entries (markdown, plain text) are `Editor`; the office entries (Word, OpenDocument, HWP) are deliberately `Viewer`, which is what greys Save out for the read-only formats — intended behaviour, not the bug. The close-and-save prompt works either way, which makes this easy to misread as "saving is broken".

23. **The table of contents is rebuilt from BOTH render paths.** `spliceRender` changes headings as surely as a full render does (`##` typed into a block, a section moved, a heading deleted), and for a while only the full path called `reloadOutline()` — so the sidebar described the document as it was several edits ago. Anything that changes the text must end at `reloadOutline()`.

24. **Reflow is deferred to the END of a resize / sidebar animation, and the reading position is restored by ANCHOR.** Re-wrapping a long document per animation frame made both feel like they were fighting the user (`suspendReflow`). Two things must stay true: lay the whole document out BEFORE scrolling (a narrower column makes it taller, and until that layout exists the scroll is clamped to the old, shorter height — which is why position held when widening and drifted when narrowing), and restore via `readingAnchor()`/`restore(_:)`, which keeps the CURSOR's line at its old height if on screen and otherwise puts the centre character back at the centre. A plain scroll offset means different text once the wrapping changed.

25. **A spinner must be shown BEFORE the work and forced to draw.** `setBusy(true)` + `spinner.display()`, then the work on the next run-loop turn. A delayed show scheduled with `asyncAfter` can never fire: the work owns the main thread, so the timer's turn only comes after the work finished and cancelled it — that version shipped and showed nothing. Gated on document size (>120k chars).

26. **A control next to the traffic lights is a TITLEBAR ACCESSORY, not a toolbar item.** This macOS lays toolbar items out trailing with the title leading, so a toolbar button lands far right no matter how identifiers are ordered — `.flexibleSpace` doesn't move it, nor does the system `.toggleSidebar`. `NSTitlebarAccessoryViewController` with `layoutAttribute = .leading` puts it where every Mac app keeps it. Centre it with a constraint; the title bar's height is not ours to guess.

27. **The sidebar is a real `NSSplitViewItem(sidebarWithViewController:)`.** That supplies the inset rounded panel, the system material and the light/dark behaviour. An `NSVisualEffectView` of our own underneath a real sidebar just hides it.

28. **A local build carries its OWN bundle identifier — `ai.ww-w.fast-md-reader.dev` — and must keep doing so.** `make-app.sh` rewrites `CFBundleIdentifier` and the display name ("FastDoc (Dev)") in the COPY inside the bundle; `Resources/Info.plist` keeps the real identifier. macOS keys per-app state to the identifier, so while they were shared, every local rebuild took the installed release's Open Recent list with it (invariant 21 explains why a rebuild invalidates it). `notarize.sh`/`appstore.sh` pass `DIST_IDENTITY=1` to keep the real identifier **and then verify it survived**, refusing to ship a `.dev` bundle: a flag that protects only when every future caller remembers to set it is not protection. Consequence for cold-start testing — a dev build's container is `…Containers/ai.ww-w.fast-md-reader.dev`, so invariant 4's cache path shifts with it.

29. **A unit test on a parser cannot tell you the parser is REACHED.** `.odt` shipped registered, parsed and covered by 24 passing tests — and could not be opened at all: both office call sites hard-coded `DocxReader`, so ODF bytes went to the Word parser and threw. Every `OdtReaderTests` case called `OdtReader.read` directly, which proves the parser and says nothing about the application. 266 tests were green with the feature completely dead; only launching the app found it. Two rules follow. **`DocumentTypes.readOffice` is the single dispatch table** — one place mapping an extension to its reader, throwing on anything unhandled rather than falling through to Word; a second, divergent list is how this recurs. And **any new format needs one test through `MarkdownDocument`'s own read path**, not just through its parser, plus an actual open in the built app. The same blindness applies to `Info.plist` (invariant 6) — both are seams no compiler and no unit test can see.

30. **Measure the corpus before believing it.** All eight contracts ship `word/footnotes.xml`, which read as "footnotes matter here" and ranked a whole sprint — but every one holds ONLY Word's `separator`/`continuationSeparator` boilerplate. Real footnotes: zero. Likewise the claim that filtering those separators prevents phantom notes: removing the filter changes nothing, because only CITED notes are ever appended — the filter is a second layer, not the load-bearing one (confirmed by mutation). **When a check passes, break the thing it checks and confirm it fails**; a green assertion whose subject is unreachable proves nothing. Two real defects this session were found by exactly that step, and one "verified" claim was withdrawn because of it.

31. **Setting an `NSTextAttachment`'s `.image` silently discards a custom `attachmentCell` the moment it's set** — AppKit switches to its own bounds-based image layout, replacing whatever cell was there. Found by experiment while building the chart/SmartArt placeholder (`OfficeTextBuilder.appendUnsupportedGraphic`), which is why that placeholder sizes itself through `.bounds` alone rather than invariant 1's `SizedAttachmentCell`: there is no "not yet loaded" state for a placeholder whose image is never nil, so nothing can revise its size after the fact.

32. **`NSTextContainer.exclusionPaths` invalidates the WHOLE container's layout — AppKit does no partial invalidation.** Real text-wrap around a floating image was built and measured (`FloatWrapExclusionSpikeTests`, kept as a reproducible spike): N floating images cost N sequential full re-layouts, measured 45ms with none vs. 301ms with twelve on a 400-paragraph document, and it isn't paid once — resizing the window or toggling the sidebar re-runs the whole pass on top of the reflow already happening there. Under the owner's "light and fast is the core" constraint this was measured, found too expensive, and deliberately not shipped; floating images still render inline, on their own line.

33. **A style's ID is not localised even though its NAME is.** The heading reader's comment argued from a true premise — a Korean Word install shows a style named 제목 1, so matching by name is unsafe — and drew the wrong conclusion: that built-in heading styles couldn't be recognised at all. The id (`Heading2`) stays the same in every locale, and skipping it left 103 of 188 heading-bearing documents rendering with zero headings. **A true premise can protect a false conclusion** — check what the premise actually rules out, not everything nearby it. **HWP is the same lesson from the other side and must not be "corrected" by this one:** an HWP paragraph has no locale-stable style id at all, so `HwpReader.headingLevel` matches the NAME — English first (`Outline 1`, the locale-stable identity HWP does offer), Korean as fallback, plus the custom names Korean reports actually use (각 장 제목 → 1, 각 절 제목 → 2). Its exclusion list is measured, not theorised: 표의 제목 appeared 112 times in one document and 목차 turned forty-odd contents lines into headings, so a name must say title/chapter/section and must not be about a table, figure, note or running head. Without any of this a real corpus rendered flat — HWP's `head_type == Outline` marks only paragraphs using outline NUMBERING, and 13 of 14 real files had no table of contents at all before it (`c46dcfa`).

34. **Measuring document STRUCTURE is not measuring reader BEHAVIOUR, and when they disagree, behaviour wins.** An XML-grep prediction of the heading gap said 36% of documents render flat; running the reader through its own read path said 55% (103/188). The grep undercounted because it treated the presence of *some* outline-capable style in `styles.xml` as protection, when what matters is whether the styles the headings actually use resolve to one — only executing the real code path can see that. The grep number was briefly recorded as a "correction" of the higher one; it was the wrong turn (`docs/06-research/gap-list.md` keeps both, visibly, on purpose).

35. **`FileManager.enumerator` stops silently at the first unreadable subdirectory unless given an explicit error handler.** The corpus probe (`CorpusProbeTests`, invariant 30's tool) under-counted its own input by about a dozen files with no indication anything was skipped — the exact silent-truncation failure this project's working style forbids, caught only because the probe's count was checked against a second method. Fixed by passing an error handler that counts skips and continues rather than aborting the walk.

36. **The reader's rhythm lives in ONE base design system, never re-inlined per renderer.** `RenderTheme` carries the base tokens (type scale + line-height/spacing/indent ratios + colour); `MarkdownStyle`/`OfficeStyle`/`PlainTextStyle` are thin branches overriding only what their format needs. The rhythm constants were once duplicated across `MarkdownRenderer`, `OfficeTextBuilder`, `TableBlockBuilder` and `PlainTextRenderer` (a change in one never reached the others); hoisting them was proven byte-identical by `RenderThemeParityTests`, which snapshots every layout-affecting attribute. Markdown output must stay identical when a token moves — re-inlining a magic number is the regression that harness exists to catch.

37. **Office paragraph/run/table formatting comes from the DOCUMENT's own styles, resolved into `ParagraphFormat`/`Span`/table `columnWidths` and applied by the one format-neutral `OfficeTextBuilder` — and "the document said nothing → the theme token, byte-identical" is the load-bearing contract.** docx resolves docDefaults → `w:basedOn` chain (cycle-guarded) → direct `w:pPr` per property; ODF resolves the `style:parent-style-name` chain; both feed the SAME builder, and absolute points ride the same `fontSizeScale` (reading-size ÷ document-default) that font size does — `.multiple` line-heights are ratios and don't scale. An office change that alters output for a document declaring NOTHING is a regression. Tables fill width from `w:tblGrid` / `style:rel-column-width` kept as PROPORTIONS and re-solved to ABSOLUTE INTEGER point widths at the reading column (invariant 39) — never percentages fed to `NSTextTable` (it recomputes those per row → a merged row's boundary drifts a pixel, invariant 42) and never a raw twip as an absolute width. Named table styles (`w:tblStyle` + `w:tblStylePr` + `w:tblLook`) resolve per-cell UNDER the direct props: cell-direct > table-direct > table-style > theme — a cascade that runs PER EDGE, with a silenced edge told apart from an unmentioned one (invariant 47). Paragraph shading/borders draw via the `CodeCardLayoutManager` block-background path (draw-time, NOT `exclusionPaths`).

38. **Comments are captured but drawn at DRAW-TIME, gated by the panel.** docx `word/comments.xml` and odt `office:annotation` become `MarkdownDocument.officeComments` + `Span.commentIds` on the commented spans (never merged away, like bookmarks; the office read contract is `OfficeReadResult{blocks,comments}`, one dispatch, invariant 29). The right comment panel is an `NSSplitViewItem` inspector (hidden by default); when open, commented spans get a faint band + number badge painted BEHIND already-laid-out glyphs (like the reading-line band), never an inline `NSTextAttachment` — so toggling the panel sets a flag + `setNeedsDisplay` and MUST NOT reflow. A comment-free document is byte-identical and the menu item is disabled.

39. **Tables are a REAL `NSTextTable`, so cell text is selectable, copyable and searchable — with columns pinned to ABSOLUTE INTEGER point widths, never percentages.** `TableBlockBuilder` lays every cell into a `GridTextTable` (an `NSTextTable` subclass remembering its column PROPORTIONS) as ordinary paragraphs carrying an `NSTextTableBlock`, so the text is part of the document — the whole point: a custom-drawn attachment, however crisply aligned, is a *picture* the reader can't select, copy or ⌘F. Columns are absolute integer point widths (cumulative ROUNDED edges of proportion × reading-column width): `NSTextTable` recomputes a percentage per row, so a boundary lands on a different fractional pixel in a 4-cell row than in a span-merged one (the "열이 살짝 어긋남" drift). `DocumentWindowController.resizeTableColumns` → `TableBlockBuilder.resizeTables` re-solves those widths on every reflow — and an OFFICE table is BUILT at that width, so the first paint is the final one (invariant 48). Because cell content (INCLUDING image/diagram/formula attachments) lives in the TOP-LEVEL storage as ordinary paragraphs, the existing top-level media passes (`presizeKnownMedia`/`prerenderAllDiagrams`/`reconcileMedia`/`measureRemoteImages`) size and paint cell media natively — no per-table descent. **History (don't rebuild it):** an earlier custom-drawn engine (`TableAttachmentCell` + `TableGeometry` + `CellText`, added `c1173cb`, removed 2026-07-24) computed its own x-edges to kill that drift, but the drift was a wrong-algorithm choice (percentage widths), NOT an `NSTextTable` limitation — absolute integer widths fix it while keeping real text, in far less code. `MarkdownRendererTests`/`OfficeTextBuilderTests` inspect the `NSTextTableBlock`s (block span/shading/border + `GridTextTable.columnProportions` + cell text in the top-level string).

40. **`--extract` is a HEADLESS branch of the same binary, gated in `main.swift` BEFORE `NSApplication`.** `FastDocReader --extract <file>` prints Markdown to stdout and `exit()`s without ever constructing `NSApplication` (no window, no Dock icon, no `AppDelegate`) — the arg check must stay first in `main.swift` or the GUI spins up. Its purpose is token economy for an AI reading a `.docx`/`.odt`: it reuses the app's OWN office reader via the SAME `DocumentTypes.readOffice` dispatch (invariant 29), then `OfficeMarkdownSerializer` (`[OfficeBlock] -> String`, pure/view-free, unit-tested without AppKit). The serializer's contract is **conservative + honest**: map to real Markdown only when unambiguous, and degrade anything a GFM pipe table can't hold (merged cells via `colSpan`/`rowSpan` ≠ 1, or non-`.paragraph` block content in a cell) to a `<raw>…</raw>` plain-text dump rather than a fabricated grid — a wrong table is worse than none for the AI consuming it. Escaping is deliberately minimal (only `|` inside a pipe cell, newlines→spaces); an AI tolerates messy text but not a mis-structured table. `stdout` is ONLY the document (errors → stderr, exit 1 read/parse · 2 usage). Coverage: docx family + odt plus md/txt verbatim (decoded through `TextEncodingDetector`, invariant 18); legacy `.doc`/`.rtf` unsupported, same as the reader. Proven both as pure serializer units AND through the real dispatch (`OfficeDocumentTests.testHeadlessExtractSerializesThroughTheRealOfficeDispatch`) — a serializer unit test alone can't prove the reader FEEDS it (invariant 29 again).

41. **A markdown feature can ship DEAD, and only rendering it proves otherwise — `MarkdownFeatureAuditTests` renders every CommonMark+GFM feature through the real `MarkdownRenderer.render` path and asserts its evidence attribute.** Strikethrough (`~~x~~`) shipped for a long time producing PLAIN text: the parser emits a `Strikethrough` node (GFM is on — tables prove it), but `inlineFragment` had no case for it, so it fell through `default` to unstyled children while the README advertised it. GFM task-list `[ ]`/`[x]` had the same fate — swift-markdown consumes the box into `ListItem.checkbox`, and `renderList` ignored it, so the ticks vanished. Both fixed (strikethrough → `.strikethroughStyle`; checkbox → `☐`/`☑` in place of the bullet). The lesson is invariant 30/34's: a parser unit test (or a grep of the visitor) can't see an unREACHED case — only the render path can, so any new inline/block support MUST add an audit assertion. **Footnotes (`[^id]`) are deliberately NOT rendered yet** — swift-markdown does not parse them, so a real implementation must source-scan like `scanMathSpans` (superscript refs + a collected section + srcRange/blockId wiring), tracked as a deferred unit; README must not claim footnotes until then (`testFootnotesAreNotYetRenderedButContentSurvives` characterizes the current preserve-but-don't-render behaviour).

42. **When a native API "doesn't align / is slow", suspect your INPUTS before reimplementing it.** Two rounds of this on tables, both resolved by a one-line input choice, not a custom engine. (a) **Alignment** — feeding `NSTextTable` PERCENTAGE column widths let it recompute per row so a boundary drifted a fractional pixel; the "fix" was a whole custom-drawn engine, when the real fix was ABSOLUTE INTEGER widths (invariant 39). The source already stored absolute twips — WE threw the precision away. (b) **Speed** — that custom engine measured each cell with `NSAttributedString.boundingRect`, ~O(n²) in char count on rich CJK text (a 1000-char patent cell: 53ms; its first 100 chars: 0.8ms — 10× length for 67× time), making a 13-table document crawl at ~750ms/reflow; a reused `NSLayoutManager` was O(n) (~4.6ms), but the deeper truth is the engine shouldn't have existed. Both the drift and the O(n²) were self-inflicted by the workaround. The general rule: percentage-vs-absolute, twip-vs-point, and the layout API you pick are load-bearing — "native API is inadequate" should be the LAST resort, after the inputs are proven right.

43. **A regular (non-agent) macOS app MUST present an interactive window on launch — launching to only the menu bar is an App Store 2.1 rejection, however intentional.** This reader deliberately started empty and FAILED review 2026-07-23: "No interactive window displayed upon launch." A document reader has no "new document", so `applicationDidFinishLaunching` presents the Open panel (`openDocumentPanel`) on the next run-loop turn WHEN launched with no document (`NSDocumentController.shared.documents.isEmpty` and no visible window) — matching shipping App Store readers; cancelling returns to the menu-bar state, which is fine. Deferred one turn so a file passed AT launch opens its own window first and suppresses the panel. `applicationShouldOpenUntitledFile` stays `false` (no blank docs); the panel, not that hook, satisfies the rule. `applicationShouldTerminateAfterLastWindowClosed` stays `false` so closing the last document returns to the (now legitimate, post-launch) menu-bar state. Do NOT "restore" the empty launch — it re-earns the rejection.

44. **HWP is parsed from raw bytes by rhwp's FFI, so it branches BEFORE the zip path — and its images are pre-decoded at read time.** A `.hwp` is CFB/OLE binary, not a zip (a `.hwpx` IS a zip, but rhwp reads both from `Data`), so `ZipArchive(data:)` would throw on `.hwp`. `MarkdownDocument.read(from:)` AND `HeadlessExtract` check `DocumentTypes.isHwp(ext)` and hand the bytes straight to `HwpReader.read` before constructing a `ZipArchive` — one predicate, invariant-29's single-dispatch discipline (HWP is DELIBERATELY absent from `readOffice`'s archive table, which throws as a safety net, since HWP can't conform to the `ZipArchive`-taking `OfficeDocumentReader`). No archive means no lazy image source later, so `HwpReader.read` decodes every embedded image inside the ONE rhwp parse handle's lifetime (`imageBase64` needs the SAME live handle) into `OfficeReadResult.images`, keyed `hwpimg:<binDataId>`; `reconcileMedia` looks that map up before the archive. Everything downstream is the shared office engine — the JSON maps to the SAME `OfficeBlock` vocabulary, so `OfficeTextBuilder` renders HWP with no HWP-specific render path (invariant 37's contract holds for HWP too).

45. **The rhwp parser ships as a statically-linked, dead-stripped xcframework — and SwiftPM does NOT relink on a CONTENT change.** `Vendor/RhwpNative.xcframework` is a prebuilt Rust static library (arm64, tens of MB); static linking lets the final link dead-strip everything the app doesn't call, so the app grows by a FRACTION of the library — most of it, including the svg2pdf/resvg PDF path, never ships. **No size is quoted here on purpose**: every one that was went stale, and one was simply wrong for months — it claimed ~3.3 MB growth when 3.3 MB was the whole executable BEFORE the parser existed (measured 2026-07-30: 3.3 → 11.0 MB release, i.e. +7.7). Measure it, don't quote it: build `release` at the commit that added the parser and at its parent, and compare `FastDocReader.app/Contents/MacOS/FastDocReader`. Note `make-app.sh debug` is ~3× the release size. The trap: SwiftPM's `binaryTarget` keys off the xcframework PATH, not its bytes — overwriting the `.a` in place does NOT trigger a relink, so `swift build` silently keeps the OLD parser and new FFI/JSON changes never appear. After replacing the binary: `rm -rf .build` to force the relink, AND verify the copy landed (`stat` the `.a` size against the build you just made). This bit us once — a sub-agent's rebuild left a stale 56 MB binary in `Vendor/` while the correct build was 58.8 MB, and the equation test failed against code that was actually correct. Rebuild + relink procedure: `docs/BUILD-RHWP.md`.

46. **A graphic's size comes from the DOCUMENT's own page width, never from the reading font — and is re-solved on every reflow.** A picture was authored as a fraction of its page, so the reader reproduces that fraction: scale = reading column ÷ `OfficeReadResult.pageContentWidth`, and a picture inside a TABLE divides by that table's own `TableFormat.sourceWidth` and is clamped to its CELL instead — a page-scaled picture sits small in a cell stretched to fill the column, and an unclamped one blows apart the fixed column geometry invariant 39 depends on. `nil` page width → scale 1, authored sizes verbatim, byte-identical to before this existed. Fusing this with `fontSizeScale` was tried in both directions and both fail: riding the font scale made ⌘+ inflate photographs and left no way to enlarge type alone, and pinning at 1.0 left photographs tiny beside 1.6×-enlarged text. Because the scale depends on the COLUMN, the size cannot be frozen at build time — each graphic carries what it was measured against (`MDAttr.officeGraphic` → `OfficeGraphicInfo.authored`/`basisWidth`), and `DocumentWindowController.resizeOfficeGraphics` re-derives it through the SAME `OfficeTextBuilder.graphicSize` the build used, from the AUTHORED size and never from the current on-screen size (which would compound rounding across a hundred resizes). Without that pass a widened window re-wrapped text and re-solved every table while the pictures stayed built-size, and the page visibly came apart. It does NOT weaken invariant 1: that forbids a reserved size depending on whether PIXELS are loaded, and this one is identical loaded or not. Alignment rides along in one place — `OfficeBlock.aligningGraphic(to:)` applies the CONTAINING paragraph's alignment, so all three formats (docx `w:jc`, ODT `fo:text-align`, HWP's own) state it once; a graphic's own explicit alignment always wins.

47. **A table border edge has THREE states, and an unmentioned one resolves against whether the TABLE drew a box — not against whether anything declared anything.** `BorderDecl` is `.drawn(side)` / `.suppressed` (turned off) / `nil` (never mentioned). "Off" and "silent" used to arrive as the same `nil`, so the builder guessed differently depending on whether a neighbouring edge happened to speak — a report whose table ruled only its header row and inner grid lost its outer box entirely. Resolution, per placement: where the table drew at least one real rule (`EdgeBorders.drawsAnyEdge`) an unmentioned edge draws NOTHING (the table described its own geometry and left this edge out); where the table drew NO box the edge falls back to the ordinary cell-direct > table-direct > table-style > theme cascade. That second arm is the correction two independent reviews found from different angles: keying off "anything was declared" let a single cell carrying one `w:val="nil"` — exactly what Word writes when someone removes one rule from one cell — strip its other three edges of the cascade the rest of the table is using, measured on a 2×2 as 1pt-faint / 0 / 1pt-faint / 0 against neighbours at a solid 1pt. **A faint stand-in outline for the first arm was built and then REMOVED (`22a9758`) — do not propose it again:** across one 114-table report, 95 tables turn their outer rules OFF explicitly and only 19 merely never mention them, so a rule keyed on "unspecified" fired on a sixth of the tables and skipped the rest — the reader saw some tables boxed and some open with no way to tell why, which reads worse than honestly showing what is there. A table that declared NOTHING is unchanged, which is every markdown, HWP and ODT table (invariant 37); a table that explicitly turned every edge off draws nothing where it used to get the app's default rule, matching Word. Disagreement between two cells about their shared boundary is invariant 50, which runs after this resolution, not instead of it.

48. **The reflow passes are paid on EVERY render, so they must be cheap, idempotent, and never run against the outgoing document.** Three walk the whole storage from `updateTextInset` — `reanchorFillMarginTabs`, `resizeTableColumns`, `resizeOfficeGraphics` — measured at 91 ms per full pass on a 62-table HWP. Three rules, each earned by measurement. (a) A caller about to REPLACE the storage wants `settleReadingColumn()`, the geometry-only half, not `updateTextInset()` — the old code paid the full walk THREE times per ⌘+ press (render, `display`'s opening call, its async tail) when only the last runs against the new string. (b) An OFFICE table is BUILT at the width it will be laid out at — `MarkdownDocument.render` hands `OfficeTextBuilder.build` a `tableWidth` of the column minus one `lineFragmentPadding` per side, the same number `resizeTables` re-solves to — so the first paint is the final one; building at the placeholder and resizing a moment later is the visible "table draws small, then snaps wider". Markdown still uses `TableBlockBuilder.initialColumnWidth`, which is why that placeholder stays. (c) A pass touches only what actually MOVED and invalidates ONCE over the union of the ranges it touched: per-cell invalidation measured 73 ms on a 62-table Korean form (1,702 cell paragraphs) against 5 ms on a 610-cell Word report — a 14× gap on 2.8× the cells, because each `invalidateLayout` re-walks everything after it — and recording every cell unconditionally invalidated the whole document to set widths to the values they already had.

49. **Slicing or deferring `precomputeLayout` was measured twice and rejected twice: the freeze is the REBUILD, not this pass.** Its `chunk = 20_000` really is the wrong bound — characters misread office documents, so a 38-table report is laid out entirely in one uninterruptible turn while a 1.2 MB markdown file gets sixty — and both obvious repairs were built, measured on real documents, and reverted. (1) Slicing by TIME (2k characters per pass to a 10 ms budget) on a 62-table HWP: worst freeze unchanged (216 ms → 194–238 ms) and time to a fully laid-out document roughly doubled (665 ms → 1126–1342 ms). (2) Bounding each step by STRUCTURE as well as length, plus laying the VIEWPORT out first, on a 38-table / 27-image docx: against a baseline of 2 turns / 105–121 ms measured six times — viewport-first alone 2 turns / 121–148 ms, a 256-unit structural cap 3 turns / 155–170 ms, a 64-unit cap 10 turns / 186–192 ms — monotone in turn count, every variant worse, worst freeze improved in none. Both failed for the same reason: the freeze is `OfficeTextBuilder.build` + `display`, so slicing layout finer cannot shorten it and only adds per-turn cost — and time-to-interactive, the one thing (2) was meant to buy, is already paid: at the instant `precomputeLayout` returns, 451 of the 452 visible characters were ALREADY laid out. What this walk buys is the complete SCROLL BAR, not the visible page. Judge a third attempt by `layoutStepCount` (deterministic), not by the stopwatch — wall clock here swings up to 3× under load, with one 2825 ms outlier that never reproduced. `OfficeRenderLatencyTests` is the instrument and pins the character bound.

50. **One boundary, one drawer — `collapsesBorders` is OFF and the winner is OURS, not AppKit's.** With collapsing on, two adjacent cells can each declare a different rule and AppKit silently picks; a vertically merged cell changes who its neighbour is from row to row, so one vertical rule changed weight — or vanished — partway down a table with nothing in the document asking for it. Off, `TableBlockBuilder.build` resolves every boundary itself. **Ownership:** an interior vertical boundary belongs to the cell on its LEFT (drawn on `.maxX`), the table's left perimeter to the column-0 cell (`.minX`); an interior horizontal boundary to the cell ABOVE (`.maxY`), the top perimeter to the row-0 cell (`.minY`). Every other side is 0 and costs no `setWidth` call (a fresh `NSTextTableBlock` is already 0) — exactly one rule per boundary, never two and never none. **Winner:** an EXPLICIT suppression beats a bare theme FALLBACK first, because that fallback is our invented default (reached only when `tableDrewABox` is false, invariant 47) and a reader-invented rule must not override an author who deliberately turned an edge off; then wider wins (`nil` counts as 0, so `.suppressed` loses to a GENUINELY declared rule — what Word does); then equal widths defer to whichever side was declared; then the owner's own colour, so nothing depends on scan order. **A merged cell takes the WIDEST winner across its whole span** — one block carries one width per edge, so per-segment fidelity isn't available to us, and the widest keeps the rule consistent down the merge instead of vanishing mid-table. Fold that over a **SORTED** neighbour order: a bare `Set<Int>` iterates in a per-process hash-randomised order, and the same document's merged rule came back red 6/14, blue 5/14, green 3/14 across 14 launches. **Geometry follows:** `contentWidth = cellWidth − 2·padding − its own two widths, in FULL` (the interior halving modelled collapsing and is gone), and `edges(forWidth:)` solves across `width`, not `width − 1` — measured through `NSLayoutManager.usedRect` in a container 200pt wider than target (a container sized AT the target silently clips an overshoot into looking exact), **exactly 600.0000 at 2/3/5/9/13 columns, merged and mixed**, where the collapsing formula gave 599.5. The LAST edge is floored to `usable.rounded(.down)`: a fractional reading column (705.5) would otherwise round to 706 and put the final rule outside the container. **Padding shrinks before a border does**, floored to an integer — a column too narrow for `defaultCellPadding` on both sides is ours to compress, a rule the document asked for is not; only a column narrower than its own two borders still overshoots, boundedly. **`rowSpan` is UNTRUSTED input:** `OdtReader`/`HwpReader` pass `table:number-rows-spanned` and HWP's own span through verbatim and only `DocxReader` clamps at its source, so EVERY walk of `p.row..<(p.row + p.rowSpan)` against the neighbour grid must clamp to `rowCount` — one unclamped read trapped `Index out of range` and killed the app on opening an ordinary `.odt`, while all 832 tests stayed green because the docx path clamps first. Cost, four interleaved paired runs on the 2,489-cell report: `OfficeTextBuilder.build` 118.5 ms median against HEAD's 118.5, a warm ⌘+ press 391 against 397 — indistinguishable end to end (an isolated 30-sample measurement of the build stage alone did find ~+12 ms, which the single-neighbour fast path halved). Parity holds: `resizeTables` subtracts both widths in full too, and cells the resize pass still moves after a render: 0 of 2489.

51. **A table cell's terminating newline carries the CELL's own attributes, so a cell costs ONE attribute run and not two.** `TableBlockBuilder` appends a `"\n"` after each cell; appending it bare let the `enumerateAttribute(.paragraphStyle)` pass stamp a fresh default `NSMutableParagraphStyle` on it — default alignment, no font, no colour — which can never equal the cell's own run. Dumped verbatim: `{1,6} "발간등록번호" keys=[NSColor,NSFont,NSParagraphStyle,mdBlockId] align=1` then `{7,1} "\n" keys=[NSParagraphStyle,mdBlockId] align=4`, 53,522 times on one report. **Every document with a table paid it**, and it was the single biggest cost in this reader: attribute runs 107,937 → 56,563 (−48%) on that report and 17,389 → 15,308 on the reference, `display` 3,595 → 1,051 ms (−71%), worst freeze 7,620 → 3,304 ms, the reference's ⌘+ 1,903 → 1,031 ms. Installing into a LIVE text view costs ~50 µs per run and is indifferent to what the runs contain (measured 1 run/13 ms, 19,655/913 ms, 108,353/5,585 ms) — so run count is the knob and half the runs were these newlines. Inheritance is an ALLOW-list (font, colour, paragraph style, baseline offset, block id, bookmark, srcRange): anything that DRAWS or is clicked (attachment, background, underline, strikethrough, link) keeps the bare terminator, so a future attribute degrades to the old behaviour instead of silently riding along. An EMPTY cell keeps the bare terminator too — it has no attributes of its own, and the preceding character's belong to the PREVIOUS cell. Laid-out height identical to five decimals on ten real documents, `--extract` byte-identical over 1.4 MB, `resizeTables` still moves 0 of 51,968 cells. The same bug existed one layer up, in `OfficeTextBuilder.cellContent`'s INTERIOR separators between the blocks of a multi-paragraph cell, fixed the same way: that function already re-applied each paragraph's STYLE across its terminator (TextKit reads spacing and line height from a paragraph's last character), so `unifyTerminator` extends that existing pass to the rest of the allow-list rather than adding a second mechanism — 12 lines, reusing `TableBlockBuilder.inheritableTerminatorAttributes` rather than copying it, because a divergent second list is how the two halves would drift apart. The separator belongs to the paragraph it TERMINATES, which is forced rather than preferred: the style pass already stamped the preceding paragraph on that character, so taking the FOLLOWING block's font would leave it matching neither neighbour. Interior separators: reference 2,323 → 374, report 271 → 7, and total attribute runs fall by MORE than the separators removed (−2,548 against −1,999 on the reference) because identically-styled paragraphs then coalesce end to end. **The residue is irreducible: 268 of the reference's remaining 374 terminate an EMPTY paragraph**, which has no attributes to inherit — the empty-cell rule reaching one layer up. Verification for that second change: laid-out height identical to five decimals on both real HWPs and every fixture, `--extract` byte-identical over 1.4 MB, `resizeTables` still 0 of 51,755 cells.

52. **Font substitution is resolved once per DECLARED FONT, gated on a sample character, and NEVER splits a span.** The earlier design asked CoreText per span and split each span into maximal same-substitute runs; that cost 2,209 CoreText calls and 17,910 spans on the reference HWP where the current one costs **22 calls and 9,328 spans** — built font runs 19,088 → 9,239, installed 23,097 → 15,516, warm ⌘+ −19%, worst freeze −34%, and `FontSubstitutionResolver` got 95 lines SHORTER. The rule: for each distinct declared font, take the most common character under it that is neither absorbing (Common/Inherited/Grapheme_Extend) nor Private Use, ties broken on the lower codepoint; ask CoreText once whether the declared font draws it; if not, stamp that answer across every span using that font. Each exclusion was found by a real document: restricting the census to non-ASCII put 5,177 Latin characters onto Lucida Grande because a stray `Ⅴ` won; not excluding absorbing classes made every census answer "space"; not excluding PUA and not refusing LastResort put 450 characters of drawable Korean out as boxes. Gate on COVERAGE, never availability — Times New Roman, Arial, Helvetica and Georgia are all installed here and none draws Hangul, which is exactly what Word writes into a Korean document's ascii slot. The cost is honest: `nil` in `Span.resolvedFontDescriptor` now means "draws the SAMPLE character", so a stray glyph inside an otherwise-covered paragraph is still substituted by AppKit at draw time. **A Hancom PUA bullet draws as a box, and that is the owner's decision, not an open item.** Measured on a real 행정업무운영편람: 97 occurrences of 13 distinct PUA codepoints in 281,887 characters (0.034%), 9 starting a line — `U+F02FC` 33 times, `U+F0848` and `U+F02EF` 17 each. A PUA codepoint has no meaning outside the font that defines it, Hancom's own fonts define these, and CoreText finds **zero installed fonts** here that can draw one, so the fallback is `.LastResort` and every app without Hancom's suite shows the same box. Mapping frequent ones onto standard bullets was offered and declined — *"글꼴이 없는 경우는 어쩔 수 없지 그냥 깨져도 깨진대로 보여줘"*. Do not add a guessed substitution table. **Flattening every font to one family was measured and is WORSE — do not propose it as a speed setting:** installed runs 108,353 → 160,626 (+48%) on a real report, because the system font has no Hangul and AppKit then substitutes per character. Even flattening font AND colour AND paragraph style together lands at 70,042 installed against 1,654 built — the residual is all Korean substitution, so no amount of uniformity escapes it.

53. **Per-script fonts: each format keeps its OWN slot vocabulary and its OWN classifier table, and a run breaks on the resolved FAMILY NAME — never on the slot index.** A document names a family per script (docx `w:rFonts` 4 slots + theme refs, ODF 3, HWP's `CharShape.font_ids[7]`), and reading only the Latin one drew Korean in the face chosen for English. **Measured, 1,557 real HWP/HWPX: 53.6% declare different fonts across their slots** — one row is `["휴먼명조", "Palatino Linotype", "HY신명조", …]`, i.e. Latin really is meant to differ. Do NOT unify the three classifiers: Word's table is keyed on Unicode BLOCKS and its `cs` slot is reachable ONLY by a run-level `w:cs`/`w:rtl` (Hebrew, Arabic, Syriac and Thaana all go to **ascii**); ODF §20.358 Table 22 is its own normative range table whose 22 GAPS — space, all General Punctuation, PUA, everything above U+FFF0 — are WEAK and absorb; HWP maps the shared UCD script table onto seven slots. Merging any two silently mis-renders the third. `ScriptRunSplitter` is shared, and the family-not-slot rule is what makes invariant 37 structural: two slots naming one family produce ONE piece, i.e. the original span. **A slot the document never DECLARED states no opinion and must not break a run either** — three independent reviews found that from three directions, because comparing `nil` as though it were a family name reintroduced slot-splitting through the back door: an ODT under a western-only style turned a 167-character Korean paragraph into 50 spans (`제1항` became 제 / 1 / 항), and a docx carrying `w:asciiTheme="minorEastAsia"` split every sentence in two and left the Latin half family-less, 1,189 spans becoming 2,186. Two more rules from the same reason: a theme role whose own default is empty falls through to `a:latin` (`a:ea`/`a:cs` are empty in FIVE of five real themes, and Word only reaches the family there through the document's LANGUAGE, which this reader may not consult), and a docx run of pure separators takes its NEIGHBOUR's family before the block table's, because Word stores a Korean sentence as one `w:r` per word so the space between two words is its own run and absorption structurally cannot reach it — keeping the table first measured 5,396 spans averaging 2.3 characters. Swift has no `Script` property (verified: 58 members of `Unicode.Scalar.Properties`, none of them script), so `ScriptRanges.swift` is GENERATED from the UCD by `Scripts/gen-script-ranges.py` with the licence notice travelling with the data; ICU is reachable via `-licucore` and is used ONLY as a test-time oracle, never linked into the app, because Apple has never documented that C API.

54. **A picture whose format has no decoder names its format; it never shows a stretched broken-image glyph — and the reconcile gate must know that decision is final.** `NSImage(data:)` returns nil for WMF, and the old `att.image = image ?? brokenImage()` stretched a 22×22 SF Symbol across a 700×465 pt frame, which reads as "this file is corrupt" when the truth is "this reader cannot draw this format". Measured: the reported document is 8 of 11 pictures WMF, the reference manual 1 of 60 — which is the whole reason one was reported and the other never was — and across 340 HWP files, 95 of 1,825 pictures (5.2%) are undecodable, all WMF or PCX, but BIMODALLY so (some documents lose 13 of 13). The pixels usually exist: LibreOffice rendered one of those blobs to a correct 794×1123 chart matching the caption we draw beneath it, and rhwp itself vendors a WMF→SVG converter that is `pub(crate)` and behind a feature flag. The label is decided at READ time and drawn by `SizedAttachmentCell`, never by assigning an image, because an attachment built as `.image` carries no `placeholderLabel` and `resizeOfficeGraphics` would stretch a labelled card on every window resize. **`reconcileMedia`'s on-screen gate must test the label as well as `att.image == nil`**: the old broken icon was what closed that gate, so without the second half every undrawable picture is re-read, re-decoded and re-failed on every scroll for as long as the document is open.

55. **A table too big to build without freezing the open is left out of the FIRST PAINT only, spliced back afterwards, and the document is then walked exactly as any other render walks it.** `OfficeTextBuilder.giantTableIndices` draws the line at `rows >= 50 AND rows × columns >= 500` — measured over 1,280 documents / 11,207 tables it fires on **0.68% of tables and 1.4% of documents while removing 30.9% of all grid cells**, and on **zero** of the reference manual's 388, which comes out unchanged (250,088 characters both ways). Both halves are load-bearing: row count alone catches a 103×2 prose table that costs nothing. First paint on a 51,816-cell report goes **3,130 → 628 ms**, three interleaved repeats at 628/641/620. The work is MOVED, not saved — 398 ms of deferred build plus 1,736 ms of payback is one full build within 1%. **Two rules were learned by shipping them wrong, both counter-intuitive.**

    **(a) The document MUST still be walked after the splice.** The original design skipped `precomputeLayout` on the theory that TextKit settles the giants by itself in ~7.5 s at a 45 ms worst slice — TRUE while the reader sits still, and worthless, because a reader scrolls. Arriving at an unlaid region forces every character in between in one call: **69,460 and 80,008 ms**, measured twice. With the walk the same scroll costs **3.2 and 5.1 ms**, and the walk's own slices (274–682 ms) are no worse than what the undeferred shipping build already produces on the same document (1,367 ms). The prototype rejected this walk on its worst slice alone and never priced arrival.

    **(b) A RE-render must never defer — first paint only (`hasPaintedOnce`).** Deferring on ⌘+/⌘−/⌘R takes the reader's anchor against the FULL document and then replaces the storage with a string a third as long, so `restore` clamps that character to the deferred string's LAST one and parks the viewport at its bottom. The splice then inserts 273,016 characters ABOVE that point, leaving the viewport inside a grid nothing has laid out — and from there it is DRAWING, not scrolling, that pays: filling the layout hole under the visible rect advances ~800 characters per pass at 150–300 ms a pass. Same document, same process, only the anchor differs: at character 0 a press costs a 498 ms worst turn and settles in 1,275 ms; at character 326,797, **9,038 ms and 181 turns over 100 ms**. The prize was always a first-paint prize. Reviving re-render deferral needs an anchor that survives the swap — mapped through `MDAttr.blockId`, the one identity both strings share — and it must be measured with the reader DEEP in the document, because at the top every version looks perfect.

    Everything else follows. The judgement lives in the RENDER layer, so `--extract` cannot see it (proven byte-identical at 725,535 and 604,800 bytes — invariant 40). The payback builds run **one per run-loop turn** (25/156/154/695/706 ms); all five in one turn would trade the freeze for a 1.7 s one, and building them off the main thread was measured (876 ms, worst main slice 32 ms, output equivalent) and rejected because `NSTextTable`/`NSParagraphStyle` construction is not documented as thread-safe. The rebuilt grid inherits the stand-in's **block id** or two blocks merge into one stop for the reading cursor (invariant 19). The anchor is restored FROM the walk's completion, never before it — restoring first clamps the scroll to a height that does not exist yet and put a reader 75% down at character 298 (invariant 24, from a new direction). Rejected with numbers: permanently flattening these tables reaches the same first paint (691 vs 664 ms) but loses the grid forever and makes the document 1.5× taller; deferring layout without deferring the build buys nothing, because the freeze IS the build.

56. **Two measured things about the deep-⌘+ freeze, one of them a fix that had to be REVERTED — read the second before trying the first again.**

    **(a) The storage swap forces a full layout, and the obvious fix breaks the reading position.** `display` replaces the text while the clip view is still parked wherever the reader scrolled to, so AppKit lays the INCOMING document out that far just to satisfy the offset — inside `setAttributedString`, one uninterruptible call. Measured with the reader 75% into the 401,765-character report: **`display` alone 87,638 ms**, returning with 290,394 characters laid out; scrolling to zero first makes it **937.9 ms** and 192. That part is real. It was committed (`2dea892`) **and reverted the same session**, because that forced layout was propping something up: `restore` scrolls to `min(y, textView.bounds.height − clip.height)`, and with nothing laid out the view's HEIGHT is still stale, so the clamp threw a reader who was 75% down to character 282. Generating glyphs inside `restore` is NOT enough (tried): glyphs are not what sets the frame height. Anyone re-attempting must establish the HEIGHT before scrolling — lay out to the anchor and `sizeToFit`, or restore from a completion after the walk. **The `restore` half of that commit was KEPT and is correct**: ask for the glyph you want BEFORE asking how many exist, because the old `numberOfGlyphs > 0` pre-guard made restore a silent no-op whenever nothing was laid out. **NEITHER property has a test, deliberately** — six attempts across three shapes each produced tests that passed with the fix removed. "A re-render never defers" shows itself only as the storage briefly shrinking, and on any shippable fixture that window is under one run-loop turn; "restore works before anything is laid out" cannot be staged because `display` lays out enough that the old guard passes anyway. Both were verified by measurement on the real 401,765-character document (reader at 41,370 → 282 with the fix out, correct with it in) and the gap is written into `GiantTableDeferralTests`. Check any new test here against a mutation before trusting it (invariant 30).

    **(b) The freeze itself is AppKit's, and it is quadratic.** Sampled during a 64 s freeze, the whole main thread sits under `CA::Transaction::flush` → `NSTextView drawRect:` → `_glyphRangeForBoundingRect:…okToFillHoles:` → `_NSFastFillAllLayoutHolesForGlyphRange` → `NSATSTypesetter` → **`NSTextTable rectForBlock:` → `NSTextBlockLayoutHelper init` → `characterRangeForGlyphRange:` → `_NSFastFillAllGlyphHolesForGlyphRange`**. Laying out ONE LINE inside an `NSTextTable` fills holes across the WHOLE document, so a 2,196-row table pays it per line — hence scaling with depth (12.6 s at 25%, 64 s at 75%). Two candidate fixes measured NOT to help: pre-generating every glyph (`ensureGlyphs` over 401,765 characters is only 22 ms — the holes are LAYOUT holes), and taking our own `drawBackground` off the layout-forcing query (AppKit's `drawRect:` makes the same call itself). Flipping `allowsNonContiguousLayout` DOES fix it — ⌘+ at 75% goes **65,853 → 5,073 ms worst turn**, suite green, scroll-bar fear does not materialise (+0.0% height error) — but it costs invariant 1's territory: `demo/math.md` jumps **1,366 pt** when its formula lands (42 pt today) and `demo/images.md` lays out **7,982 pt against 12,124**, because less space is reserved when the visible range is computed non-contiguously.

    **The owner's chosen direction supersedes all of it.** A paged document (docx/odt/HWP — anything with `officePageContentWidth`) should be ZOOMED like every real viewer rather than re-typeset at a new font size; markdown and plain text keep the font-size model because they have no page. That removes the rebuild entirely instead of optimising it, retires the three whole-storage reflow passes for office (the column stops changing), and collapses invariant 46's graphic scaling. Design, build order and the numbers to beat: `docs/02-planned/paged-zoom-design.md`.

57. **PAGED = THE DOCUMENT IS THE TRUTH, THE APP CONTRIBUTES NOTHING.** A paged document (`officePageContentWidth != nil`, never `kind == .office`) is reproduced, not re-typeset: ⌘+/⌘−/⌘0 are `NSScrollView.magnification` and rebuild nothing; every absolute comes from the file. Owner's rule: *"우리 자체 판단을 버리고, 파싱하는 정보 그대로 다 보여지게 하자 (정의되지 않은 값들만 디폴트를 뭘로 지정할지만 옵션)"*. Measured by opening one real Korean report beside Word, Pages and Hancom's HWP Viewer at matched scale. Four of the five breakages were the app filling in a value the document HAD stated.

    **(a) "The document said nothing" must be EARNED — it was false five times.** (1) Word keeps a table's cell margin in the **default table STYLE** (`w:style[@w:type="table"][@w:default="1"]`), not on the table; reading `w:tblPr/w:tblCellMar` alone turned an explicit `top=0 bottom=0` into 7pt on all four edges — 14pt of a 28.3pt row where Word draws 18.5pt. (2) A Korean/Japanese document states line height ONCE, section-wide, as `w:sectPr/w:docGrid@w:linePitch` (360 twips = 18pt); unread, every unstated line fell to the font's natural 13pt. (3) A docx omitting `w:sz` from `w:docDefaults` is not asking for 11pt — 11 is what Word WRITES into a new file, 10 is what it ASSUMES when the element is absent, and that constant is the theme base size, deciding **99.1%** of that document's characters (9,567 of 9,657). (4) Heading numbering (`1.`, `1.1.`, `가.`) lives in the heading STYLE's `w:numPr`, not the paragraph. **Before adding a fallback, find where the format keeps that value** — invariant 33 from a fourth direction. (5) **HWP, the largest:** the parser exported no cell margin, so every HWP cell fell to `TableBlockBuilder.defaultCellPadding` = 7pt invented, four edges. Sweeping that one constant on a real 490-page 행정업무운영편람 against the official viewer's **429** pages: **7pt → 495 · 4 → 471 · 2 → 449 · 1 → 439** — the whole 66-page gap was that number. Fixed upstream: rhwp's `Cell::effective_padding(&table.padding)` already resolves the `aim` flag, the table-wide fallback and the preserved-pad hygiene limit against Hancom's own PDFs, so the FFI exports THAT (four `padLeft/Right/Top/Bottom` in points) and `HwpReader` maps it to `Cell.edgePadding` — one rule, in the place that earned it. Real per-cell values (1.41 / 0.00 / 2.83 / 5.10 / 8.50pt over 5,494 cells) take the file **495 → 455** pages, its `.hwpx` twin 160 → 148. The remaining 26 are a DIFFERENT quantity — rhwp's own pagination of the same file is **393**, 8% SHORT of the viewer while we are 6% long — so do not "fix" it by tuning padding back up. **Both candidates for that residue are dead ends.** (i) No declared row height exists: `Table.row_sizes` is the CELL COUNT per row (`UINT16[NRows]`, `rebuild_row_sizes()`), and the model carries no row-height field. (ii) Line-height overshoot is real but nearly free to remove: swapping the paged percent arm from `.atLeast` to `.exact` moved the file **455 → 452** pages and the `.hwpx` twin not at all, against a predicted ~34 page-equivalents. Why that prediction failed is the part worth keeping: **summed excess is not page-equivalents** — 10,021 of this document's 14,545 lines are inside TABLES, and a row's height is its TALLEST cell, so shrinking most lines in a row changes the row by nothing. Judge a candidate by moving the number it claims to explain (one release build + one `--pdf` run), not by an integral. ~26 pages stay honestly unexplained. Together these took the measured row 28.5 → 19.17pt against Word's 18.48.

    **(b) The opening zoom is NOT 1.0.** Measured on the owner's machine: **Word 120%, Pages 125%, HWP Viewer ~115%** (its status bar reads "86%" in 96-dpi units — 0.86 × 96/72 = 1.147, confirmed off its own ruler at 1 cm = 65.4 px on a 2× display against 56.7 px at actual size). The value moved twice from being reasoned about rather than measured: fit-to-window opened documents 1.5×–2.9× oversized; 1.0 then made this the smallest reader of the four. `DocumentWindowController.defaultPageZoom` is now **1.8**, on the owner's reading of a real report on this display — the peer band is the floor, not the target, because Word's 120% sits on Word's own 10–11pt body while a Korean report set in 10pt at a 481pt column is smaller on screen. ⌘0 returns there; the menu says "Default Zoom" because "Actual Size" and "Zoom to Fit" were each a lie in turn.

    **(c) NOT ours to fix.** AppKit CEILS an `NSTextTableBlock` border to a whole point — declared 0.1/0.25/0.5/0.75/1.0pt ALL draw 2px, 1.25–2.0 draw 4px — so a document's 0.5pt rule cannot be honoured through `setWidth(for: .border)`. **The cost is LAYOUT, not just pixels, measured through the reader's own builder** (`SubPointRuleSpikeTests`): at a 600pt target a WHOLE-point rule lands EXACTLY (1.0 and 2.0 both 600.00 at 2/3/5/9/13 columns — invariant 50's arithmetic is right), while every fractional width overshoots ~1pt per column boundary and grows linearly (0.5pt → **+2 / +3 / +5 / +9 / +13**), so a 13-column table of Word's ordinary half-point rules ends 13pt past its column. The size of the fraction barely matters (0.10≈0.25, 0.50≈0.75), so no friendlier number tunes it away. **Two figures are withdrawn — 594.0 and 609.0** — both from a HAND-ROLLED `NSTextTable` rather than `TableBlockBuilder`; the spike's own first draft was hand-rolled and reproduced 594.0 at a plain 1.0pt border, where the shipping builder is exact to 0.01. **The GEOMETRY half is fixed**: `TableBlockBuilder.laidOutBorderWidth` rounds a declared width UP to a whole point and BOTH the `setWidth` call and the content-width subtraction go through it, so all eight widths land exactly at every column count (0.0 overshoot across the board). What that does NOT do is make the rule thinner. **The INK half is CLOSED, not deferred — do not propose the custom block again:** the owner read a real report at 1pt and said "1pt는 괜찮아 어색하지 않음". `TableWidthIndependenceTests`/`SubPointRuleSpikeTests` guard the geometry that WAS fixed. A substituted font's line height is NOT the inflater (refuted: `.AppleSystemUIFont` 11pt and Apple SD Gothic Neo 11pt both report 13.0pt, well under Word's 18).

    **(d) The non-paged half must not move, and that is testable.** Every change above is inside `if paged`, and the row-height and grid work broke **zero** existing tests — the in-suite fixtures declare no page width, so they stay on the fill-the-window model (invariant 37). A change here that turns an existing test red without a paged fixture in it is a regression, not a specification.

    **(e) The band between two pages is the document's own two margins.** The band was `header + footer + 12pt`, the 12 a "space between pages" the reader invented. The document states it: **bottom margin + the next page's top margin**, precisely where a header and a footer live in all three formats — so the band is `max(declared margins, what we actually draw)`, expanding past the paper only when this reader's rendering would otherwise cover the body. On a real `.odt` the two agree within a point (85.10 declared against 84.15 invented), which is exactly why a made-up constant survived review. HWP says it most clearly: its exported top margin already INCLUDES the header strip (measured 163.00 = declared 120.48 + 42.52 of 머리말).

58. **A running header/footer is RESERVED by moving line fragments and PAINTED at draw time — it never enters the document string, and every format's live page number is substituted at painting.** `PageBandLayoutDelegate` (the documented `NSLayoutManagerDelegate` hook `shouldSetLineFragmentRect`, NOT an `NSLayoutManager` subclass — overriding `setLineFragmentRect` only RECORDS a rect the typesetter already decided, so the next line lands on top of it) pushes each page's first line down by one band; `PageBandPainter` draws into that space from `drawBackground`, like the reading-line band and comment highlights. Inserting the header into storage was rejected: a page boundary lands mid-paragraph and would split it, and ⌘F would answer nineteen times for one header. **What each half must keep doing.** The band's height is invariant 57(e)'s, and the two outer edges are NOT `textContainerInset` — that can only give top and bottom the same value, so leading room comes from the same line-shift mechanism and trailing room from `setExtraLineFragmentRect`; the trailing effect is ABSOLUTE (`baseline + trailing`), not incremental, because AppKit already reserves one default line height past the last character. The "snap to top" thresholds in `restore(_:)` and `scrollCharToTop(_:)` must add `leadingBand` or ⌘-Home scrolls past a reserved header. A blank entry and an ABSENT one are the same answer — reserve nothing — which is why `w:titlePg` with no first-page part synthesizes an EMPTY entry rather than falling back to the default header (invariant 47's three-state lesson, second place). **Page numbers are three separate mechanisms and only one was ever wired:** Word marks a `PAGE` field with `w:fldChar`/`w:instrText`, ODF caches the last computed number as the field ELEMENT'S OWN TEXT (so an unmarked `.odt` footer reads "- 2 -" on every page), and HWP stores no characters at all (`Control::AutoNumber(Page)` — an unmarked `.hwp` reads "-   -"). All three now set `Span.pageNumberField`, which merge guards must exclude exactly like bookmarks and comment ids, and `PageBandPainter.substitutingPageFields` replaces them per page. HWP's own run lands wherever the vendored parser's control-position fallback puts it — correct for a right-aligned header, at the END of the line for a number centred between dashes. **WHERE each side is drawn is the SHEET's own grid, not a fraction of the gap:** the gap layout opens is the document's margin PLUS whatever room the previous page's last line left unused, so centring in halves of it moved the header and footer a few points per page — measured at 5.5 / 11.125 / 18.25pt above the sheet edge on three consecutive pages, which the owner read as "홀수쪽, 짝수쪽의 여백이 다름". docx states both distances (`w:pgMar/@w:header`/`@w:footer`) and they are used from the sheet edge, clamped into the real gap so an overrunning table cannot be painted over; ODT and HWP state neither yet and keep the halves fallback (ODF measures its top margin TO the header rather than to the body, so it needs its own analysis).

59. **⌘P on a paged document prints the reader's OWN pages — no second pagination engine, because `pitch` IS the paper.** Measured on the reference report: body 671.75pt with margins 99.25/70.90, and the band is exactly those two margins (invariant 57e), so `pageContentHeight + band == 841.90 == A4`, and its width `56.7 + 481.9 + 56.7 == 595.30`. Printing needs one subtraction — `PagePagination.sheetTop` — and `ReaderTextView.knowsPageRange`/`rectForPage` hand AppKit those rects. Letting `NSTextView` paginate instead puts the reader's page 3 across two sheets; mutation-checked, the printout collapses to **1 page against the reader's 4**. Paper is the document's own sheet with printer margins at **ZERO** (the document's margins are already inside the laid-out text — `textContainerInset` sideways, the band vertically), `scalingFactor` 1, both paginations `.clip`; `.fit` would scale the sheet to the printer's imageable width and silently void every measurement invariant 57 protects. **Six findings below, found by printing and then measured; three were also wrong on screen.**

    **(a) Page 0's sheet top must never be CLAMPED, and the room it needs comes from the INSET — a line shift cannot make room at the top of a text view.** `NSTextView.textContainerOrigin` derives from where laid-out content starts: measured on two real documents it is exactly `inset − ⌈usedRect.minY⌉`, so pushing the first line down by the leading band moved the origin by the same amount and the line landed back at the inset with the band cancelled. Page 1's sheet then began 111.0pt (HWP 편람) / 72.0pt (reference docx) ABOVE the view's origin — unreachable on screen, while PRINTING was correct throughout (a print rect may reach past `bounds`), which is why this survived a paginated PDF and was reported by looking at page 1. `DocumentWindowController.verticalInsetHeight` is now `verticalInset + leadingBand`, applied at the ONE place the band is decided plus the two inset assignments, so the sheet lands at +28 and the whole first page is on screen. The inset is symmetric, so the same room appears below the last page — desk, not paper. What must never happen is CLAMPING a computed sheet top to 0: that prints page 1 with a 28pt margin and every other page with its real one.

    **(b) The reading zoom does NOT reach the paper, measured not assumed.** `scrollView.magnification` transforms the CLIP view; the text view's own `bounds`/`frame` are identical at 1.0 and 1.8 (595.3 × 6493.9 both times), so `NSPrintOperation(view: textView)` prints at actual size with nothing to save and restore. `PrintPaginationTests` pins it, so a future zoom that DID move the view's own geometry is caught here rather than on paper.

    **(c) `NSPrintInfo.shared` must be COPIED, never configured.** The old code set `horizontalPagination` on the shared object, self-correcting only because it re-set the same two fields every time; adding paper size and margins there would leak A4-with-no-margins into the next document printed.

    **(d) A header is authored against the PAGE's body width, not the reading column** — the reference report printed with NO running header because of this. `configurePageBand` took `columnWidth` from the live text container, which for a paged document equals the page body only once the window has been laid out; the first render can precede that, leaving the container at its 600pt starting size with nothing re-running the band. The header is `w:jc="right"`, so it was built into a 600pt box laid at the page's own left margin and its text ended at x=656 on a 595.3pt sheet. Taking the width from `officePageContentWidth` makes it a constant of the FILE (invariant 57) and removes the timing dependence; Word's own PDF shows the header 42 times, ours now 7 of 8 pages (page 1 is a `w:titlePg` cover, correctly bare).

    **(e) A footer belongs to its own sheet, and when it cannot fit there it is SKIPPED, not moved.** `sheetEdge` clamps into the gap layout actually opened so an overrunning table is not painted over — and when the overrun passes the paper's edge that clamp pushes the footer onto the NEXT sheet: measured, a table overran by **1.12pt** and printed `- 5 -` at the top of page 6. `PageBandPainter.footerFitsOnItsSheet` judges it against the UNCLAMPED grid position, which is exact — the delegate always shifts a page's first line to precisely `page × pitch + leadingBand`, verified on all 8 pages of the reference (841.90, 1683.80, 2525.70, … to the hundredth), so page boundaries never drift even though the gaps between them do. Skipping follows `bandExists`'s existing judgement: a missing page number reads as a short page, a misplaced one reads as a corrupt document. The page outline surfaces the same fault on screen, so this is not a print-only correction.

    **(f) PAPER HAS NO TOGGLE, and the desk gap must never reach the print grid — it DROPPED TEXT.** Two rules, one call (`DocumentWindowController.beginPrintLayout` → `applyPageBand(forPrinting:)`, undone by `endPrintLayout` when the job ends). First: printing applies the paged shape whatever the View menu says, because the page breaks belong to the FILE — with the outline switched off a printout used to come out as one continuous run with no header, no footer and no page margins. Second, the one that lost content: while the outline is on the band also carries `RenderTheme.pageDeskGap`, which is desk rather than paper, so the print grid ADVANCED 12pt further than each sheet was tall and that strip belonged to no page at all; anything laid out in it was drawn into the PDF and printed nowhere. Measured on a real 147-page HWPX: a sheet covers the body plus its bottom margin (76.52pt here), so a line overrunning by MORE than that fell into the strip — page 34's `a.` item vanished and the next line printed half-cut at the top of the following page, while `pdftotext` still found both, which is why a text-level check called it "no content lost" and was wrong. The gap is dropped in BOTH places it lives — the delegate's own `deskGap` (which sizes the sheet) and `PageBandGeometry`'s band (which sizes the grid) — and `testPrintedSheetsTileWithNoGapBetweenThem` asserts the sheets meet exactly AND that a sheet is the document's own page height, because mutating either half alone still tiles. Overruns still print, into the next sheet's top: an ugly page beats a missing line.

    **PDF export is FREE and must not be built** — macOS's print panel has "Save as PDF", so the moment ⌘P works, so does PDF export; an "Export as PDF…" item would be a second, worse path to the same file. It is also what makes this testable: the operation runs headless to a file, so page count and paper size are ordinary assertions rather than something judged by looking at a printout.

    **THE LIMIT, measured, and NOT a print defect: the reader paginates the reference report to 8 pages where Word makes 19.** Ruled out by measurement, so nobody re-derives them: content is complete (7,314 characters in `word/document.xml` against 7,321 in the storage — an earlier "193,094" was a regex that let `<w:t[^>]*>` match `<w:tbl>`), the line count is right (689 line fragments), the 18pt `w:docGrid` line pitch is parsed and applied, images are not it (2 attachments, 202pt, none zero-height), deferred giant tables are not it (storage identical after the splice), and explicit page breaks are not it (ONE `w:br w:type="page"`, zero `w:pageBreakBefore` in the document AND in `styles.xml`). What remains is concentrated in Word's own front matter — its pages 1–6 hold 51 lines between them — plus tables this reader cannot split across a page (invariant 55/58's known edge), which is why 3 of our 8 printed pages carry table rows inside the margins. A paged-fidelity item (`docs/06-research/2026-07-29-paged-fidelity/`), not something printing can fix.

60. **The View menu's three page toggles — page outline / header / footer — are a LAYOUT switch, not a visibility flag, and the sheets they draw are the same rectangles printing puts on paper.** `PageViewOptions` (global, in `UserDefaults`, all three ON by default) decides three things at once: which entries `MarkdownDocument.applyPageBand` passes on (a hidden header is passed as NO ENTRIES, so it is neither measured nor painted — one mechanism, not a flag each consumer re-checks), whether the band exists at all with nothing drawn in it (`separatesPages`), and whether the page-break hairline is drawn (`drawsDivider` — a real sheet edge says it better, so the rule yields to the outline). `applyPageBand` is called from BOTH the render and `reapplyPageBand`, deliberately one function: a toggle re-deriving the band with its own copy of that arithmetic would drift from the render's the first time either was touched.

    **(a) "쭉 연결되어 보이고" means the band must not be RESERVED.** The comments panel can set a bool and repaint (invariant 38) because its marks sit on glyphs that do not move. This cannot — so a toggle re-solves the band and re-lays out, in invariant 56's order: scroll to the top FIRST (invalidating with the clip parked deep makes the next draw fill every hole in one call — 87,638 ms against 937.9), then invalidate, then restore the reading position from the layout walk's completion, never before it. It must never reach `MarkdownDocument.render`: nothing is rebuilt, `renderGeneration` does not move, and the reading column of a paged document never shifts by a point.

    **(b) The restore is PARKED, not a completion closure — `precomputeLayout` cancels an in-flight walk whenever a new one starts (`layoutToken`), and a cancelled walk's completion never runs.** Measured while building this: a toggle whose walk was superseded by the render's own opening tail silently lost the reader's place, landing them at character 0 from 75% down. `pendingAnchor` is applied by whichever walk reaches the end, so supersession becomes a later restore instead of a lost one.

    **(c) The desk between two sheets is `RenderTheme.pageDeskGap`, the one number here no document declares.** Two stacked sheets of paper TOUCH, so the space between them on screen is a property of the desk. This is NOT invariant 57(e)'s invented constant returning: that one claimed to be the document's own inter-page space, which the document HAD stated. Reserved only while the outline is on, never printed — `PagePagination.sheets` takes it back off, so the paper is exactly the document's own sheet and `makePrintOperation` reads its height from the sheet rather than the pitch. **Getting this wrong looked like nothing had happened:** the first version had no desk, the sheets tiled edge to edge, the desk fill was covered by the very sheets it sat behind, and the feature drew as a hairline indistinguishable from the page-break rule it replaces. Confirmed by pixel-sampling the capture — gap and paper both `(255,254,255)`.

    **(d) With the outline on, the FIRST and LAST pages get their full margins** (`leading = max(headerLeading, marginTop)`, and the mirror for the footer). Otherwise page 1's sheet begins one top margin above the first line, which with only a header's worth of leading room is ABOVE the view — so page 1 draws with no top border and a visibly shorter margin than every page after it. The two outer PAINT arms then place their content at the document's own header/footer distance INTO that room, reducing to the previous `top: 0` whenever the reservation is only as tall as the header.

    **(e) Owner decisions, settled here rather than asked.** GLOBAL rather than per window (a reader who wants continuous flow wants it for every document, and the choice must survive a relaunch); all three ON by default (the owner's framing was *"페이지 외곽 모양(그럼 선이 필요 없어짐)"* — the outline REPLACES the rule, so shipping it off would hide the feature); NO drop shadow (it costs a blur per sheet on every scroll pass, and the desk plus a hairline already reads as paper). One menu click to change.

    **(f) A page is CENTRED on the paper's width, and four separate things kept undoing that** — all four reported by the owner looking at the screen, each a different mechanism. (1) `sizeToFit` widens a text view's frame back to its clip view, so `PageCenteringClipView`'s `frame < clip` test silently stopped firing — measured at 727.2pt of frame around a 595.3pt sheet, and 909.0pt after a zoom press, which also drove the magnification to `clipFrame ÷ frame` = 0.8876 (a zoom-IN that zoomed OUT, two feedback loops solving for each other). Fixed at the root: the clip view reads `ReaderTextView.pagedPaperWidth`, a constant of the DOCUMENT, so no frame drift can reach it; the frame is additionally pinned by `pinPagedFrameWidth` after every `sizeToFit` and every magnification change, because the frame is the SCROLLABLE area and a wrong one lets a reader scroll into empty desk. (2) AppKit calls `constrainBoundsRect` when the bounds ORIGIN changes, not when the clip's FRAME does — so opening the table of contents narrowed the reading area and left the old origin; `recentrePage()` now asks for the constraint explicitly. (3) THREE scroll call sites hard-coded `x: 0` (`restore`, `scrollCharToTop`, and the reveal in the outline jump); each meant "scroll vertically to here" and each undid the centring on every reflow, which is why the page snapped left on opening AND closing the panel. They now preserve `clip.bounds.origin.x`. (4) The desk BESIDE the page is the scroll view's background (`syncDeskBackground`) — the text view cannot paint outside its own bounds, so without it a centred page sat on the same white as the paper and read as no page at all.

    **(f2) ONE function applies the whole paged view state — the fix for the CLASS rather than for those four bugs.** Five rules describe a paged view (which width is the paper, how wide the scrollable frame is, what colour the space beside the page is, whether the page is centred, whether a sideways scroller is needed) and they were applied by FIVE paths each handling a different subset. Audited: the reading-column settle did all five, a magnification change three, `sizeToFit` one, and the View-menu page toggle **none** — which is why switching the outline off left the desk colour behind. `applyPagedViewState()` does all five and every path calls only that; it is a no-op for a document with no page, so the non-paged branch goes through the SAME function rather than a second divergent one. Two more single-source repairs from the same audit: `pageSheets` is DERIVED from `printSheets` (two copies of the sheet arithmetic is how screen and paper would come to disagree), and the desk gap is carried on `PageBandLayoutDelegate.deskGap` — the layout that RESERVED it — rather than re-read from the preference at draw time, which left a window where a paint would take the new answer against the old band and mis-tile every sheet by 12pt. **Testing this needs care:** a toggle's own layout walk ends in `sizeTextViewToFit`, which applies the same state, so a test that waits for the async tail passes whether or not the TOGGLE did it — fake-green, confirmed by mutation. Assert IMMEDIATELY after the toggle, which is also what a reader sees.

    **(g) A panel that takes width away shrinks the page to fit; nothing ever enlarges it.** `shrinkPageZoomToFit` is one-directional by instruction — *"무리하게 줄이진 말고, 창이 우측으로 삐져나가지 않도록 축소해서 맞추라는 뜻"* — so the sidebar and the comments inspector call it and a manual window resize just reveals more desk (the removed "zoom follows the window" rule stays removed). It fits `paper × zoom` into the reading area MINUS `pageWindowSideMargin` on each side.

    **(h) A page break is never drawn through a table.** A line inside a table cannot be shifted (invariant 55/58), so a table crossing a boundary overruns it and layout opens no band — and a sheet drawn on the arithmetic grid put its edge, and the desk behind it, in the middle of the table's rows. `PagePagination.joiningUnopenedBoundaries` unions those sheets, which says the true thing: this page ran longer than its paper. SCREEN ONLY — paper cannot stretch, so `rectForPage` keeps the paper-sized grid, and that divergence is the medium's rather than two implementations disagreeing.

    **(i) A stored global preference makes any test that measures the band depend on it.** `PageBandReservationTests` pins the pre-feature shape in `setUp` (outline off, header and footer on) — otherwise nine of its assertions move with the shipped default and the suite reads differently for a developer who had switched the outline off. Every new test here resets the store on both sides.

61. **A table that will not fit on the rest of its page is MOVED WHOLE to the next one — decided by measuring a layout that already happened, and carried out by shifting exactly ONE line.** Until this existed a table ran past its page's text bottom, so its rows printed inside the margin: on the reference report 4 of 16 tables overran by 71 / 139 / 145 / 236pt, three of its eight sheets. The screen could tell that truth (`PagePagination.joiningUnopenedBoundaries` unions the sheets), paper cannot.

    **(a) SPLITTING was built and measured here, and invariant 64 later shipped it under a menu — read both.** What follows is why it is not the DEFAULT and can never be unconditional. Letting the ordinary between-page rule shift table lines produces a real Word-like split, and on a table of single-line rows it is flawless: rows stay whole, each page's segment keeps its own border box, header and footer land in the gap (`docs/fixtures/office/paged-visual/tablepage.docx`, captured). On a real report it TEARS. A vertically merged cell spans the boundary, so the half of the row that moved leaves that cell stretched across the gap — with this reader's own running header and page number painted inside the table — and the row's two halves end up a page apart. Splitting honestly needs `NSTextTableBlock` geometry we deliberately do not own (invariants 39/42). The safe-row-boundary variant is what invariant 64 built; it does not save the reference report's first table, whose left column is merged across the very boundary in question, so that one is still carried whole.

    **(b) ONE line is enough, measured not assumed.** The typesetter positions each line after the previous one, so shifting a table's first line carries every later line with it — the property the between-page rule already relies on. Pushing the reference report's table #0 left its height identical (438.45pt both ways) and landed its visual top exactly on target. **But the first line in TEXT order is not the table's top**: a vertically merged cell is centred in its own span, measured 21.35pt below the table's top edge on that same table, so `TableMetrics.topInset` carries that distance. Moving by the naive `target - rect.minY` would land the visible top that far into the page.

    **(c) MEASURE, then place — the height does not exist when the typesetter asks.** At the moment `shouldSetLineFragmentRect` is called for a table's first line nothing has measured that table, so `DocumentWindowController.settlePagedTables` walks the COMPLETED layout, decides (`PagePagination.tablesToPush`), and re-solves. That extra pass rides `precomputeLayout`'s existing chunked walk, so no single turn grows. Cost on real documents (10k–27k characters, 8–13 tables moved): **2–3 rounds, 85–260ms total**, of which the measuring step is **1–4ms** — the cost is entirely the re-layouts. A document with nothing to move pays one line-fragment walk and stops.

    **(d) The two refusals are load-bearing.** A table TALLER than the page is never moved: it would overrun the next page just as far, having emptied the one it left (a 660pt table on a 220pt page — moving it adds a near-empty page and changes nothing else). And an already-decided entry is kept VERBATIM rather than re-derived: a moved table now fits, so re-deriving would drop it, which would move it back, which would make it not fit — the settle would never converge. Because the record only grows and the layout rule is idempotent (a table sitting at a page top declines to move again), the loop terminates on its own; `maxPagedTableSettles` is a backstop, not the mechanism.

    **(e) The whole document is invalidated each round, deliberately.** Moving a table changes which boundaries LAYOUT opened, and `openedBoundaries` is what the painter and the page outline read — keeping the earlier half of that record while re-deriving the rest would leave the two halves describing different layouts. Re-deriving all of it is one honest pass and (c) says it is affordable.

    **(f) Printing settles SYNCHRONOUSLY first.** ⌘P straight after opening is exactly when the asynchronous settle has not finished, and paper has no honest way to show an overrun. `makePrintOperation` calls `settlePagedTablesFully` before it decides anything.

    **(g) The async seam needs its own test, and it must wait on the RESULT.** Every other check in `PagedTableOverrunTests` calls the settle itself, which proves the rule and says nothing about whether opening a document REACHES it (invariant 29) — a version whose walk never settled would leave them all green while every reader still printed rows in the margin. That test cannot use a completion callback (a cancelled walk's completion never runs — invariant 60b), and it cannot stop at the first sign of life: one round only moves what overran where it stood, and moving it makes later tables overrun, so a wait that stopped there caught the document mid-repagination with three tables still in a margin. It polls until no table ends in a margin.

    **(h) The settle reaches a DIFFERENT fixed point depending on how much asynchronous work ran first, so the reader and `--pdf` can disagree about the page count — measured, and NOT a content loss.** On `testdocs/everything/1790387_prep_final_report.hwpx`: `--pdf` produces **147 pages** (98 tables pushed, 143 boundaries opened, 32 lines in a margin) while the same document printed from an in-process controller produces **156** (92 pushed, 151 opened, 64 in a margin) — with **identical options** (`outline` on, `splitTables` off), identical band (159.37), pitch (853.88), page body (694.51), column (481.9) and window (820×640), and **identical content: 5,492 laid-out lines both ways**. Nothing is missing from the shorter PDF; the same lines are packed differently, and the headless one is the CLEANER by the margin metric. Settling FROM SCRATCH is stable within a process (`pushedTables` cleared + full invalidate + `settlePagedTablesFully`, three rounds: 92 / 156 / `used=133031.36` every time, to the hundredth), so invariant 61(d)'s convergence fear is not what makes these disagree — the starting layout is. Anyone fixing this must pin WHERE the settle starts, not make it re-derive.

    **(i) The residual margin overruns are tables the settle DECLINED to register, and `pushWholeTable` is structurally unable to help them.** It moves a table only when the settle put it in `pushedTables` (`guard let metrics = pushedTables[charRange.location]`), so every other table line is refused — traced on that document: **1,550 refusals**, of which the ones surviving to the final layout are the 32. Turning "Split Tables Across Pages" ON changes **nothing** on this file (147 pages, the same 29 overrun pages, the same three severe ones at +76.5/+68.0/+76.4pt), which is invariant 64(a)'s point measured a second way. And the overrun is not always where it looks: the visible page-34 break sits beside ordinary paragraphs (checked in the source XML — no enclosing `hp:tbl`), while the table that actually overruns is a neighbouring 2-row one. Judge this class from the delegate's own refusals, never from the rendered page.

    **Numbers, and one honest limit.** Reference report 4 overruns → **0**, 8 tables moved, **8 → 11 pages**; its ODT twin 1 → 0; `tago-tables.odt` 5 → 0. `--extract` byte-identical (13,914 bytes — this lives in the RENDER layer, invariant 40), and a document with no page width is never touched (invariant 57d). The page count moving toward Word's 19 is a coincidence of direction, NOT convergence: Word SPLITS tables by default (`w:cantSplit` absent), so a reader that moves them will never reproduce Word's pagination. That gap stays a paged-fidelity item, not a printing defect.

62. **A header or footer that BUILDS to nothing must reserve nothing — "the entry has blocks" is the wrong question, and 28% of real Korean documents answer it wrongly.** `w:titlePg`'s deliberately blank cover header arrives with NO blocks and was always handled; an entry made of nothing but EMPTY PARAGRAPHS arrives with blocks, measured a full line height, and opened a band on every page with nothing in it. Measured over 548 real `.hwp`/`.hwpx`: 94 declare a header or footer at all, and **26 of those 94 (28%) declare one that draws nothing** — and the reference report's own `.odt` declares exactly such a first-page header, which is why it reserved 42.55pt above its first line for a blank. `PageBandGeometry.drawsSomething` decides it from what the entry BUILDS, and `entryDraws` is the single predicate both the band measurement and `DocumentWindowController.configurePageBand`'s leading-band gate ask (they had drifted: fixing only the measurement left the leading gate still asking `blocks.isEmpty`). Two things it must keep allowing: a picture-only header (an attachment is `U+FFFC`, not whitespace, so the text test passes it) and a header drawing only a RULE or shaded band (no glyph reaches the built string, so the BLOCKS are asked for `shading`/`borderEdges` directly). Invariant 47's three-state lesson one level deeper: present, present-but-empty, absent. Found by running `FMD_HEADER_FOOTER_PROBE` across real HWP — which also **closed the "HWP printing unverified" gap**: `.hwp`, `.hwpx`, `.odt` and `.docx` now all pass it, header and footer built to real glyphs with live page numbers and a PDF whose page count matches the reader's (140 / 45 / 450 / 8 pages). The probe itself had to be corrected twice: it pinned no page options, so invariant 60(d)'s full-margin first page read as a failure, and it asked `blocks.isEmpty` too.

63. **`NSWindowController.document` is `unowned(unsafe)`, and this reader asks for it FROM THE DRAW PATH — so every read goes through `DocumentWindowController.mdDocument`, never `document as? MarkdownDocument`.** A window can outlive its document by a run-loop turn, and CoreAnimation commits the next draw inside that turn: `ReaderTextView.drawBackground` → `drawPageSheets` → `pageSheets` → `printSheets` → `pagedDocumentWidth` → `pagedWidth` → `objc_retain` on freed memory. The cast does it — an `unowned(unsafe)` read producing a `+1` reference walks the dead object. It killed the WHOLE SUITE with SIGSEGV, deterministically, and two crash reports a day apart show that identical frame; what made it deterministic was a new test that pumps the run loop. A `weak` mirror kept in step by overriding the setter answers `nil` instead — the same answer every non-paged document already gives, so no caller changed. **Note `swift test` HIDES this**: it reports the suite as merely "failed" with truncated output and no crash report. Run the bundle directly — `swift build --build-tests` then `$DEVELOPER_DIR/usr/bin/xctest .build/arm64-apple-macosx/debug/FastDocReaderPackageTests.xctest`, which exits 139. **There is deliberately no unit test** (invariant 56's reason — every shape tried was fake-green: nil-ing the local reference does not release the document because the window keeps it alive, and `removeWindowController` clears the controller's own pointer so the UNFIXED code answers nil too); verified by that mutation, and the gap is written into `PagedZoomTests`.

64. **A table that will not finish on its page is either BROKEN at a row boundary or carried whole — the reader's choice, except that a table taller than the page is always broken.** The View menu's "Split Tables Across Pages" (`PageViewOptions.splitTables`, global, OFF by default) picks between them; the owner's rule *"표가 한장이 넘을때... 이런 경우는 무조건 쪼개야 해"* overrides it, because a table with no whole page to be carried to could only ever be left with rows in a margin.

    **(a) THE PIECE THAT MOVES IS NOT A ROW — it is the run of rows no merged cell spans.** Breaking above row `R` is safe only when no block has `startingRow < R < startingRow + rowSpan`; break where one does and the merged cell stretches across the gap between two pages with this reader's own header painted inside it, and the row's halves end up a page apart (rendered and looked at — invariant 61a). Rows welded by a merge travel together (`PagePagination.unbreakableGroups`). Registering plain ROWS instead was built and measured on the reference report, which is merged nearly everywhere: the safe rows moved, the merged stretches between them did not, and twenty lines still landed in margins. A table nothing can be broken inside falls back to being carried whole even with breaking ON — better whole on the next page than half in a margin.

    **(b) Both answers are correct pagination, and neither is Word's.** Measured: reference report 11 pages carried / 10 broken, its `.odt` 8 / 7, a 39-page HWP 39 / 38, a 483-page HWPX 496 / 483 — and ZERO rows in a margin either way on every in-repo fixture. Word splits by default (`w:cantSplit` absent), so its page count will not be reproduced by carrying; a paged-fidelity item (invariant 59).

    **(c) The settle re-measures every round, and the metrics are ROUNDED to a hundredth of a point so it can stop.** A piece's height comes back as `161.70000000000002` one round and `161.7` the next, and the loop compares the whole record — without rounding it would never converge. Measured convergence: 2–4 rounds, 95–427ms, on documents from 7k to 100k characters.

    **(d) The page a point sits on needs a hair of TOLERANCE, and this is not tidiness.** A piece moved to a page top lands at exactly `page × pitch + leadingBand`, and that number does not survive the division — measured, a line placed at page 6's top came back as `5051.279999999` against a pitch product of `5051.28`, so a bare `floor` called it page 5, judged it against page 5's bottom, and reported a piece that had just been moved correctly as still overrunning. `PageBandLayoutDelegate.page(of:leadingBand:pitch:)` owns the tolerance and `PagePagination`'s own check uses the same one — the two must agree exactly or the decision keeps asking for a move the rule has already made.

    **(e) THE LEDGER WAS UNDER-MEASURING, and that half IS fixed.** A row's extent was taken from its LINE FRAGMENTS, and a cell draws its padding and border OUTSIDE its glyphs — measured at **3.48pt per cell** over 2,674 cells of a real report, i.e. ~70pt across a twenty-row group, exactly the gap that let a piece the arithmetic said would fit still end in a margin. `DocumentWindowController.laidOutTables` now grows every line rect by its own block's `width(for: .padding/.border, edge: .minY/.maxY)`, applied to every line rather than only the first and last (an interior line's inset loses to the `min`/`max` anyway). Paired A/B on one build: 편람 **580 → 566** lines in a margin with breaking off and **599 → 592** with it on, its `.hwpx` twin **35 → 33** and 36 → 36 with the worst overrun falling 174.37 → 164.13pt. Judged by `topInset`, which is 0 for a ledger built from glyphs alone and is that cell's own top padding once right (mutation-checked).

    **(f) THE LIMIT, measured and NOT closed.** On very large real Korean documents rows still land in margins: 205 lines of a 38-page HWP and 771 of a 483-page HWPX. **192 and 556 of those are inside a single unbreakable piece TALLER THAN THE PAGE** — a one-row table used as a text box, holding a page and more of prose — which cannot be placed anywhere without breaking a row, i.e. splitting one cell's text across two pages, the tear this design exists to avoid. That part is honest. The REST (13 and 215 lines) is unexplained and should not be re-derived blind: the settle converges (4 rounds, and raising the cap from 8 to 40 changes nothing), the delegate SEES every registered piece (1040 of 1040), and it declines them because the recorded height says they fit — traced on one, `visualTop 24446.62 + height 161.70 = 24608.32` against a page bottom of `24636.04`, while that piece's own lines reach `24682`. So a piece's measured extent is smaller than what is drawn inside it, by about its own `topInset`; the row bookkeeping in `DocumentWindowController.laidOutTables` (which keys a merged cell's whole extent to its STARTING row) is the place to look. In-repo fixtures show zero, which is why this needs a real document. **And breaking makes that residue WORSE, the opposite of what the toggle promises** — measured twice on the two documents the owner uses as the release gate: `2025_행정업무운영편람_최종.hwp` **723 → 807** lines in a margin (off → on) and `1790387_prep_final_report.hwpx` **23 → 30**, while the WORST overrun is identical to the hundredth either way (354.68pt / ~175pt), i.e. the dominant offender is the same over-tall unbreakable piece in both configurations and breaking merely adds new boundaries that overrun. The toggle is not a repair for this residue and must not be recommended as one; it stays OFF by default, which these numbers say is better on real Korean documents.

65. **Decoded pixels outlive the document that needed them, and that is what "the app never gives memory back" actually was.** Measured on the release build: freshly launched **15 MB**; open a 20 MB HWPX → 161 MB; open a 10.7 MB HWP and a 14.4 MB DOCX after it, close every window, and it sat at **224 MB with nothing open** — which is why an instance left running 44 hours held **471 MB** with a single markdown file on screen. (b) `malloc_zone_pressure_relief` was built and REMOVED: measured in BOTH orders — before the purge it returned 0 MB immediately and 0 MB three seconds later (correct: the memory was still referenced), and after the purge, on a close that demonstrably gave back 97 MB, it still returned 0 MB. 67. **A Swift value carried as a text attribute must be `Hashable`, not merely `Equatable`.** `NSMutableAttributedString` hashes attribute values when deciding whether two adjacent runs can coalesce, so an `Equatable`-only Swift struct makes the runtime print "Obj-C `-hash` invoked on a Swift value of type … that is Equatable but not Hashable; this can lead to severe performance problems" — which this app did on every office document, for `OfficeGraphicInfo` and `FillMarginTabInfo` (and therefore `TabStop`/`TabAlignment`/`TabLeader`). So the honest claim for the store is "works in folders you have granted", NOT "does not work". **That claim was still FALSE for `--pdf` in 1.2, because a grant this app holds does not reach the process that writes the PDF.** `NSPrintInfo.AttributeKey.jobSavingURL` is honoured by the PRINT SUBSYSTEM, not by us, so the security-scoped access `restoreGrants()` opens never applies to it: measured on the shipped 1.2 build, printing to `~/Documents/_fdtest1.pdf` — **directly inside an already-granted folder** — failed with `PMSessionBeginCGDocumentNoDialog() returned -61`, as did a deeper path under the same grant, while the identical print into the container (`…/Data/tmp/`) produced a correct 9-page, 76,149-byte PDF. The fix is one indirection, in `HeadlessPDF.writePDF`: print to `NSTemporaryDirectory()` (inside the container when sandboxed, ordinary temp otherwise — ONE path, not a branch only one build exercises), then `FileManager.moveItem` it to the destination, which the APP does and the grant therefore covers. **The grant hint moved with it** — it annotates only the move's failure, never the print's, because a print failure can no longer be about the user's folders. Ungranted destination, measured after the fix: exit 1 in **2.0 s** naming the real refusal, against a hang that had to be `pkill`ed. **AppKit answers a failed print with a modal alert, and a headless process never dismisses it** (`No NSAlertAction found for modalResponse: 0`, then nothing — no event loop, `.prohibited` activation), which is why the staging directory's writability is checked BEFORE `op.run()`: the remaining print-failure paths are the print stack's own, not ours to trigger. `swift test` is structurally blind to all of this (it runs unsandboxed, so `FolderAccess.isNeeded` is false) — what it DOES pin is that an unwritable destination still yields a real PDF and fails only at `couldNotPlace`, which the pre-fix shape cannot reach; mutation-checked, and the mutation **hangs instead of going red**. `Scripts/smoke-headless-pdf.sh` is the half a test cannot cover: run it against `SANDBOX=1 ./Scripts/make-app.sh release` before shipping. Two things this cost: the grant panel's own menu item is named ONCE (`FolderAccess.grantMenuTitle`) so the headless hint cannot name a menu item that no longer exists, and **verifying any of this through System Events is a trap while two identically-named apps are running** — `first process whose unix id is N` returned the OTHER process (the installed release, unsandboxed), so three separate menu readings disagreed and all were wrong; the app dumping its own `NSApp.mainMenu` to a log settled it in one run.

71. **"Where am I" is ONE toggle whose unit belongs to the document, drawn where it cannot touch the document, and reachable by typing the number back.** `MarginNumberStore.unit(paged:drawingPages:)` decides it once — pages for a paged document that is DRAWING its pages, lines for everything else, including a paged document whose outline is off (the owner's *"페이지로 나눠보기 옵션이 없을 때에는 라인 번호로 통일"*) — and the menu title, the painters and every test read that one answer instead of re-deriving it. Line numbers are `MDAttr.blockId + 1`, one per block, aligned to the glyphs' CAP TOP (a line fragment includes its leading, so aligning to `rect.minY` floats the number above the words it labels, visibly on a heading), and a line inside a table gets none — a cell is a grid position, and numbering the 10,021 table lines of a real report drowns the 4,524 that are its text. **Both painters are confined to what is already laid out**, because the way a decoration changes a document is not by writing to the storage but by ASKING a question that makes layout from inside a draw pass (`glyphRange(forBoundingRect:)`, `ensureLayout`, `usedRect`), and `MarginNumberTests` asserts every line sits identically with the numbers on and off.

    **(a) Page numbers are on the DESK, and they SHRINK before they disappear.** A number inside the sheet competes with the document's own header/footer and reads as content the file does not have, so `PageNumberDeskView` is a sibling laid over the scroll view — no text storage, no layout manager, structurally unable to move the document. But the desk is only what is left of the window after the paper, and at the reading zoom the paper routinely fills it, so a fixed 72pt number simply was not drawn ("좌우 여백이 아주 크지 않으면 안 보임"). `placement(number:deskWidth:)` walks a fixed ladder — 44 with a generous margin from the paper, then 44/32/24 against the gutter — and only when none fit does it fall back to just INSIDE the paper's own left margin, fainter. The 44pt ceiling is the owner's, set by looking at it: 72 and 56 read as too big. Stepped rather than scaled by a ratio: a numeral's width is not proportional to its point size, so a ratio has to be re-measured anyway, and a ladder keeps the size consistent from page to page.

    **(b) Typing a number IS the command.** Digits go to `DocumentWindowController.jumpBuffer` (four of them — a 490-page report exists in this project's own test set, so three would make its last pages unreachable), Return jumps, Escape or 1.8s of silence forgets, and `JumpIndicatorView` echoes it over the scroll view. Measured on `2025_행정업무운영편람_최종.hwp` (rhwp's own render is the reference, and OUR pinned 0.7.19 CLI produces it: `rhwp export-pdf` → **394 pages**): section 0 declares body `396.9×507.4pt` with a top margin of `138.9`, while sections 2–10 — where 2,551 of the document's 2,618 paragraphs live — declare `395.7…396.9 × 555.6pt` with a top margin of `110.6`. rhwp's own render tree for a body page names exactly that (`Body {x 113.4, y 147.4, w 529.1, h 740.8}` px at 96dpi = `85.05 / 110.6 / 396.8 / 555.6` pt), so the body section's numbers ARE the renderer's numbers, and the cover's are not. 74. **HWP states a cell's borders through an id, and that id is the ONLY thing that draws a rule — a table's own fill is its background.** Every HWP cell carries a `borderFillId` into `DocInfo`'s border-fill table; the exporter emitted the id but never the table, so the id resolved to nothing and every HWP table was ruled with the reader's own theme grid. Measured on the same 편람: **821 border-fill definitions, 423 of them with all four edges `type 0` (no line)** — the layout boxes a Korean document uses to place things had their grid drawn back on by us. The fill table now ships as a document-level array (`borderFills`, indexed `borderFillId - 1`; HWP's reference is 1-based and `0` means "unnamed"), the same shape and for the same reason as `charShapes`, and each edge arrives as a type plus width in POINTS (HWP stores a 16-step mm enum; converting at the source keeps the host from carrying that table). A resolved edge is always a DECLARATION — `none` becomes `.suppressed`, never silence — because silence falls back through invariant 47's cascade to the very rule the document erased.

    **A table's own border-fill is its BACKGROUND, and that had to be measured rather than reasoned.** The first version of this work stamped the table's fill onto the perimeter cells as a box, on the strength of one document where the cells were all-off and a box was visibly there. Rendering the same page from rhwp's own SVG settled it the other way: on the page carrying that box there is **not one stroke element** — the box is drawn as NINE image tiles (the table's fill is a PICTURE fill), and on the 기안/협조/결재 table, whose table fill declares four solid edges, rhwp draws only the CELLS' dotted rules and no solid box at all. rhwp's renderer passes the table's fill to `render_cell_background` and to nothing else (`layout/table_cell_content.rs:529`). So `HwpReader` maps the table's id to `TableFormat.defaultShading` and never to a border; a picture fill has no shading colour and is honestly absent (that box does not render until image fills are supported). The stamping code and its two tests are gone — what stands in their place is `testTableOwnFillIsShadingNeverABorder`.

    **What HWP still loses, measured on the same file: the LINE STYLE.** Its fills use `dot` 59 times and `double` 13 times against 1,025 `solid`, and `BorderSide` carries only width and colour — so a dotted rule is drawn solid. This is not an HWP gap: `DocxReader` reads `w:val` only to tell `none`/`nil` from a rule (`DocxReader.swift:2791`) and `OdtReader` splits `fo:border`'s style token and drops it (`OdtReader.swift:1781`), so all three formats render every declared rule solid. 75. **A Korean document's drawings arrive as PATHS, and only the ones placed AS CHARACTERS may be drawn inline.** rhwp's exporter used to answer every drawing object with `{"label":"shape","w":0,"h":0}` — no geometry, not even a size — so a page whose diagram is four labels joined by six arrows rendered as four labels in empty space (78 shapes in `2025_행정업무운영편람_최종.hwp`, 322 paths between them). One thing to draw instead of nine, and no second opinion about what an `arc_type` means.
    **Drawn at READ time, into a PDF, so the vocabulary learns nothing.** `HwpShapeRenderer` renders the paths into PDF bytes and `HwpReader` hands them to the media map under a `hwpshape:` id — from there a drawing IS an embedded picture to everything downstream (reservation, reconcile, sizing, `--extract`), so no new `OfficeBlock` case, no builder branch, no serializer arm. PDF rather than a bitmap because the reader zooms; an arrowhead rasterised at 16pt is a smear at 32. Arrowheads are this reader's geometry, not the document's — HWP states only WHICH head a line has — and are scaled to the rule's own width so a hairline connector does not carry a barb the size of a glyph.
    **Three things the export got wrong the first time, all measured on the same file.** (i) A shape's points are stored in the object's ORIGINAL space and its `ShapeComponentAttr` carries six render coefficients that place them — the renderer applies that matrix (`layout/shape_layout.rs`'s `transform_pt`) and the export did not, so a real pair of arrows came out as `M 0,0 L 100,100`: 1pt specks, the matrix having carried all of their extent. (iii) A LINE record still carries a fill colour — white, in these documents — so filling every path painted white bars across the text and a table's own column label vanished under one; only a path that CLOSES is filled.

    **The gate is `treat_as_char`, and it is not a detail.** HWP anchors most objects by coordinates, and this reader has no floating layer (invariant 31 — built, measured, deliberately not shipped). Measured: several of that manual's shapes are the size of the whole page (555×752pt), and inlining all of them took the document from 423 pages to **452**. An anchored drawing is therefore skipped — the same nothing the reader showed before it could draw at all — while an as-character one is drawn where it belongs. A TEXT BOX's words are never at risk either way: rhwp emits them as SIBLING blocks, so they arrive as ordinary paragraphs whatever happens to the frame. **A floating layer for the paragraph-anchored ones was BUILT and REMOVED**: 17 of that manual's 33 anchored objects are `para`-relative, which this layout CAN locate, so each was painted over the text from a zero-width carrier — and the offsets alone turned out not to be the placement. `vert_align`/`horz_align` decide what an offset is measured FROM, and without them a 431pt decorative rule landed on the table's own `< 기 안 >` column label and erased it. The arrows stay undrawn until that geometry is done properly; these numbers are here so the next attempt starts from them rather than from scratch.

76. **A fill can be a PICTURE, and in Korean documents it usually is.** Measured on the same manual: of 821 border-fill definitions, **352 are picture fills** — used by 610 cells and 55 tables — against 53 solid colours and no gradients at all. The rounded annotation frames and tinted panels a Korean document is built out of are images, not colours, so a reader that knows only `bg` renders them as blank paper (which is exactly what this one did while claiming to honour the document's shading). A gradient degrades to its first stop, because a panel washed in one of its own colours is closer to the document than blank paper.

Mutation-checked: dropping the filter reddens the test by name.

78. **A Korean document's page number is not in a header — it is on the 바탕쪽, and drawing that means drawing objects on the SHEET rather than laying a flow into a band.** Invariant 77 ended with the honest state that this manual's 434 pages carried no number at all, because the only running head its file declares belongs to a five-paragraph landscape insert. rhwp's own render puts the number on every page from the master page, and so does this reader now. What the mechanism is, measured on `2025_행정업무운영편람_최종.hwp`: **13 master pages, of which the body section's `both` template holds four objects** — the running title (a text box at (55.16, 58.12) pt, 338.46 × 16.62), the full-page artwork (a picture at (0, 0), 555.58 × 760.80), the tab down the outer edge (a drawing at (500.62, 218.55), 64.83 × 113.68) and the number box (a text box at (446, 679.86), 37 × 22, whose span carries the same `pageNumberField` a running header's does). Measured after: **all 434 pages carry their own number**, at x 455–463 and y 60.8 of 754 — bottom right, constant, matching rhwp's own render.
    Three things this cost, each of which looked like a rendering bug and was not. **(a) Stored order is not draw order.** The artwork is stored FIRST and the title SECOND, so drawing them as stored painted a full-page picture over the title on every page. rhwp sorts paper-relative nodes by `(plane, z_order, stable_index)` where plane is the text-wrap band; the export now carries `plane`/`z` and the reader sorts by the same key rather than inventing one. **(b) A shape's border comes from its LINE TYPE, not its width.** HWP states the two separately and type 0 is "선 없음": the title box and the number box each declare type 0 with a width of 33, and an exporter asking only `width > 0` boxed both on all 434 pages while rhwp draws neither. The same rule's other half is the one that would have been missed by simply inverting the test — a declared line with width 0 still draws, at Hancom's own 0.12 mm minimum, and a dashed one is never thinner than a pixel. **(c) A degenerate box is not a size to invent.** One master text box (the cover section's rotated tab label) states a width of ZERO; it is dropped rather than given a width this reader chose, which is invariant 57's rule restated. The body section's own four objects all state real boxes, so nothing is lost by it: the file's ONE zero-width box belongs to another section's template and carries no spans at all. The vertical tab LABEL rhwp draws down the outer edge is the one piece of this page still missing, and it is not that box — the body section's tab object is a drawing with two paths and no text, so wherever those glyphs come from is not yet exported.
    **A master page belongs to its SECTION, and a reader that flattens every section into one column must still pick per PAGE.** Keeping only the body section's template — the rule invariant 77 needed for a running head — was reported on sight: that section's chapter title printed on the cover, on the table of contents and on 400 pages of other chapters. The flat export says nothing about where a section begins, so it now carries `sectionStarts` (the block index each section starts at); `OfficeTextBuilder` marks those blocks with `MDAttr.sectionIndex`, and a page's section is the LAST marker at or before the character the typesetter put at that page's top. Measured on the 편람 (14 sections, 13 templates between them): the title stops being constant and follows the section — 4 cover pages with none, 16 pages of `2025 행정업무운영 편람`, 164 of `제2장. 공문서 관리 등 행정업무의 처리`, and so on. Two of those sections declare no template at all and one declares a pair with no objects, so their pages draw nothing rather than borrowing a neighbour's — the appendix's own page numbers come from a FOOTER instead, which is still filtered to the body section (invariant 77) and is the next thing this needs.
    **The running head is the same rule one level down, and its own placement had to be fixed to survive it.** Once a page knows its section, the entries no longer need filtering to one section (invariant 77's answer while nothing could place a page): every section's are kept and chosen per page. Turning that on exposed two placement faults that had been invisible while only one section's entries existed, both measured on the same manual's appendix. (1) With NO declared footer distance the footer divided the GAP layout opened — and a page whose last line ends early opens a gap that begins in the middle of the sheet, so the page number printed at y≈451 of 754, across the body. (2) The header's mirror fallback put page 372's number at the BOTTOM of page 371's paper. Both now anchor to the SHEET EDGE whenever it is known (a missing distance means "as low as the paper allows" / "just below the paper's top"), which is the same paper-grid discipline the master page itself uses. After: each appendix page carries exactly one number at y≈18.6, alternating bottom on odd and top on even pages — which is what the document declares and what rhwp's own render does. The band's own height is now the TALLEST entry rather than the first, since any section's may be the one painted.
    Scope, deliberately: master pages ride the page-outline master switch (`PageViewOptions.underOutlineRule`) like every other piece of page furniture — with the outline off there is no sheet for them to be on — and they are NOT gated on drawing to screen, because a printout missing the page number is missing the document. Mutation-checked, both ways: removing the sort reddens two tests by name and removing the degenerate-box guard reddens one.

79. **Word states a page per SECTION too, and the body's TRAILING `w:sectPr` is the LAST section's.** Invariant 73 measured what taking the wrong section's page costs in HWP — a 394-page manual rendered as 458 — and fixed it there by choosing the section with the most paragraphs. The docx reader had the mirror image of the same bug and nobody had looked: `body.children.last(where: { $0.name == "w:sectPr" })` fed the page geometry, the line grid AND the running-head references, so a report whose final section is a one-page landscape appendix or a colophon typeset the ENTIRE document on that page. `DocxReader.typesetSectionProperties` now applies HWP's rule to Word: a section ends at the paragraph whose `w:pPr/w:sectPr` closes it (the body's own trailing one closes the last), the section holding the most paragraphs wins, and a TIE goes to the EARLIER one — `max(by:)` returns the last maximum, which is the same trap invariant 73 names for `max_by_key`. A table counts as content, so a section made of one long table does not read as empty. A single-section document — the overwhelming majority — has exactly one candidate and is byte-identical to before.

    **ODF states it a third way, and the same rule reaches it.** There is no section element at all: a page style changes when a paragraph applies a style carrying `style:master-page-name`, and every following paragraph stays on that master page until another switch. So the count is per MASTER PAGE — the first declared one is the default, an EMPTY `style:master-page-name` is a page break that keeps the current style (not a switch), and the switch is resolved through `style:parent-style-name` because a writer puts it on the named style while the paragraph names the automatic one (`P1`). The chosen master page then supplies BOTH the paper and the running header, so those two can never come from different page styles. Counting only the paragraphs that NAME a style is the trap: an ordinary paragraph declares none, so that count sees only the switch points and one appendix paragraph outvotes a whole body.

80. **An office picture's pixels must live on the CELL, not on `attachment.image` — otherwise the box the reader clicks stops being the box it drew.** Invariant 31 records that setting `NSTextAttachment.image` makes AppKit drop a custom `attachmentCell`; what nobody had traced is what that costs AFTER the reserved size is already decided. `reconcileMedia`'s office path set `att.image` the moment bytes arrived, so from then on the attachment was laid out AppKit's own way — from the picture's NATURAL size — while everything else in this reader still believed the document's declared box. Measured on `2025_행정업무운영편람_최종.hwp`: **36 of its 124 pictures declare a box whose aspect differs from their own pixels by more than 5%**, the worst by 2.69× (a 593×363 picture in a 348×79 box). Reported as a picture drawn in one place and selectable in another — *"이미지의 윗 부분은 클릭해도 이미지가 뜨지 않고, 아랫부분 영역은 클릭하면 이미지가 선택되어 새 창으로 떠버린다"*. `SizedAttachmentCell.pixels` now holds them and the cell draws from there, so the reserved box governs layout, drawing and hit-testing alike, loaded or not — the same reason `undrawableLabel` is a label on the cell rather than an image on the attachment. The markdown path still uses `att.image` deliberately: it re-derives its fitted size from the loaded pixels, so the two cannot disagree there. Every mirror surface moved with it — the "already loaded" gate, the purge test and the print-completeness count all ask the cell now. A test pins BOTH halves: pixels on the cell keep the reserved height, and pixels on the attachment provably discard the cell.

    **What the move handed us, and what it cost for two weeks: the app now makes the draw call.** `NSImage.draw(in:from:operation:fraction:)` — the four-argument one — does NOT consult a flipped context, and the text view is flipped, so EVERY picture in EVERY office document rendered upside down from the moment the pixels moved onto the cell. It went unnoticed because a photograph mirrored vertically still reads as a photograph; it was a whole-page COVER, whose title then read bottom-up, that made it obvious. The fix is the `respectFlipped: true` overload `MasterPagePainter` was already passing for the identical reason. The test draws a red-over-blue picture into a flipped canvas and asserts which colour is on top — with the flag removed it reports blue on top, so it cannot pass by accident.

81. **An object the document pins to the PAPER can be drawn on its sheet; one pinned to a PICTURE's worth of page cannot be taken out of the flow.** Invariant 75 stopped at "only an as-character drawing is drawn", because placing an anchored one needs more than its offsets. rhwp's own rule is two lines (`renderer/layout/shape_layout.rs`'s `calc_shape_bottom_y`): the reference gives an origin and an extent — `paper` the whole sheet, `page` the body area inside the margins, `para` the paragraph — and the ALIGN says where in it the offset starts (`top` adds, `center` centres then adds, `bottom` measures up from the far edge). The export carried the reference and the offsets but never the align, which is why the earlier float layer had to guess and guessed wrong. With the align exported, a paper- or page-relative object is placed exactly and drawn on the sheet its anchoring block falls on — the block is marked (`MDAttr.anchoredObjects`), and layout's own line rect answers which page that is, so nothing is cached that a reflow could invalidate.

    **Ink pinned to a sheet is CLIPPED to that sheet.** An object may be bigger than its own paper — a chapter divider's numeral measures 736pt on a 754pt sheet and sits low on it — and the screen draws every page into ONE continuous view, so with no clip that numeral ran off the paper, across the desk gap and onto the next page, where it sat beside that page's own running header. Printing never showed it: a printed page clips to its sheet by construction, which is exactly why the `--pdf` export looked correct while the window did not. `MasterPagePainter.draw` now clips to the sheet rect before painting anything, master furniture and anchored objects alike.

    **A PARAGRAPH-relative object is placed too, and the split is where the work goes.** Its reference is the anchoring paragraph, so half the placement cannot be settled at read time — but only half. Horizontally `para`/`column` measure against the text COLUMN, which this reader lays out at one fixed width, so the reader finishes x/width/height itself and hands on the vertical rule alone (`ParagraphAnchor`: an align and an offset). The draw pass completes it from the marker's OWN line rect (`lineFragmentRect`, minus the sheet's top), which is why a reflow moves the object with its paragraph instead of stranding it — nothing about the vertical position is ever stored. This is NOT the rejected float layer returning: that one had no align and so measured every offset from the top, which is how a 431pt rule ended up over a table's column label. Measured on `2025_행정업무운영편람_최종.hwp`: **28 anchored drawings placed — 13 by the sheet rule, 15 more once the paragraph reference was honoured** (the seals and the flow-chart arrows), with the page count unchanged.
    **A PICTURE anchored to the paper is drawn on its sheet TOO — but only because the document's own page breaks are read.** Floating them was built, measured and rejected once: the manual's cover is two pages of anchored artwork and nothing else, so with the pictures out of the flow those pages had nothing left to make them pages and the document went **451 → 436**, losing the cover. The missing fact was not about pictures at all — it was that a page existed only where text reached. Invariant 82 fixed that, and with the author's breaks honoured the artwork has a sheet to be drawn on: the cover is page 1, and the foreword's 688pt frame no longer eats two pages of body and pushes the text that belongs INSIDE it onto the next one. Keeping such a picture in the flow was itself the corruption.

82. **A document's own page breaks are DATA, and dropping them silently misplaces every page after the first one.** rhwp's paragraph model carries the break that starts a paragraph (`ColumnBreakType`: 쪽 나누기 / 구역 나누기 / 단 나누기) and its own renderer honours it — our structured export simply never mentioned it, so a host that receives only the flow gets a document with no page breaks at all. Measured on `2025_행정업무운영편람_최종.hwp`: **185 breaks**, the first three of them in the front matter, which is why the cover, its blank verso and the foreword ran together and every later page sat wherever the accumulated slide left it. The export now carries `breakBefore`, the reader collects the blocks (`OfficeReadResult.pageBreakBlocks`), the builder marks them (`MDAttr.startsPage`) and the band delegate starts such a line on a fresh page — the SAME line-shifting mechanism invariant 58 uses for a running band, checked BEFORE the "does this line fit" rule, because the author's instruction is not a consequence of how the lines fell. `section` counts as a page break (a Korean document starts a page at one, and this reader flattens sections into one column); `column`/`multiColumn` deliberately do NOT — they move to the next COLUMN, which a single-column reader cannot honour, and treating them as pages would invent breaks the document never asked for. Page count went 451 → 520 against rhwp's own 394; the residual is line consumption, not pagination, and the front matter now matches page for page.

83. **AN EXPORT IS A CONTRACT, AND A CONTRACT HAS TO BE AUDITED — the parser knew ten more things than it said.** Invariant 82 was found by chasing one symptom (a foreword printed on the wrong page); auditing the whole export against rhwp's own model afterwards found nine more of the same class, every one of them data the model already holds and rhwp's own renderer honours. What a host cannot receive it must invent, and each invention was visible: a heading styled "keep with next" typeset alone at the foot of a page; a table's column labels absent from its second page (this reader hardcoded `headerRows: 0` and said so in a comment); a list numbered 1,2,3 where the author wrote 가,나,다; a signature block's tab columns collapsed to a default width; a cover with the running header it explicitly hid. Now carried and consumed: paragraph `keepWithNext`/`keepLines`/`widowOrphan` and the STYLE's own `pageBreakBefore` (a different signal from the author's inserted break), paragraph tab stops, a list's format string + start number + glyph system + bullet character, a table's leading repeat-header count, and per section the furniture it hides, the page number it restarts at, its 원고지 grid and whether it is set vertically. Measured on `2025_행정업무운영편람_최종.hwp`: **275 paragraphs whose tab stops were being dropped, 18 tables whose repeating header rows were being dropped**; across the test corpus a document turned up whose section restarts page numbering, which nothing could have known before.

    **A marker read at the wrong MOMENT is a marker that does not exist.** The breaks were collected inside `configurePageBand`, which the render deliberately calls BEFORE `display(_:)` installs the new text so the delegate carries this render's numbers before a line is laid out — which means the storage in hand there is still the OUTGOING document's, and on a first open there is none. The screen therefore ignored every page break while `--pdf` honoured them all, because printing re-applies the band against text already in place. Every check that went through the print path passed; the app was wrong the whole time. They are set in `display(_:)` now, immediately after the storage is installed and before any layout is asked for, and a test drives the REAL render and asserts the delegate ends up holding locations that point into the installed text at characters the builder actually marked.

    **What is carried but deliberately NOT honoured, and why that is still worth carrying.** Vertical (세로쓰기) sections and multi-column geometry are recorded in the vocabulary and ignored by layout: one column is invariant 57's own decision and vertical typesetting is a layout engine this app does not have. Recording them is what lets a caller tell "the document never said" apart from "we ignored it", which is exactly the distinction whose absence made all ten of these gaps invisible for so long.

84. **THE SCREEN AND THE PAPER ARE ONE ANSWER — check them against each other, not each against itself.** Two defects shipped in one night from the same crack, in opposite directions. First the window ignored every page break the author placed while `--pdf` honoured them all: the break locations were read in `configurePageBand`, which the render calls BEFORE `display(_:)` installs the text, so the screen was looking for markers in the OUTGOING document while printing — which re-applies the band with the text already in place — found them all. Then the fix for that inverted it: clearing the locations on the path printing takes left the PRINTOUT ignoring them, and the reference manual went **520 pages to 436** while the window stayed right. Each time, every check that went through ONE path passed, which is why neither was caught by a green suite or by reading a PDF. `ScreenPrintParityTests` now asserts the two paths agree — the same breaks after either is re-applied, the same page count, and drawn sheets that are unions of printed ones and nothing else — and both defects are re-derivable from it: each mutation fails four of its five cases.

    **A page the AUTHOR ended is a page the reader DRAWS.** The screen joins sheets across a boundary layout never opened, so a page break is never drawn through a table (invariant 61/64/72). A document page break breaks that assumption: it leaves the rest of its page empty, and an empty page has no line of its own to cross the next boundary, which reads as "layout never broke here" — two sheets were welded into one double-height page carrying two running heads and two page numbers. `recordBand` now marks every boundary a shift JUMPED OVER as opened, because those pages exist by the document's own instruction rather than by a line reaching them.

    **And when there are no pages at all, an anchored object still has to be SEEN.** With the page outline off there are no sheets to draw on, so floating a picture out of the flow made the cover, the frames and the master furniture vanish entirely — the trade that puts a picture where the document pinned it is only honest if it is still visible. In continuous mode each one is drawn against its anchoring LINE instead of against a sheet: its own paper x, its block's own y.


85. **A DRAWING'S TEXT BOX SPEAKS ITS OWN DRAWING'S COORDINATES, AND A GROUP CHILD'S `common` IS EMPTY.** A Korean document builds its cover and its foreword out of a picture frame with a box of text sitting inside it, and a reader that flows those words down the body column lays a 300pt block of type across a 396pt column — beside the frame rather than inside it. The geometry was exported once before and deliberately not honoured, because the first mapping treated the offsets a group nesting accumulates as paper coordinates and the 편람 went **520 pages to 436** with 1,510 paragraphs indented into almost no width. The reason was narrower than "the coordinates need the group-origin walk": for a group CHILD the `common` those offsets come from is empty, and what was being exported was not a coordinate at all — measured on the 편람's foreword box, `boxX=2` and `boxW × boxH = 0 × 0`. A child's position lives in its render matrix (`render_tx/ty` with `render_sx/sy`), which ALREADY composes every nested group's move, scale and flip, so the rule is add the OUTERMOST object's origin once and never accumulate again — `renderer/layout/shape_layout.rs`'s own group-origin walk, and the reason a negative scale needs the min/max of both transformed corners rather than `tx`. A rotated or sheared child is exported with no box at all: an axis-aligned rectangle would be a coordinate we invented. The exporter deliberately does NOT resolve where the outermost object itself sits — that is `anchoredFrame`'s rule, already written on the Swift side, and stating it twice is two copies that drift. Measured after: the foreword's text moved from the body column (x 74~466) into its own 309.1pt box (x 107.5~415.5) with the page count **unchanged at 520**.

    **Only the horizontal half, and the narrowing is CLAMPED.** Honouring the vertical position would take the paragraph out of the flow entirely — the floating-object layout invariant 31 measured and did not ship — and would also take the words out of `--extract` (invariant 40). Left in the flow the text still reads and still extracts; it is only lower on the page than the document draws it. And a box that does not leave at least a quarter of the column is refused rather than obeyed, because that is exactly the shape of the 436-page failure: a coordinate misread reaches this code as a very narrow box, and flowing at full width is wrong but legible where a 20pt column is neither.

    **rhwp is the baseline for text INSIDE a frame, not for where a paper-anchored frame goes.** rhwp draws the same foreword at x 151~452 — exactly (555.59 − 476.4) / 2 = 39.6pt further right, i.e. it CENTRES an object that the document pins to the paper's left edge (`hp:pos horzRelTo="PAPER" horzAlign="LEFT" horzOffset="0"`, with `hp:outMargin` zero on every edge). The rest of the geometry agrees exactly: both renders put the text 24pt right of the frame's OWN centre, and this reader's frame ink is symmetric within its 476.4pt frame. So the two differ by one number — the frame's paper x — and this reader follows the declaration. It is recorded rather than matched, because that export draws no pictures at all (invariant 84's own note) and cannot arbitrate where a picture belongs.

86. **`textWrap` DECIDES WHETHER AN ANCHORED OBJECT HOLDS SPACE — floating both kinds deletes pages.** Invariant 81 took a paper-anchored picture out of the flow so the cover would stop pushing the manual apart, and invariant 82 made that safe by giving the author's own page breaks somewhere to land.     **The wrap is the OUTERMOST object's answer, not the child's — and so is everything else about placement.** See invariant 87: this was found as a wrap-only defect and fixed as one, twice, before the shape of it was clear.

    **What this reader still does NOT do is wrap text AROUND the object.** A wrapping object is kept in the flow as a full-width block, which reserves more height than HWP's own side-by-side wrap — the exclusion-path layer that would fix that is invariant 31's, built and measured and deliberately not shipped. So the manual settles at 526 pages rather than 520: the six extra pages are objects that genuinely hold space, held crudely. Reserving too much is visible and correct in kind; reserving none deletes pages, which is neither.

87. **PLACEMENT IS READ ONCE, FROM THE OBJECT THE DOCUMENT PLACED — reading a child's attributes answers plausibly and wrongly.** HWP hangs a `CommonObjAttr` on every node of an object tree, and exactly one of them is a placement: the outermost object, the one the document positioned. A group's children carry that same struct filled with DEFAULTS — 왼쪽/위 for alignment, 어울림 for wrap, zero offsets, zero size — and their real geometry lives in their render matrices instead (invariant 85). So reading a child does not fail loudly. It returns "top-left, in the flow", which looks like an answer.

    The same defect therefore arrived three times, in three fields, and was fixed three times as three unrelated bugs: the WRAP (a full-page cover went back into the text, 520 pages → 529); the ALIGNMENT (the 편람's foreword frame was drawn at the paper's left edge when the document centres it — 476.4pt of frame on 555.59pt paper, so the page was **39.6pt** out, `(555.59 − 476.4) / 2`); and the reference edges and offsets, which ride on the same attribute and were wrong with it. Each fix was a field-by-field override beside the emit site, which is why the next field was wrong again.

    It is now ONE decision: `Placement::of(common)` is built from the outermost object and handed to everything that object emits — pictures at any nesting depth, the object's own flattened paths. Depth never changes the answer, so nothing accumulates and nothing is re-read. Every block that carries an anchor takes the value rather than an object to read it off, so forgetting is not expressible. `width_criterion` deliberately stays with the picture: what a picture's own width is measured against is a fact about the picture, not about where the document put the object.

    **Verified against the engine, not against a PDF.** rhwp's own CLI export draws no pictures for this file (invariant 85), so it could not arbitrate where a frame belongs and this reader's left-edge placement looked defensible for a day. rhwp's WEB studio draws them, and it centres the frame — which sent us back to the source, where the group's own `hp:pos` says `vertAlign="CENTER" horzAlign="CENTER"` and the LEFT/TOP values that had been read belong to a different object entirely (the 555.6 × 752.9pt full-page decoration). After the fix the frame's ink is symmetric on the paper (x 69.0~486.0 of 555.59) and its text lands at x 147.0~455.0 against rhwp's 151~452, the remainder being the text box's own inset. Page count unchanged at 526.

88. **A RULE IS DRAWN AT THE WIDTH THE DOCUMENT DECLARED, INSIDE THE BAND LAYOUT CHARGED FOR — the two numbers are not the same number.** `NSTextTableBlock` draws a rule at the width it is given, and the width it is given has to be a whole point or the geometry stops adding up (invariant 39's `laidOutBorderWidth`). So every sub-point rule was handed up ROUNDED and painted at a full point. Measured on a real contract: it declares six widths — 0.283 / 0.340 / 1.134 / 1.417 / 1.700 / 1.984pt, which is HWP's 0.1 / 0.12 / 0.4 / 0.5 / 0.6 / 0.7 mm — and they came out as **two** (1pt and 2pt), so a 0.1mm hairline was painted as heavy as the box around the table. The document's own hierarchy of weights was gone, and a grid whose fine rules and heavy rules look alike is exactly what reads as ragged. The reserved band still rounds up — nothing moves — and the RULE is drawn at its declared width, centred in that band. Measured after, on the same page: rules at 0.38 / 1.62 / 1.75pt where there had been 1.0 / 1.12 / 2.0.

A rule with a declared width is therefore filled through a bezier path, which is antialiased, so a fine rule reads as fine at any scale. Whole-point rules keep the snapped fill they have always had — crisp is right when the width is exact, and that is every markdown table and every rule this reader invents itself.

    **A declared rule is never drawn away to nothing.** Below about a quarter point a line stops being a line on any display and reads as a MISSING rule rather than a fine one, so the drawn width has that floor. And the pixel test that was supposed to prove all this could not: at one device pixel per point, 0.3pt and 0.9pt paint the same rows and differ only in how dark they are, so counting rows reported them identical with the defect still in place. The geometry is asserted directly instead — `rule(in:edge:)` — and four separate mutations (never record the width / draw the whole band / drop the floor / stop centring) each fail it.

89. **A PICTURE PINNED TO ITS PARAGRAPH HAD NOWHERE TO GO — `anchoredFrame` answers only for paper and page.** Invariant 81 gave DRAWINGS a paragraph anchor ("a seal over a signature line, an arrow onto the table beside it") and the picture branch never got one, because the two branches were written a week apart and only one of them needed it at the time. `anchoredFrame` returns nil for a 문단 기준 object, so a picture fell through to the flow and was drawn inline at its paragraph's own left edge with BOTH declared offsets discarded. Measured on a real one — the seal declares 어울림 없음 at column + 285.9pt across and 155.3pt down, and was drawn at the body's own margin, **264pt to the left** of where the document puts it. The picture branch now tries `paragraphAnchoredPlacement` after `anchoredFrame`, the same order and the same guards the drawing branch uses, and the seal lands at x 342.6 (margin 56.69 + the declared 285.9) with its vertical half left for the draw pass.

    **What remains is line consumption, not anchoring.** That contract's signature block is inside a TABLE, and the seal's 155.3pt is measured from a paragraph above it, so the offset crosses several table rows before it lands. Our rows are not HWP's rows to the point, and the seal settles about two lines low — the same residual as the 편람's 526 pages against rhwp's 394, and it will move when that does.

90. **THE 526-vs-394 PAGE GAP IS NOT LINE HEIGHT — measured, and three plausible causes were eliminated.** The residual after invariant 82 was recorded as "line consumption", and the obvious reading of that is that our lines are taller than HWP's. They are not. rhwp's own CLI can export per-page SVG (`rhwp export-svg`), which carries every line's baseline as a coordinate, so this is directly measurable against `--pdf`. Measured on the SAME paragraphs of `2025 행정업무운영 편람` (found in both renders by content, not by page number — the page numbers diverge, which is what made an earlier comparison of "page 61 to page 61" produce a 45% difference that does not exist):

    | | rhwp | ours |
    |---|---|---|
    | 11pt body (≈110%) | 12.15pt | 12.1–12.9pt |
    | 12pt body at 160% | 19.2pt | 19.5pt |

    Both agree within ~1.5%. What was eliminated, each by measurement: **line pitch** (above); **the `.atLeast` floor** — switching every percentage to `.exact` moved 526 → 525, so the floor sitting under a tight percentage costs one page, not a hundred; and **an empty paragraph's basis** — see below, 526 → 527. What was quantified: **table splitting** accounts for 11 pages (526 → 515 with `pageSplitTables` on), and the drift accumulates UNIFORMLY (+21 by our page 100, +74 by 300, +119 by 500), so it is not a handful of structural insertions.

    **The first positive lead, and it came from the owner's own guess — now implemented, and worth 2 pages rather than the 11 it looked like.** A page break is a no-op when its line is ALREADY at a page top — `shift > 0.5` guards exactly that, which is what makes a second layout pass idempotent. But 94 of the 편람's 185 break markers sit on an EMPTY paragraph: that paragraph takes the break, lands at the top of the new page, and occupies one line there.     **Finding the marker read was losing breaks, which is why the estimate was wrong.** `enumerateAttribute` reports the longest range over which one attribute is constant, and two adjacent paragraphs that both break carry the same `true` — so they arrive as ONE run and the old read kept only the first location. Measured on the 편람: **176 runs against the document's 185 paragraph markers**, so **9 breaks were silently dropped**, including ones with real text above them (a heading that breaks straight after a paragraph that breaks simply stopped starting a page). Reading each run's paragraphs restores all 185; with the 7 suppressions the reader now honours 178, and the page count goes **516 → 518**. It is correct rather than cheaper — the same trade as invariant 91.

    **What actually holds the blank pages, measured after the above.** Logging every line fragment's FINAL page on the 편람: **49 of 514 pages carry no glyph-bearing line and no anchored object at all**, and they are not filled with empty paragraphs either — those 49 pages hold **172 empty lines between them, about 3.5 each**. That is the shape to attack next, and it needs what this rule deliberately does not use — a page's emptiness AFTER layout. The sanctioned way is the one `settlePagedTables`/`orphanRunStarts` already use: measure from a completed layout, hand back a character-keyed record, re-lay.

    Two facts still to be reconciled by whoever picks this up: we draw **9,627 text lines against rhwp's 4,983** while our prose lines carry MORE characters each (median 30 against 21), so the surplus is SHORT lines rather than wrapped prose; and our pages hold more prose than rhwp's (17.9 lines/page against 14.3) while still needing more of them. Do not re-derive the eliminated causes.

91. **A PARAGRAPH'S PERCENTAGE SPACING IS OF ITS OWN SIZE — including when it has no characters.** Invariant 83's basis rule (the percentage is of the text's OWN size, not the document default, because only 19.5% of real paragraphs are within 5% of that default) had a hole in it: a paragraph with no RUNS has no size to take, so it fell through to the document default — and on the 편람 that default does not exist, leaving a hardcoded 11pt guess as the basis for **793 of 2,789 paragraphs (28%)**, every one of them an empty spacer line. Every HWP paragraph carries a char shape whether or not it carries text, so the export now sends `baseSizePt` and the reader prefers runs → paragraph base → document default, in that order. This does NOT reduce the page count — measured 526 → 527, because those paragraphs' real size is LARGER than the guess was. It is correct rather than cheaper: the number now comes from the document instead of from this reader.

92. **A TABLE IS BROKEN AT A PAGE BOUNDARY BY DEFAULT, because that is what the document does.** The choice existed as a menu toggle and defaulted to "keep it whole", for a reason that was real and turned out to be narrower than it looked: breaking is only ever done where no vertically merged cell crosses the boundary, and a Korean report form is merged almost everywhere. But that rule is a guard INSIDE the breaking — a merged form is still carried whole because the boundary refuses it — so defaulting to whole was protecting tables that were never at risk while moving the ordinary ones HWP breaks. Measured on `2025 행정업무운영 편람` against rhwp's own render: keeping tables whole left **166pt of blank paper** at the foot of one measured page, where HWP starts the table there and continues it overleaf, and across the file it is **11 pages** of the gap (527 whole against 516 broken). A page the document fills is not this reader's to leave half empty. Unchanged: a table taller than its own page is always broken whatever the menu says, and the memberwise `PageViewOptions(outline:)` shorthand still means the pre-breaking shape, so the call sites that describe that state keep describing it.

93. **THE THEME HAD NO PER-SCRIPT SLOTS, so AppKit fixed the string per CHARACTER and cut a run at nearly every word.** An office document names its own face PER SCRIPT — HWP carries seven slots, docx four, ODF three, and 53.6% of real HWPs genuinely declare different fonts across them (invariant 53). Markdown and plain text have no document to declare anything: the theme put the system UI font on everything, that font has no Hangul, and AppKit's own fixing then left the Hangul on `AppleSDGothicNeo` while every space, digit and newline BETWEEN the words stayed behind on the system font. Dumped verbatim from a built string: `{376,2} "구분" .AppleSDGothicNeoI-SemiBold` then `{378,1} "⏎" .AppleSystemUIFontDemi`, alternating for the whole document. Measured on a generated 370k-character Korean markdown document of 300 tables: **246,900 font runs, one every 1.5 characters**, against **8,215** on a Korean HWP of comparable size through the office path — 4.55 runs per table cell against the office path's 1.80.

    `FontSubstitutionResolver.applySubstitutions(to:)` gives those two paths the same slots, decided the way invariant 52 decides an office document's: **once per (declared font, SCRIPT)** — never per character, never per run — on the most common character that font actually draws in that script, and only where the declared font does not already draw it. Runs are then split by `ScriptRunSplitter`, whose absorbing rule is what does the real work: a character with no script of its own JOINS the run in progress instead of starting one. Spaces alone were **42% of all font runs** on a mixed Korean/English document.

    **Per (font, script) rather than per font, because one sample cannot serve two scripts.** The first version asked once per FONT and it fixed nothing on real documents: Korean spreads across many distinct syllables while English repeats `e` and `o`, so the most common character in a mixed Korean document is LATIN, the system font draws it, the gate never fires. Measured: 23,754 runs before and after, unchanged. Splitting the census by script is what makes the question answerable at all.

    **`nil` family means "the document said nothing"; "no substitute" is the opposite and must not be spelled the same way.** `ScriptRunSplitter` deliberately does not break on a `nil` family (its own doc records three reviews arriving at that). Returning `nil` for a script the theme font DRAWS therefore folded the Latin into the Hangul piece and moved English onto the Korean face — caught by `ThemeScriptSlotTests`, not by reasoning. The covered case now returns the declared font's OWN family, so the run breaks and the Latin keeps the face the theme chose.

    **Worth, release build, same machine**, on the pure-Korean document: font runs **246,900 → 2,700 (−98.9%)**, total runs −92.5%, runs per cell **4.55 → 1.00** (invariant 51's value), first paint **1,284 → 661 ms**, full layout **6,356 ms and never completing → 5.3 ms completing**, memory after full layout **689 → 108 MB (−84%)**, drawing a screenful **10.3 → 3.4 ms (−67%)**. On the mixed document, **23,754 → 11,268 (−53%)**. That beats the ceiling measured for deleting `NSTextTable` altogether (−78% memory, and drawing got WORSE), so the table engine was never the defect these numbers pointed at.

    **A Latin-only document is byte-identical** — `moby-dick.md`, 6,397 font runs and 6,540 total, before and after — because the gate asks whether the declared font draws THIS text and the theme font draws `e`.

    **A SUBSTITUTE CARRIES A POINT SIZE, and this path hands the resolved `NSFont` straight to the storage — so grouping the answers by FACE NAME silently retypesets the document.** Shipped in 1.4.0 and reported on a real Korean report: `#`, `##` and the table headers came out at ONE size. They are all `.systemFont(weight: .semibold)` — the theme's ladder varies only the SIZE — so they share a face name, and two things keyed on that name alone folded them together: `byFamily`, which the apply pass looks the substitute up in, and `FontSubstitutionCache.substituteFont`'s memo, which is keyed on the declared face and the sample character with no size in it. Whichever size resolved first won, and Dictionary iteration order decides which that is — so the same file rendered its headings at 30pt on one launch and at 16pt on the next. The office path cannot express this defect: it stores a DESCRIPTOR and `OfficeTextBuilder` rebuilds it at the span's own size (`:533`). The fix sizes the substitute to the font it replaces and groups by face AND size; the memo is deliberately left size-free, because every office probe asks at `probeSize` and adding size there would only buy CoreText calls.

    **Each half needs its own fixture, and the obvious one hides the memo half.** Three headings worded differently sample three different characters, so the memo never collides and a test built that way passes with the memo defect still in place — verified by mutation. The case that bites is two SIZES of one face over the SAME words, which is what a real report's repeated heading vocabulary produces. Gated by `SubstitutedRunSizeTests` (both halves) and `ProgressiveKoreanRenderTests`, which also closes a second gap: the substitution is decided PER CHUNK from a cache that lives only as long as the call, and `ProgressiveRenderTests`' attribute-parity check runs on a Latin-only fixture that never reaches the pass at all.


94. **A KOREAN DOCUMENT SAYS WHERE ITS LINES MAY BREAK, and two thirds of them say something this reader was not asking.** HWP's `ParaShape` carries five bits about how a line is fitted; the export never sent any of them, so every HWP paragraph was laid out with whatever AppKit does by default. Measured across **1,589 real HWP/HWPX files, 454,134 paragraphs** (`HwpLineBreakProbeTests`): Hangul broken between CHARACTERS in **287,367 paragraphs (63%)**, between WORDS in **164,928 (36%)**, and **1,489 of the 1,589 documents** use the character setting somewhere. How many characters fit on a line is how many lines a document has, which is how many pages it has — so this is not a typographic nicety.

    **The nominal schema is backwards and the code is right.** Bit 7 is named `KEEP_WORD`, and it means break between CHARACTERS; 0 means break between words. rhwp measured Hancom three separate ways before believing it (`composer/line_breaking.rs`, #2185 — a kbu ladder file, an `80168 r10` control, and a preserved `LINE_SEG` comparison), and its own line breaker uses this reading. Anyone re-deriving this from the field name will get it exactly inverted.

    **AppKit's default is the CHARACTER setting**, so the load-bearing branch is the other one: `.word` inserts `NSParagraphStyle.lineBreakStrategy.hangulWordPriority` and `.character` removes it, leaving any other strategy the caller chose alone. `OfficeLineBreakingTests` pins that platform default explicitly, so a future macOS flipping it fails a test instead of silently swapping which branch does the work. Effect on the 편람, which declares the character setting in 1,859 of its 1,996 paragraphs: **518 → 519 pages** — the 137 word-break paragraphs, and nothing else. The value is in the other 1,488 documents, not this one.

    **Three of the five bits are decoded and deliberately NOT honoured, and the measurement is why.** Latin broken other than between words: 394 paragraphs (0.09%) in 49 files. Auto-spacing at a Hangul/Latin or Hangul/digit seam: 3,366 (0.7%) in 82 files — and honouring it means an attribute run at every script seam, which is exactly the cost invariant 93 spent a session removing. Line height taken from the font's own metrics: **59 paragraphs (0.013%) in 9 files**. They are carried in `ParagraphFormat` (`autoSpaceEastAsianLatin`, `autoSpaceEastAsianNumber`, `lineHeightFromFontMetrics`) so the next reader can see they were measured and dropped rather than missed. `.hyphen` behaves as `.word` on purpose: a hyphen is already a break opportunity in standard line breaking.

95. **ALMOST EVERY KOREAN DOCUMENT NAMES A FONT THIS MACHINE DOES NOT HAVE, and its own nominated substitute is missing too.** A declared font decides every glyph's width, and a width is a line count is a page count — so "is the document's font here" is a pagination question, not a cosmetic one. Measured over the same 1,589 real files (`HwpDeclaredFontProbeTests`): of **1,552,061 char-shape font references, 1,543,849 (99.5%)** name a family `NSFont(name:)` cannot resolve, and **all 1,589 documents** name at least one. The 265 distinct missing names are the ordinary Korean publishing set — 명조, HY신명조, 맑은 고딕, 굴림체, 함초롬바탕(1,323 documents), 휴먼명조, 바탕, 돋움.

    **HWP's own substitution fields do not help, and that is the measurement, not a guess.** The format lets a document nominate a replacement (HWP5 `alt_name`, HWPX `substFont`) and lets it embed the bytes. Of **66,909 font-table entries, 65,120 (97.3%) are missing, 9,084 of those nominate a substitute, and 0 of those substitutes resolve either** — the nomination is another Hancom face. Fonts are embedded in **2 entries across 2 of the 1,589 documents**, and **11,304 entries are HFT**, Hancom's own format, which is installed on no machine that does not have Hancom Office. So `Font.alt_name`/`subst_font`/`is_embedded`/`resolved_bin_data_id` are exported and decoded (`HwpFontFace`) and deliberately NOT honoured: honouring the nomination would change nothing 9,084 times out of 9,084, and registering an embedded font process-wide would serve two documents.

    **What is left is this reader's OWN fallback, and it is one face.** With the name unresolvable, `FontSubstitutionResolver.declaredFont` drops to the theme's probe font and lets CoreText substitute per script, so a 명조 document — a serif — is measured and drawn in the theme's sans face, as is every other document. A metric-aware map from the 265 named families to the Korean faces macOS ships (AppleMyungjo for the 명조/바탕/신명조 family, AppleSDGothicNeo for 고딕/돋움/굴림) is the open lever here, and it is a change to this reader rather than a field to import. Not attempted yet; the corpus above is the instrument that would judge it.

96. **A THIRD OF KOREAN TABLES FORBID BEING CUT AT A PAGE BOUNDARY, and until now nothing asked them.** Invariant 92 made breaking a table the reader's default — measured, and right for the document it was measured on — but it was a policy chosen for every table because the export carried no per-table answer. HWP has one: `Table.page_break` is three-way (나누지 않음 / 셀 단위 / 행 경계), and `Table.repeat_header` is a SEPARATE switch from having heading rows at all. Measured over 1,589 real files, 18,616 tables (`HwpTablePolicyProbeTests`): **5,878 (32%) forbid cutting**, 12,570 allow it at a row boundary, 168 anywhere, none silent — and **558 of the 1,589 documents** hold at least one table that forbids it, 243 of those tables being 20 rows or longer.

    The reader now carries that answer as `TableFormat.pageBreakPolicy` and stamps `MDAttr.tableKeepsWhole` over a table the document forbids cutting — an ATTRIBUTE rather than a lookup back into the block model, because the decision is taken from a COMPLETED layout (`settlePagedTables`), where the only handle on a table is where its characters are. `PagePagination.tablesToPush` then carries such a table whole instead of registering its rows as break points. **Two guards keep this from undoing invariant 92**: a table TALLER than a page is still broken, because moving it only empties the page it was on; and an absent attribute means "the document did not say", which is every markdown table and every silent office one, so those keep the reader's own default exactly. Effect on the 편람, whose 388 tables include 57 that forbid cutting: **519 → 520 pages**.

    **`repeat_header` is carried and not acted on, and the numbers are why.** It is true on 17,474 of the 18,616 tables — HWP's default state — while only 909 tables have heading rows at all, so the switch says almost nothing on its own; reprinting a heading overleaf also means inserting rows into the text storage during pagination, which is the re-render splice invariant 55 measured at 69,460 ms. `TableFormat.repeatHeaderRows` carries it for whoever revisits that.

Measured across 1,589 real files, **221,747 char shapes** (`HwpCharDecorProbeTests`), by share of shapes and by how many documents use it at all:

98. **A FOOTNOTE BAND IS A FIXPOINT, NOT A RESERVATION — and the safe half of its oscillation is the tall one.** A note is drawn at the foot of the page its marker is CITED on, so the height a page reserves is a function of which markers landed there, and which markers land there is a function of how much room the reservation left the body. The two genuinely fight: a band that grows pushes a marker near the foot onto the next page, which makes the band that grew shrink, which lets the marker back. That is a reachable 2-cycle with ONE note on ONE page, so "run until nothing moves" does not terminate — it spins to the round cap and then keeps whichever half of the oscillation it happened to stop on, which is the half where a note's page reserved nothing for it. `FootnoteBandSettle` therefore detects the REPEAT (the sequence is deterministic, so a state seen twice means the rest is a cycle) and resolves it by taking the **pointwise maximum** over the states visited. Reserving too much leaves a measurable gap inside the sheet; reserving too little draws a note on top of the body. Between loose and corrupt, only loose ships.

    **A PAGE THAT RESERVES A BAND IS A SHORTER PAGE, AND THE TABLE RULES WERE THE FOURTH COPY THAT DID NOT KNOW IT.** `PageBandLayoutDelegate.textBottom` exists because three layout rules each held their own `page × pitch + pageContentHeight` and a band made that number vary per page — "three chances to disagree about where a page ends, which shows up as a line drawn over a footnote rather than as a failed check". `PagePagination.tablesToPush`/`oversizedPieces` were a fourth, still asking the flat number, so a table that fitted the whole sheet but not the body a band left it was declared to fit, registered in neither record, and left where it stood. MEASURED on a 30-note fiscal report (`refs/rhwp/samples/2010-01-06.hwp`): every sheet carries a ~686pt table and a five-note band of 286pt on a body of 700pt, and sheet 3's table was drawn to **y=802 of an 841.9pt sheet**, interleaved line for line with the four note lines beneath it. The definition now lives ONCE, in `PagePagination.textBottom`/`bodyHeight`, and the delegate calls it; an EMPTY `noteBands` returns exactly the old number, which is what keeps every document that cites no footnote provably untouched.

    **The other half was an ORDERING one, and it is the half no unit test can see.** `settlePagedTablesFully` (the synchronous settle printing uses) ran the tables to a stop and THEN the notes, and never re-asked the tables. At the moment the table pass runs nothing has reserved a band yet, so every table is judged against the whole sheet — both rules individually correct, and only their order producing the defect. The asynchronous walk never had it: its `settlePagedTables() || settleFootnoteBands() || settleColumnPlacements()` chain re-asks the tables every round. The two now alternate until neither moves, which terminates because the note rule latches at its own STOP and a table is only ever moved once. Effect on that report, notes readable out of the printed page: **27 of 30 → 30 of 30**, and no sheet overruns. Across all 31 footnote-citing documents in the corpus: notes drawn **449 → 454**, pages whose content ran off the sheet **47 → 39**, and not one document got worse. `FootnoteBandRealFileProbeTests` (`FMD_FOOTNOTE_DRAW_PROBE`) is the instrument; reverting the alternation makes it report **164 body lines drawn into their own page's note band**.

    **Two things measured here and deliberately NOT acted on.** (1) **The clamp never fires.** `maxBandFraction` exists so a note taller than its page cannot reserve the page out of existence, and splitting such a note across sheets was the obvious next feature — over all **31 footnote-citing documents, including a 95-note file named `text_footnote_tail_overpagination`, `clamped == raw` every time, 0 of 31**. There is no material for that feature in this corpus. (2) **The reservation is NOT larger than what is drawn, and believing it was cost a wrong diagnosis.** Reading the printed page it looks over-reserved — 286pt of band against notes whose first lines span 170pt. Instrumenting both sides says otherwise: `PageBandGeometry.builtHeight` (the reserve, `NSLayoutManager.usedRect`) and `FootnotePainter`'s `boundingRect` measure the SAME note at the SAME width within two points, **46.0 against 48.0**, and the painter's is the larger of the two. 170pt was first-line to first-line; the band is four gaps plus the last note's own height plus the separator allowance, and it reconciles exactly. Do not "tighten" this.

    **What IS wrong is WHICH PAGE a note is drawn on, and it now has a number.** `FootnoteBandRealFileProbeTests` compares the assignment the painter uses against where the markers actually landed in the layout that shipped: over the 31-document footnote corpus, **266 of 420 notes are drawn on the page that cites them**. The cause is the last act of the ruling. A stop on a CYCLE resolves to the pointwise MAXIMUM over the states visited — a vector no round proposed, so no layout was ever built against it — and applying it moves the very markers the frozen assignment was taken from. `refreshFootnoteAssignment` takes the assignment once more from the caught-up layout and adopts it ONLY if the frozen bands already cover it: **242 → 266**, four documents going from partial to exact (9/9, 5/5, 22/22, 1/1) and none regressing.

    **Two ways of closing the rest were built, measured and undone.** Reopening the whole ruling when a table moves splits the table across two sheets and leaves the notes on the sheet its markers left. GROWING the bands to cover the refreshed assignment — monotone, so seemingly still the loose half — measured **261 of 420 and 42 body lines drawn into a band**, because a band grown after the tables have settled shortens pages no rule re-checks. Loose beats corrupt here too: the guard DECLINES rather than grows. What is left (a document whose tables move after the notes have latched) needs the tables to reach their final places before the notes rule at all, which is a different loop from the one this invariant describes.

    **The band does not change the page — only the body's floor.** A note makes no sheet taller (this is what Word and HWP both do), so `pitch` stays uniform, `PageGrid.textTop` and `page(containing:)` are the numbers they always were, and `PageBandLayoutDelegate`'s derive-the-page-from-the-rect rule stays idempotent under mid-document re-layout. What moves is `PageGrid.bodyBottom`, and nothing else. Folding the band into the pitch instead was rejected on exactly this: it would have made every existing consumer — printing, the page count, the margin numbers, the anchored-object pass — read a page boundary that the document never declared.

    **The clamp is what makes any of it bounded.** A note taller than the page it is cited on would reserve the whole page, leave the body nowhere to go, and push the same marker one page further every round forever. `maxBandFraction` = 0.75 keeps the body's height positive; it is a TERMINATION guard, not a typesetting judgement, and what actually happens to a note too tall for its room is S15's. An infinite band clamps like any other oversized one rather than falling to zero — zero is the unsafe half, and it is the value a broken measurement is likeliest to produce.

    **ONE BUDGET EACH, NOT ONE BUDGET BETWEEN THEM — and getting this wrong makes the rule above never fire.** The table settle, the note-band settle and the column placement ran in one loop as `settlePagedTables() || settleFootnoteBands() || settleColumnPlacements()`, sharing a single round budget. The tables spend the rounds, so on a document whose tables keep moving the note band's own rule never reaches a STOP at all — it only ever returns `.retry`. That is not a slow convergence; it is a different failure, because **the band is only frozen AT the stop**, and until then the assignment is re-derived on every pass. Measured on a 30-note document, three successive rounds assigned notes to pages `{0,1,3,5,6,7,8}`, `{0,1,2,4,5,6,7}` and `{0,1,3,4,5,6,7,8}` — so pages that had reserved a band cited nothing and pages citing notes had no band, and the painter drew **11 of 18 note instances**. Giving each settle its own loop took the same document to **17 of 18**, better than it had ever been. Tables first (a table that moves changes which page cites a note), notes second (a band only shortens the body it was measured against), columns last (placed from a flow neither of the others changes).

    **The assignment is part of the ruling, not a separate answer.** A band's height is a function of which notes a page cites, so when `FootnoteBandSettle` stops, the assignment it stopped ON is frozen with it (`settledFootnotePages`). Re-deriving it afterwards against a layout the band has since changed is what lets the two disagree at all.

    **One round budget, defined once.** The table settle terminates on its own and treats the cap as a backstop; the note band can genuinely cycle and is stopped BY it. `DocumentWindowController.maxPagedTableSettles` is therefore DEFINED as `FootnoteBandSettle.maxRounds` rather than written beside the loop — two numbers that must agree and live in two places disagree eventually, and this pair would disagree silently (the loop still finishes, just on a state one half of the settle never saw). A round costs roughly 38 ms on the reference document, so eight is about 300 ms of worst case.

99. **A FOOTNOTE IS IN THE WRONG PLACE; AN ENDNOTE IS ALREADY IN THE RIGHT ONE — and the corpus says so by a factor of five.** Both arrived the same way: the exporter appended each note's body to the flow after the section that cited it, so both read as stray body text. Fixing "notes" as one thing would have been wrong. Measured over the 637-sample corpus (`examples/scan_footnotes.rs`, counts only — no document text): **333 footnotes across 22 documents (3.5%)** and **1,832 endnotes across 33 documents (5.2%)**. An endnote BELONGS at the end of its section or document, which is exactly where the flat append already puts it — so moving both to fix one would have broken 1,832 correct placements to repair 333 wrong ones. Only footnotes are lifted into `OfficeReadResult.footnotes`; an endnote stays an ordinary trailing block and its marker is deliberately left untagged.

    **The corpus also decides the shape of the band.** **306 of 333 footnotes (92%) are a single paragraph**, tailing off to a handful of 18- and 25-paragraph notes — so a band is normally one or two lines and overflow (S15) is the exception, not the common case. Every one of the 1,622 shape declarations says `eachColumn` (the foot of the column, i.e. the page) and **`print_inline_after_text` is declared by NOTHING** — no document in the corpus wants its notes run on after the body text, which is the one declaration that would have made the whole reservation pointless. Separator line type does vary and is real: 1,392 solid, 202 none, 28 type 10.

    **Lifting a note out of the flow silently breaks `--extract`.** The headless path exists so a tool can read a document WITHOUT the reader, and it serialises `blocks` — so the same edit that put a note in the right place on screen deleted it from the extraction, with nothing to report the loss. `OfficeMarkdownSerializer.serialize` therefore takes the notes separately and re-emits them as markdown footnotes (`[^3]: …`). A mutation that drops that append is caught by `FootnotePlacementTests`.

    **THE GATE A NOTE ASKS IS "ARE THERE SHEETS", NOT "IS THERE A BAND" — and asking the second one is circular.** `PageBandLayoutDelegate.isActive` means "is there anything to reserve", which for a running head is known before layout and for a note is DERIVED from it: the note's own reservation is what makes the answer yes. Gating the note path on it therefore settles on "no" for exactly the documents the feature exists for — measured, **17 of the 22 footnote-citing documents in the 637-sample corpus declare neither a running head nor a foot (77%)**, and every one of them drew no note at all while the exporter had already lifted the notes out of the body flow. Not late, not misplaced: absent. Assignment (`footnotePages`), reservation (`settleFootnoteBands`) and the print-time settle therefore ask `paginates` (`pageContentHeight > 0`); `isActive` is widened to `band > 0 || !noteBands.isEmpty`, so a note's reservation activates the shifting rule that reserves it. A document with no notes and no head is untouched — `noteBands` is empty and every number is what it was.

    **Three separate things had to be true for a note to reach paper, and each failed silently on its own.**

    - **`HwpSpan` declares an explicit `CodingKeys`, and Swift's synthesised decoder skips any property that list omits — with no error and no warning.** `noteRef`/`noteRefKind` were absent from it, so every marker in every document decoded to `nil`, no page ever cited a note, and nothing anywhere reported a problem. The existing marker test could not see this: it built its `Span` by hand and proved only that the builder honours a tag it is handed. A test that starts at the JSON (`testAMarkerTagSurvivesTheDecoder`) is what actually guards the wire. This is invariant 45's failure shape in a second place — the field is in the model, the value is on the wire, and the reader never sees it.
    - **The painter rode inside the running head's `if let pageBandContent` block**, which is `nil` whenever `band == 0`. It now paints from its own `footnotePaintContext`, deliberately NOT by widening `pageBandContent`: `masterPageContent` reads that nil as "this document has no running head", so widening it would quietly change what a 바탕쪽 paints.
    - **A settle that changes a reservation must INVALIDATE the layout, not merely ask for another walk.** `settlePagedTables` always did; `settleFootnoteBands` did not, and `ensureLayout` will not redo work it considers valid — so the band was correct, the painter drew into it, and the body was still sitting on top of the notes. Measured on a real 5-note document, whose PDF interleaved note text with body text line by line. Printing needed the same fix from the other side: `settlePagedTablesFully` settled tables only, so ⌘P and `--pdf` reset the bands and printed a page that reserved nothing.

    **A marker is usually not in a paragraph.** On the first real document this was measured against, all five markers sat inside TABLE CELLS — so a mapping path that carried the tag for body paragraphs and dropped it for cells would look exactly like a document with no footnotes. `testAMarkerInsideACellIsTaggedToo` holds that.

100. **A COLUMN IS DECIDED FROM THE FLOW AND KEYED BY CHARACTER — because the typesetter carries a moved line's `y` and throws away its `x`.** This app has ONE `NSTextContainer` and an `NSTextView` cannot have more, so TextKit's own multi-container column flow is unavailable without replacing the view. What is available is the machine the page band already uses (invariant 58): `shouldSetLineFragmentRect`, moving a line before it is set. The page band pushes a line DOWN; a column break sends one back UP and across. The typesetter accepts that — measured, `ColumnFlowSpikeTests` — and it carries the `y` to the lines that follow.

    **It does not carry the `x`.** A line's horizontal position is re-derived from its paragraph every time, so the obvious rule — "see that this line has run past the foot of its column, move it across" — places the first line of column 2 correctly and returns every line after it to the left edge. Built and measured on `samples/basic/shortcut.hwp`: **32 lines moved, 1,200 stayed**, which draws as a narrow single column rather than as two, and is strictly worse than not having columns at all. The first version of the spike missed this by asserting only that SOME lines were in each column, which that broken rule also satisfies; the assertion that catches it is now in the spike by name.

    With `x` unable to hold the state, the column a line belongs to **cannot be read back out of the laid-out page at all**. So it is decided once, from the flow laid out as a single tall stack, and stored keyed by the line's own CHARACTER LOCATION — the one handle a transform cannot move. `ColumnGeometry.placements` is that map and `DocumentWindowController.settleColumnPlacements` measures it. Idempotence then holds by construction rather than by argument: a re-layout asks the map, and the map does not change.

    **One pass, not a fixpoint — and that is a property of where the width is applied.** The line BREAKS are decided when the text is BUILT, at the column's width (`OfficeTextBuilder.columnWidthPerBlock`), so moving a line into its column changes where it is drawn and never how it wraps. Building at the column width is also what makes a TABLE fit: a table carries its own width and would otherwise stay page-wide inside a narrow column, and **244 of the corpus's tables sit under a column declaration**. Contrast the note band, which changes the very layout it is measured from and therefore needs `FootnoteBandSettle` (invariant 98).

    **The corpus says this is worth more than footnotes were.** 637 samples (`examples/scan_columns.rs`, counts only): **64 documents (10.0%) declare more than one column** — three times as common as a footnote — across 149 declarations, 125 of two columns and 20 of three. Paragraphs under one: 22,204 of 558,452 (3.98%). **57 of the 149 (38%) do not want equal columns** and 56 (38%) draw a rule between them. `direction` is `leftToRight` in all 149 and `SectionDef.text_direction` horizontal in all 811 sections — no right-to-left or vertical machinery is owed to this material.

    **A declaration is a POSITION, not a section property.** HWP puts `ColumnDef` in the text, so a document goes to two columns and back, and one sample does it 22 times. The layout is therefore stamped over every BLOCK of a run rather than onto the run that declared it — that run is a zero-width anchor with no character for an attribute to live on, which is why the first attempt found no runs at all. A declaration of ONE column is carried as an END rather than dropped, or the previous one would stay in force to the end of the document.

    **Widths arrive in two units in the same field** — HWP 5 states shares summing to 32,768, HWPX states points — so `proportional` separates them and nothing may assume one. Shares resolve against their OWN total rather than the constant, so a document whose numbers are slightly off lands inside the page instead of overflowing by its own rounding error; absolute widths too wide for the page fall back to the equal split, because keeping the text on the sheet beats honouring a number that does not fit.

    **A RUN OFTEN DOES NOT BEGIN AT A PAGE TOP, and the assumption that it did was wrong twice over.** This was recorded here as a known limit on the belief that documents start a column run at a section break. `ColumnRunStartProbeTests` (`FMD_COLUMN_START_PROBE`) went and asked: over 800 real documents, 66 carry a column run, and of their **140 runs, 74 (52%) begin partway down a sheet**, covering 1,926 of the 114,068 lines laid out under a run. So this is the common case, not the corner.

    Placing such a run "from that page's top" was wrong in both directions. It drew the run's first column over the single-column text ABOVE it — that text is already there — and it handed the leftover height down as the height of every LATER sheet, so the columns stopped partway down each page and the run spilled onto sheets it did not need. A run therefore has TWO column heights: what is left of the sheet it starts on (`firstColumnHeight`) and the whole body of every sheet after (`columnHeight`), and its first sheet's columns begin where the RUN begins rather than where the page does. When a run does start at a page top the two heights are equal, `runOrigin` IS the page top, and every term reduces algebraically to what it was — which is what keeps the runs that already worked untouched, asserted directly rather than argued.

101. **A MARKDOWN FILE'S FIRST PAINT BUILT THE WHOLE DOCUMENT, and four fifths of what it built was text nobody could see yet.** Opening a 3.5 MB / 54,795-line Korean markdown file spent **4,596 ms** before the window appeared (`FirstPaintProbeTests`, three runs, load average 2.6–3.1 — quote the load or the number means nothing, see invariant 65). Reading and parsing that file is 2.8 ms of it. The rest is the WALK that turns the parsed tree into an attributed string, and a reader cannot see past the first screenful of it.

    The front of the document is now built and shown, and the rest is appended afterwards: **4,596 → 1,006 ms (−78%)**, median of 993.6 / 1,011.3 / 1,006.3. The work is MOVED, not saved — the same total build still happens, exactly as invariant 55 says of the giant table it defers, and for the same reason it is allowed to: at first paint the reading anchor is character 0, so none of the geometry that makes deferral dangerous exists yet.

    **The SOURCE may not be sliced — only the walk.** Markdown has document-global state: a reference link definition (`[x]: url`) or a footnote definition can sit on the LAST line and bind text on the first. Parsing a prefix on its own turns such a link silently into plain text, and silent is the worst failure a reader has. So the document is parsed WHOLE (15% of the cost, unavoidable) and only `Document`'s top-level children are handed out in slices — a block boundary cannot fall inside a link, a fence or a URL, which is also what makes `autolink` and the font-substitution pass safe to run per chunk instead of once over everything. `ProgressiveRenderTests` asserts exactly that case: a link defined on the last line is already a link in the first chunk.

    **Slicing the LAYOUT instead was already tried and rejected — twice (invariant 49).** Viewport-first layout was built, measured and reverted both times, because the freeze is the BUILD, not the layout. This is the same conclusion applied from the other side.

    **ONE builder for the whole document**, deliberately: its initialiser scans the source for line starts and math spans and was 705 of 6,029 first-paint samples, so re-creating it per chunk would pay that again every time — and block ids keep counting up across chunks, which is what invariant 19 asks for.

    Two things were paid for here and should not be re-earned. **`next + blocks` overflows** when a caller asks for "the whole remainder" as `Int.max`; the clamp must subtract from what is left. That trapped on the first real document, in the append turn — a turn no probe reaches, because a probe never spins the run loop, and the crash is therefore invisible to the very measurement that motivated the work. And **the storage cannot be compared against a fresh render attribute-by-attribute with `isEqual`**: a paragraph style carrying an `NSTextBlock` compares by object IDENTITY, and every render builds fresh table blocks, so even the same document rendered twice comes out "different". Compare descriptions with their pointers stripped, at the RENDERER level — `display` puts things in the storage that no render produces (margin numbers, the reading band), so the document layer can only be held to the contract `SpliceRenderTests` already uses: same text, same block source spans.

    **A headless print keeps it, and that was measured rather than assumed.** The design note said `--pdf` must build whole; the version that forced it off there was written and then deleted, because printing the same 3.5 MB file both ways in one process settles to **2,797,110 characters either way**, in 6.2 s whole against 5.7 s front-first (`ProgressivePrintParityProbeTests`, `FMD_PROGRESSIVE_PRINT_FILE`). What actually protects that path is the settle loop: `isProgressiveRenderPending` joins `deferredTables` in its quiet test, so it cannot return while a tail is still arriving — the same answer invariant 55 gave for the giant table it defers. While looking for a truncation that was not there, two things were learned that will otherwise be re-learned: the app BUNDLE and the bare CLI binary paginate the same file differently (the bundle registers its own fonts, 1,844 pages against 1,441), and **rendering the same file twice in one process does not produce the same document** — a 553-page HWP settles to 553 pages in 6.3 s on the first render and to 545 in 3.2 s on the second, reproducibly, with identical code on both sides (measured twice while trying to attribute the difference to this feature, which does not even reach the office path). Separately, printing a NON-PAGED markdown file headlessly moves run to run for the same reason: the unchanged build printed 1,844, 1,845 and 1,862 pages. Both are the bounded settle loop meeting lazily-sized media, so **a page count may only be compared between renders taken from the same ordinal position in a process** — and for markdown it cannot be compared at all (invariant 102 is what came of chasing that). The text is what holds still, so the text is what the probe asserts.

    **The tail arrives in TWENTY turns, and the first attempt at one turn was the mistake worth recording.** Handing the whole remainder over at once made the window appear at ~1,000 ms and then froze for **3,728 ms**, which spends exactly what painting early bought. The build cannot move off the main thread (invariant 55 measured that and rejected it), so it is divided — but the number that decides the shape is not the freeze, it is what the document costs to FINISH:

    | tail | worst turn | tail arrived | **fully laid out** |
    |---|---|---|---|
    | one turn | 3,753 ms | 3,828 ms | **48,626 ms** |
    | twenty turns | 220 ms | 8,564 ms | **8,857 ms** |

    Appending 2.8 M characters in one edit hands TextKit one enormous invalidation that it then pays off for **48 seconds**; appending in pieces lets it lay out as the pieces land. So the divided shape is better on every axis that matters and only looks worse on "tail arrived", which is a midpoint, not a finish — measure to SETTLED or the undivided version gets credit for work it has not done yet.

    Divided by COUNT, not by a time budget: a per-turn time budget was built and measured first and lost in both directions at once. Every piece carries a fixed cost (copy the delta, run the two range passes, append, let the view invalidate), so more pieces cost more overall — 8.3 s at 40 ms, 9.7 s at 80 ms, 11.1 s at 150 ms — while the worst turn stayed stubborn anyway, because one oversized block outlasts any budget. And when reporting this, count the PIECES the render handed out; a probe that reported its own poll count made a 21-piece tail read as 650 turns. Many chunks buy a smoother arrival but oblige the outline panel, find, the scroll bar and ⌘End to cope with a document that is still growing, and that verification costs more than the change did. The head is 120 top-level blocks, and documents under 300,000 UTF-16 units are built in one pass, because their first paint is already immediate and splitting them would spend an edit to save nothing.

102. **A HEADLESS PRINT OF A LONG DOCUMENT IS NOT PAGE-STABLE UNDER LOAD, and neither of the two obvious causes is it.** The same 3.5 MB markdown file, printed by the same binary in separate processes, gives **1,893 / 1,892 / 1,891 pages on a quiet machine and 1,875-1,893 on a loaded one** (six runs, artificial load 15-50). A paged HWP is stable — 550 / 550 / 550 — so this is the non-paged continuous-text path.

    **Two designs were built, measured and REVERTED**, both from the same wrong premise (that `waitForRenderToSettle` was giving up too early):

     1. Settle on the WORK being finished rather than the height standing still — a `isLayoutWalkInProgress` flag on the controller and an `isMediaSizingPending` on the document, both joining the quiet test. Six runs each, interleaved, under the same load: **old 1891/1876/1875/1891/1876/1893, new 1891/1875/1876/1892/1875/1891.** Identical distributions.
     2. Bound the wait on being STUCK instead of on total time (restart the deadline whenever anything moves). It never fired: with (1) in place the loop still exited on its three quiet polls every single run, so the deadline was not what ended those prints.

    What that leaves is the part worth keeping: **the loop believes the document is finished, and the document is genuinely a different height.** The two cheap explanations are ruled out — a bundled font racing registration (this app registers none) and a stand-in image area (office sizes are decided at build time, and the markdown file holds one image, which cannot move 18 pages).

    Two measurement traps were paid for on the way and should not be re-paid. **Rendering the same file twice in ONE process does not produce the same document** — 553 pages at 423,665 pt, then 545 at 417,537, then 507 at 388,428, reproducibly, on identical code — so a probe must compare renders taken from the same ordinal position, which is why `ProgressivePrintParityProbeTests` renders three times and compares the second against the third. And **the app BUNDLE and the bare CLI binary paginate the same file differently** (1,844 against 1,441): compare a bundle against a bundle.

103. **A CALL COUNT PROVES THE ENGINE WAS ASKED, NOT THAT ITS ANSWER WAS USED — and the gap between those two is invisible to every test that compares values.** Invariant-style finding from the 바탕쪽 port (S5C-3). The migration already knew that two implementations agreeing numerically makes "who answered" unobservable in the values, and answered it by observing the CALL — `RustOfficeDocumentHandle.answeredQueries`, a delta of exactly one per draw pass. That observation is one layer short. Making `MasterPagePainter.draw` ask the engine and then discard the reply (`offset < engineAnswers.count` → `offset < 0`, so every page falls to the host's own `applicablePage`) left the call count at one, left every value equal, and **passed all three parity tests**. A wiring that silently ignored the engine would have read as fully engine-backed.

    **What closes it: hand the seam an answer the host cannot produce, and require the output to follow it.** Two templates declared alike — same section, both `.defaultPages` — so `applicablePage` can only ever reach the FIRST; the reply then names the second, and the drawn page must show the second's object and NOT the first's. `MasterPageEngineParityTests.testTheSelectionAnswerDecidesWhichTemplateIsDrawn` does it by sampling ink on both sides of an offscreen sheet, and it is the only one of the four that catches the discard. Assert the precondition too (that the host really would answer the first), or the test proves nothing about which of them answered.

    **Two aiming traps were paid for here and should not be re-paid.** A mutation that adds a second call with an EMPTY batch changes nothing observable — the bridge returns early on no pages, so `answeredQueries` never moves; aim a duplicate call at the same NON-empty batch instead. And a mutation of `applicablePage`'s `guard !candidates.isEmpty` is unobservable by construction in both languages: with no candidates the `find` below returns nothing and `?? candidates.first` is nothing either, so the guard's presence cannot change an answer. It is kept for transliteration fidelity with the Swift it ports, but **it must not be counted as a covered branch** — the test that claims to cover it passes whatever is done to it.

104. **A PROCESS-GLOBAL PRECONDITION CANNOT BE GATED BY A ONE-PROCESS TEST SUITE — the first class that installs it makes its absence permanently unobservable, so the suite goes green over an app that never worked.** Found in S5D-2, measured rather than reasoned. The engine's two ports — the font world (`RustEngineFonts`) and the text measurer (`RustEngineMeasure`) — are one-shot process globals. `RustEngineMeasure.install()` had **zero callers in `Sources/`**; `RustEngineFonts.install()` had three, all inside `RustEngine`'s docx/odt read path, and `.hwp`/`.hwpx` branches to `HwpReader` before it (`DocumentTypes.swift:121`). `RustOfficeDocumentHandle.init` called neither. Every parity test passed because each test class installs both itself.

    **What the app actually did**, run in isolation against a real `.hwp`: the handle opened, and the first band query PANICKED inside the engine (`swiftshim/src/font_provider.rs:133`), which `guard_scalar` turned into an ordinary refusal — so the reader answered from its own arithmetic and the engine was never asked anything. HWP is also the ONLY format whose footnotes reach `OfficeReadResult.footnotes` (`HwpReader.swift:501`; neither docx reader lifts them), so the exact path the footnote work targeted was the one that was dead. The flag is opt-in (`Package.swift:14`) and no shipped build was affected — the migration was on course to ship it.

    **The fix is ownership, not another call site: whoever OPENS the handle installs what that handle's queries need** (`RustOfficeDocumentHandle.init`, both idempotent). Relying on some earlier call having installed them is call order, and call order is not a contract — it held for docx and silently did not for HWP.

    **The check that proves it can only run alone.** Once the handle installs on open, ANY test in the binary that opens one poisons the observation — which also retired `RustEngineBridgeTests`' `+setUp()` capture of "no measurer yet", now permanently unreachable in a shared process. `EngineInstallPreconditionProbeTests` (`FMD_INSTALL_PRECONDITION_PROBE`) is therefore a **probe, not a gate**: env-named, run with `--filter` alone, the same shape `crates/fastdoc-engine/tests/page_band_measure_port_absence.rs` already uses on the Rust side for the same reason (a separate test binary gets its own process for free; XCTest does not). Do not "promote" it into the suite — inside a full run it cannot fail, and a check that cannot fail is worse than no check because it reads as coverage.

    **`s5c1.md:86` had already named this failure mode** ("the measurer is not installed when the query runs") and the wiring shipped anyway. A plan recognising a hazard is not the same as the hazard being prevented; the prevention has to be a call in `Sources/` or a probe someone runs.
