# fast-md-reader — dev notes (read before continuing)

Native macOS **document viewer** (reader-first), shipped as **Fast Document Reader**. Markdown is where it
started; it also reads **Word `.docx`/`.docm`/`.dotx`/`.dotm`, OpenDocument `.odt`, and Korean HWP `.hwp`/`.hwpx`** (read-only) —
text, tables with merged cells and cell-level images/lists, images, links (including internal
bookmarks/cross-references), footnotes, headings resolved through all three ways Word and ODT can
declare one, clause/list numbering with overrides, equations rendered through the app's own formula
engine, charts and SmartArt diagrams (via Word's legacy-picture fallback, or an honest placeholder
when none exists), right-to-left text, review comments (shown in a right panel, hidden by default),
and presentation resolved from the document's OWN style cascade — paragraph spacing, indent,
line-height and alignment; run/theme colour, highlight, font, size, caps/small-caps and underline
style; tab stops and their alignment; paragraph shading and borders; table columns that fill the
width by the document's own grid proportions, plus cell shading, PER-EDGE borders (an edge the
document silenced is told apart from one it never mentioned, invariant 47), vertical alignment and
margins, and named table styles' banded rows and shaded headers — every absolute value sized to the
document's own default so the reader's zoom multiplies on top of it, not a hardcoded app rhythm.
Pictures are the deliberate exception: a graphic is scaled by the reading column over the DOCUMENT's
own page width and honours its paragraph's left/centre/right alignment, so ⌘+/⌘− resizes text alone
while a picture tracks the window (invariant 46). Floating/anchored image text-wrap was built,
measured, and deliberately not shipped (invariant 31). Plain text (.txt/.csv/.log…) opens verbatim.
`.rtf` was deliberately dropped (`35c9485`): AppKit's RTF reader loses tables, lists and embedded
images, so supporting it honestly meant writing a second parser the size of the Word one.
Korea's dominant **HWP** format (`.hwp` = HWP 5.x binary/OLE, `.hwpx` = OWPML XML) is parsed by
**rhwp** (Rust, MIT — github.com/edwardkim/rhwp, a fork we maintain adding a structured-export FFI
and an equation→LaTeX emitter), shipped as a prebuilt **static-library xcframework**
(`Vendor/RhwpNative.xcframework`, arm64) statically linked into the app; rhwp's JSON is mapped to the
SAME `OfficeBlock` vocabulary by `HwpReader.swift`, so the identical `OfficeTextBuilder` renders HWP —
tables, images, styles, hyperlinks, footnotes, equations, and headings taken from the paragraph's
STYLE NAME, which is how a Korean file declares one (invariant 33) — and `--extract` works for it too.
Writing is deliberate and narrow: right-click a block → Edit / Add Below / Move / Delete, held in
memory until ⌘S.
Two headless flags let a tool use the reader without a window: `--pdf` prints a document to a PDF file
through the SAME print path ⌘P uses (invariant 66), and `--extract` runs the SAME office reader without any
GUI and prints the document as Markdown to stdout — for feeding a `.docx`/`.odt` to an AI without it
spending tokens on the zip/XML (invariant 40).
The Finder's own space-bar preview is this engine too: `Contents/PlugIns/QuickLookPreview.appex`
carries a COPY of the app's executable and `main.swift` routes it to `NSExtensionMain`, so the
preview is the reader rather than a second, simpler rendering of the same file (invariant 68).
Pure Swift/AppKit + TextKit, SwiftPM executable. No web runtime for text. WebKit renders only two
things — mermaid diagrams and TeX/KaTeX formulas — and only on a cache miss; both cache to vector PDF.
Code highlighting is native (34 languages, single-pass scanner), no JS.

## Build / test / run

- **Build app**: `./Scripts/make-app.sh [debug|release]` → `FastDocReader.app` in repo root (ad-hoc signed).
- **Toolchain (MUST)**: standalone Command Line Tools has a mismatched SwiftPM ManifestAPI → `swift build` breaks. Always use Xcode's toolchain. `make-app.sh` auto-sets `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` if unset.
- **Tests**: `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test` (1345 tests, keep green; 36 skip by default). Every skip is a probe that needs a real document this repo does not ship, named by an environment variable: two markdown edit-latency measurements (`FMD_LATENCY_FILE`); the whole-reader cost probe (`FMD_PERF_FILE`, plus `FMD_PERF_WIDTH`/`FMD_PERF_HEIGHT`) which walks ONE real document through every stage a reader pays in order — parse, first paint, time-to-interactive, full layout, zoom, width change, jump to the end, read all the way down — and samples the process's own memory at four points, so a change that improves one stage while ruining another is visible in a single run (invariant 65's numbers came from it); office ones (`FMD_OFFICE_LATENCY_FILE` for the ⌘+ cost breakdown, `FMD_HWP_STYLE_PROBE` for a real HWP's paragraph-style frequencies, `FMD_TABLE_PROBE` for one table's geometry, `FMD_SPAN_PROBE` and `FMD_SUBST_PROBE` for the attribute-run counts invariants 51/52 are judged by, `FMD_DOCX_FONT_PROBE` for a docx's resolved-family histogram, `FMD_GIANT_TABLE_LATENCY` for the paired first-paint measurement invariant 55 is judged by); HWP real-sample checks (`FMD_HWP_SAMPLE` for parse/default body size/page width/equation, `FMD_HWP_IMAGE_SAMPLE` for pre-decoded images, `FMD_HWP_SPAN_DUMP`/`FMD_HWP_SPAN_DUMP_OUT` for the before/after dump that proved the rhwp rebuild changed nothing, `FMD_HWP_SLOT_SURVEY` for how often a corpus varies its seven font slots); the re-runnable corpus probes (`FMD_CORPUS_DIR`, and `FMD_RENDER_CORPUS=<colon-separated dirs>` which drives 1,279 real documents through the real render path as a crash gate); the paged-fidelity probes added while matching Word page by page (`FMD_PAGED_PROBE` for the row-pitch/line-box decomposition, `FMD_TABLE_MATCH` for a table's geometry against its source, `FMD_HWP_LINESPACING_SURVEY` for a corpus's line-spacing modes, `FMD_HWP_EXPECT_PT`/`FMD_HWP_EXPECT_WIDTH_PT` for a real HWP's declared page numbers, `FMD_HEADER_FOOTER_PROBE` for a real docx/odt/hwp's running header — the only check that a NON-docx header both reserves its band and builds to real glyphs, AND that ⌘P on that same file produces a PDF with the page count the reader reports, which no reader unit test can see, invariants 29/62); and the floating-image-wrap layout-cost spike (`FMD_FLOAT_PERF=1` — see invariant 31, that feature was measured and deliberately not shipped, and the spike stays as a test so the finding never has to be re-derived).
- **The suite is FLAKY UNDER LOAD, and it is not your change.** Verified by running the same commit twice: at a green commit under load ~50 the suite reported 0, 1 and 3 failures on successive runs. The offenders are always wall-clock or async-timeout tests untouched by whatever you are doing — `SpliceRenderTests.testLongDocumentEditStaysFast` (a 250 ms budget), `OfficeImageLoadingTests` placeholder cases (a 2 s `XCTestExpectation`), `WindowResizeGateTests`, `LargeDocumentTests`, `PerDocumentFontSizeTests`, and `PageViewOptionsTests.testTheReadingPositionSurvivesAToggleFromDeepInTheDocument` (seen once at load 12→25 reporting the reader at character 0; passed on the next four full runs and in isolation — it waits on an asynchronous layout walk, so a machine that starves that walk reads as a lost reading position). Before believing a failure, check `uptime` and re-run the named test in isolation; a quiet machine finishes the suite in ~14 s and a busy one in 40–55 s.
- **Run a dev build from the REPO** — `open ./FastDocReader.app`, and to open a DOCUMENT in it, `open -a "$(pwd)/FastDocReader.app" <file>`. **The `-a` is not optional.** `open ./FastDocReader.app <file>` reads as two independent arguments: it launches the dev bundle AND hands the document to whatever app is REGISTERED for that type — which, on a machine that also has the shipped build installed, is `/Applications/FastDocReader.app`. Both processes then appear in `pgrep` a second apart, the document opens in the RELEASE, and a change you are trying to eyeball is simply not in the window you are looking at. Two identically-named apps make that invisible; check `ps -o command` for which bundle owns the window before trusting a visual verification. Do NOT copy the dev build to `/Applications`: that folder holds properly signed builds only (owner's rule). A dev build there is ad-hoc signed, and macOS ties per-app state to the signature, so every rebuild reads as a different app — which is exactly why Open Recent kept emptying (see invariant 21). `/Applications` gets a build from `notarize.sh` or the App Store, nothing else.
- **Quit cleanly, never `pkill`**: `osascript -e 'tell application "FastDocReader" to quit'`. Force-kill loses recent-docs persistence and can leave state inconsistent.
- **⌘R (Reload)** reloads the *document* content only — it does NOT pick up a new app build. A code change needs rebuild + relaunch.

## Layout / files

- `App/AppDelegate.swift` — menu bar built **in code** (no MainMenu.nib). Any standard shortcut or menu must be added here — including the tab jumps: ⌘1…⌘8 and ⌘9-is-the-LAST-tab live in a "Go to Tab" submenu of the Window menu, because in a code-built menu a key equivalent exists only if a menu item carries it. ⌥⌘←/→ use AppKit's own `NSWindow.selectPreviousTab(_:)`/`selectNextTab(_:)` and need no code of ours; ⌃⇥/⌃⇧⇥ were already AppKit's.
- `App/MarkdownDocument.swift` — `NSDocument`; render pipeline, presize + prerender, lazy media reconcile.
- `App/DocumentWindowController.swift` — text view, scroll, tabs, find, source-edit panel, keyboard nav, reading-line highlight, the sidebar split (`NSSplitViewController`) and every reflow path. `updateTextInset` owns the three passes that re-solve the document to a changed reading column — `reanchorFillMarginTabs`, `resizeTableColumns`, `resizeOfficeGraphics` — while `settleReadingColumn` is its geometry-only half for callers about to replace the storage (invariant 48).
- `Navigation/ReaderTextView.swift` — the reading cursor: key handling, unit navigation, gutter-click block select, reading-line band. `Navigation/TextNavigator.swift` — pure line/sentence/paragraph boundary math (no view). `Navigation/AnchorResolver.swift` — resolves an internal link's target fragment (bookmark or heading slug) to a scroll position; pure decision logic, no view, so a dead cross-reference resolving to "do nothing" is unit-testable without a window.
- `App/ExternalEditor.swift` — "Edit in <App>" for read-only office documents: finds a candidate editor by bundle identifier (never by path — an app that moves would otherwise become a dead button), remembered per format. Split into a pure, fully-tested half and an `NSWorkspace`/`Bundle` glue half verified by launching the app.
- `Render/MarkdownRenderer.swift` — CommonMark/GFM → `NSAttributedString`; also detects mermaid, ```` ```math ```` and `$$…$$` and turns them into web-block placeholders.
- `Render/WebBlock.swift` — the ONE place that knows there are two WebKit engines (`.mermaid`, `.math`); every measure/presize/reconcile pass iterates `enumerateWebBlocks`. `Render/WebBlockRenderer.swift` — WebKit → cached vector PDF, shared by both.
- `Render/PlainTextRenderer.swift` — non-markdown text (.txt/.csv/.log…) rendered VERBATIM, monospaced, one block per non-blank source line. `App/DocumentTypes.swift` — the single list of openable extensions; Info.plist mirrors it, and `DocumentTypeDeclarationTests` now fails when the two disagree in either direction (invariant 69).
- `Navigation/BlockEdit.swift` — pure source arithmetic for add/delete/move (no views), feeding `applySourceEdit`, the one path that changes the text. `App/OutlinePanel.swift` — the table-of-contents sidebar (LEFT `NSSplitViewItem` sidebar), built from the heading attributes the renderer already leaves behind. A document with no headings hides the button and collapses the panel, decided from the SPLIT VIEW's actual state rather than the controller's own `isOutlineVisible` flag — that flag records only what the user toggled in THIS window, while AppKit can restore a sidebar it saved from another one, which is how an empty 180pt panel ended up beside a document with no outline at all.
- `App/CommentPanel.swift` — the review-comments sidebar (a RIGHT `NSSplitViewItem` inspector, hidden by default, ⌥⌘C), mirroring `OutlinePanel`; lists `MarkdownDocument.officeComments`. The body highlight + number badge for each comment are drawn behind the glyphs (draw-time, gated by `ReaderTextView.commentsVisible`), never an inline attachment (invariant 38).
- `Render/Office/PageBandGeometry.swift` / `Render/PageBandLayoutDelegate.swift` / `Render/Office/PageBandPainter.swift` — the running header/footer, in its three halves (invariant 58): how tall the band at a page boundary is (the document's own two margins, never less than what we draw), the `NSLayoutManagerDelegate` that reserves it by pushing each page's first line down, and the draw-time painter that puts the header/footer in it with this page's live number. Nothing here touches the document string. The delegate also owns the ONE other thing that moves at a page boundary — a table that would otherwise run into the margin is moved whole to the next page (`pushWholeTable`, invariant 61), decided by `DocumentWindowController.settlePagedTables` from a layout that already happened.
- `Render/Office/PagePagination.swift` — where each SHEET is, in the text view's own coordinates — the rectangles printing puts on paper AND the ones the page outline draws on screen (invariants 59/60). Pure and view-free: one subtraction over numbers layout already holds, because the reader's page grid IS the paper. It also decides WHICH TABLES have to move so none of them prints in a margin (`tablesToPush`, invariant 61) — the same page arithmetic, judged by numbers rather than by looking at a printout.
- `App/PageViewOptions.swift` — the View menu's three page toggles (outline / header / footer) and the global `UserDefaults` preference behind them (invariant 60). `MarkdownDocument.applyPageBand` is the single place that turns them into a band, called by both the render and `DocumentWindowController.reapplyPageBand`.
- `Render/RenderTheme.swift` — the BASE design system: type scale + rhythm tokens (line-height / spacing / indent ratios) + colour, inherited by three thin per-format branches `MarkdownStyle` / `OfficeStyle` / `PlainTextStyle`. The rhythm constants live here ONCE; renderers read tokens, never re-inline them (invariant 36) — including the two ABSOLUTE ones the rules use, `RenderTheme.tableBorderWidth` (an integer point, invariant 42) and `Palette.tableBorderFaint` (the perimeter stand-in of invariant 47, faint in the ALPHA, never in the width). `Render/Office/OfficeBlock.swift` — the format-neutral vocabulary all three readers map into: blocks, `Span`, `ParagraphFormat`, `TableFormat`, and `EdgeBorders`, whose `BorderDecl` gives an edge three states rather than two (invariant 47). `Render/Office/OfficeTextBuilder.swift` — the ONE format-neutral builder turning the office block vocabulary into typography, applying each block's resolved `ParagraphFormat`/`Span`/table geometry (invariant 37) and sizing every graphic through the single `graphicSize` a reflow re-uses (invariant 46). `Render/Office/HwpReader.swift` — the rhwp bridge: HWP/HWPX `Data` → rhwp's structured JSON (via the `CRhwpNative` FFI) → the SAME `OfficeReadResult` `DocxReader`/`OdtReader` return, pre-decoding every embedded image at read time into `OfficeReadResult.images` (the FFI parse handle can't survive to lazy reconcile). `Vendor/RhwpNative.xcframework` — the vendored prebuilt rhwp parser (Rust static library, arm64), statically linked and dead-stripped; rebuild it via `docs/BUILD-RHWP.md` — and note `Scripts/record-rhwp-source.sh` defaulted to the OTHER working checkout (`~/Documents/DEV/refs/rhwp`) while testing `[ -d "$RHWP/.git" ]`, which is a DIRECTORY in a plain clone and a FILE in a submodule: it therefore rejected `Vendor/rhwp-src`, fell through to the default, and recorded a build from the submodule as coming from a different commit. It now defaults to the submodule and tests `-e`. The Rust source is an unlinked fork checkout, and our own four commits are backed up IN THIS REPO as `vendor-patches/rhwp/` — **read that folder's README before touching the parser**: it records the base commit, the restore procedure, and why we are PINNED to 0.7.19 (upstream moved 7,345 commits / 45,014 source lines in ten days at ~110 merged PRs a day, so a needed fix is CHERRY-PICKED, never rebased onto `main`). `Vendor/RHWP-SOURCE.txt` names the commit the shipped `.a` was built from, coverage + known gaps in `docs/hwp-support-gaps.md`, full design in `docs/hwp-support-design.md`.
- `Render/TableBlockBuilder.swift` — turns a row/cell vocabulary (markdown GFM + office `Cell`s) into a REAL bordered `NSTextTable` (`GridTextTable`, an `NSTextTable` subclass carrying its column proportions), shared by both renderers, so cell text is real selectable/copyable/searchable document text (invariant 39); it also resolves each cell's four edges from the table's and its own declarations (invariant 47) and then resolves each BOUNDARY between two cells to a single drawer, with `collapsesBorders` off so the winner is ours rather than AppKit's (invariant 50). `build(width:)` takes the width to solve at — the real reading column for an office document, the `initialColumnWidth` placeholder only for markdown and for any build with no window yet — and `resizeTables(in:toWidth:)` re-solves every table's columns to absolute integer widths on each reflow, touching only cells that moved (invariant 48). `Render/SizedAttachmentCell.swift` — the attachment cell that OWNS its `reservedSize` so an `image==nil` medium keeps its space (invariant 1), used by images and formulas.
- `Render/Office/OfficeMarkdownSerializer.swift` — the `--extract` serializer: office block vocabulary → Markdown (pure `[OfficeBlock] -> String`, view-free), conservative mapping with a `<raw>` fallback for un-mappable tables (invariant 40). `App/HeadlessExtract.swift` — the `--extract` CLI itself (reads the file via the single `DocumentTypes.readOffice` dispatch → serializer → stdout); `App/main.swift` gates it BEFORE `NSApplication` so no GUI starts. `App/HeadlessPDF.swift` — the `--pdf` CLI, which CANNOT gate there because layout, fonts and printing are all AppKit: `main.swift` creates `NSApplication` with activation `.prohibited`, never installs `AppDelegate` (it would present the Open panel, invariant 43) and never enters the event loop, while `HeadlessPDF.waitForRenderToSettle` pumps the run loop by hand to drain the SAME asynchronous completion pipeline `render(into:)` schedules for the interactive reader (invariant 66).
- `QuickLook/QuickLookPreviewController.swift` — the Finder's space-bar preview (`QLPreviewingController`), built through the SAME door `--pdf` uses (`MarkdownDocument.read` → `makeWindowControllers()` → that controller's content view) so the preview cannot drift from the reader. It ships in `Contents/PlugIns/QuickLookPreview.appex`, assembled by `make-app.sh` from `Resources/QuickLookPreview-Info.plist` + `-.entitlements` (local/Developer ID) / `-mas.entitlements` (store), with a COPY of the app's own executable — see invariant 68 and `docs/02-planned/quick-look-extension-design.md` for the measured format-by-format outcome and the App Store's separate-App-ID requirement.
- `App/TextEncodingDetector.swift` — what a file's bytes actually are (BOM → strict UTF-8 → BOM-less UTF-16 → regional legacy → verified guess → Latin-1), and the bytes to write back in that same encoding.
- `Render/CodeHighlighter.swift` — single-pass native highlighter, 34 languages + aliases.
- `Cache/MermaidCache.swift` — content-addressed disk cache, keyed by (source + engine version) so the two engines never collide.
- `Resources/mermaid.min.js`, `Resources/katex.min.js`, `Resources/katex-inlined.min.css` (KaTeX fonts inlined as data: URIs — regenerate with `Scripts/build-katex-css.sh`). `Resources/Info.plist` — bundle config. `Scripts/make-app.sh` — build+bundle+ad-hoc sign.

## Hard-won invariants (DON'T regress)

1. **Scrollbar stability = decouple media SIZE from PIXELS.** An `NSTextAttachment` with `image==nil` (not-yet-loaded / purged) collapses to ~0 height → total height and the scrollbar swing on scroll. Fix in place: `SizedAttachmentCell` owns `reservedSize` independent of the image. Loading/purging pixels must **redraw only, never touch layout** (`redrawGlyphs`) — if size is unchanged, do NOT call `storage.edited`/`ensureLayout`. This cost **4 debugging rounds**; keep the size/pixel split intact.
2. **Uncached docs must behave like cached ones.** On first open, `prerenderAllDiagrams` renders every uncached web block — diagram OR formula — to the disk cache (bounded concurrency, `cap=min(3,…)`), then `presizeKnownMedia` reserves each exact area and lays out **once**. After that, sizes never change on scroll. Both engines ride this one pipeline via `WebBlock`; giving formulas their own path would mean re-earning this property (and getting it wrong = formulas resizing mid-scroll).
3. **`invalidateDisplay` alone does NOT draw a newly-set attachment image** — you need `storage.edited(.editedAttributes, …)`. (Learned the hard way when diagrams went invisible.)
4. **The web-block cache lives in `FileManager.default.temporaryDirectory/fast-md-reader/mermaid`** (the dir name is historical; it holds BOTH mermaid and KaTeX PDFs now, disambiguated by the engine's `cacheVersion` in the key), NOT `~/Library/Caches`. The app is sandboxed, so that resolves INSIDE the container — `~/Library/Containers/ai.ww-w.fast-md-reader/Data/tmp/fast-md-reader/mermaid`, **not** the `$TMPDIR` your shell sees. When testing "uncached cold start", clear the CONTAINER path; clearing the shell's `$TMPDIR` copy looks like it worked and proves nothing. Bump the engine's `cacheVersion` (in `WebBlock`) when its capture changes — a stale PDF outlives the bug that made it.
5. **Fresh-DB/fresh-open tests are fake-green for the cache/migration class** — they create the target state directly and skip the render path. Cold-start behavior must be tested by actually clearing the mermaid cache dir and relaunching.
6. **NSDocumentClass in Info.plist must be module-qualified**: `FastDocReader.MarkdownDocument` (a SwiftPM executable, so NSDocumentController can't find a bare class name).
7. **Open Recent**: AppKit's automatic population does NOT attach to a code-built menu → it's populated manually via a menu delegate in `AppDelegate` reading `recentDocumentURLs`. macOS prunes deleted files from the list (a deleted test file → correctly shows "No Recent Files").
   - **Read `recentDocumentURLs` ONLY from `menuNeedsUpdate`** (i.e. when the user opens the menu). Under the sandbox each read can consume a limited pool of security-scoped extensions; apps that poll it (timers, `validateMenuItem`) exhaust the pool and then fail to reopen recent files. Apple's published workaround — cache the list, refresh on activation — would make it *worse* here, since that fires on every ⌘Tab. On-demand-only is already the safe pattern; verified working sandboxed across repeated relaunches. If recent files ever stop opening, this is the first suspect.
8. **Sandboxed WKWebView needs `com.apple.security.network.client`** even though mermaid loads only a bundled local JS file and the app makes zero network requests — WebKit runs out-of-process and renders nothing without it. Don't "clean up" that entitlement.
9. **Sandboxed = a document's sibling images are unreadable, and macOS NEVER prompts.** Measured, not assumed: relative, absolute, and `file://` paths all fail sandboxed while remote URLs load; the same binary unsandboxed loads them all. The sandbox denies before TCC is consulted, so no prompt appears, and there is no "Documents folder" entitlement to request (iMovie's Documents/Desktop/Downloads toggles come from its *media* entitlements — not a route we have). Granting Full Disk Access does nothing: the sandbox still refuses. The only way through is `FolderAccess` — user picks the folder in an open panel, persisted as a security-scoped bookmark (what Marked 2 / iA Writer / MWeb do; Typora / Obsidian / IntelliJ skip the store instead). **Don't re-litigate this; four plausible theories (temp path, ad-hoc signature, TCC identity, launch method) were each disproved.**
10. **A blocked image's placeholder is itself an image**, so its click check MUST come before the zoom check in `ReaderTextView.mouseDown` — otherwise clicking "Click to allow…" just enlarges that label.
11. **Remote images are presized by fetching only their header** (`Range: bytes=0-65535` → ImageIO), mirroring `prerenderAllDiagrams`: measure everything, then lay out ONCE. Never "reserve a guess and correct it later" — that reflows under the reader, which invariant 1 exists to prevent.
12. **Math is read from the SOURCE, never the parsed text.** `MarkdownRenderer.scanMathSpans` finds `$$…$$` in the raw markdown before the parser touches it. Two reasons: (a) markdown claims `_`/`^` as emphasis, so `$$a_1^2$$` parses to *a12* — silently wrong maths; (b) a `\\`-then-`=` line inside a matrix is read as a setext heading, so the parser shreds one formula across several nodes. A block is turned into a formula only if it lies ENTIRELY inside a scanned span. ```` ```math ```` fences are verbatim, so they skip the dance.
13. **KaTeX fonts are inlined as data: URIs in `katex-inlined.min.css`.** The render page loads with `baseURL: nil`, so a relative `url(fonts/…)` resolves to nothing and every glyph silently falls back to a system font at the wrong metrics. Inlining removes the resolution step. Snapshot only after `document.fonts.ready` — KaTeX lays out synchronously but the fonts arrive async, and snapshotting early bakes fallback metrics into the cached PDF forever. **The fonts are OFL-1.1, separate from KaTeX's MIT code** — `licenses/KaTeX-fonts-OFL-1.1.txt` + notice in `THIRD-PARTY-NOTICES.md` are required, and `make-app.sh` copies both into the bundle (the licence must travel with the fonts).
14. **The reading-line band repaints the whole visible rect on every selection change** (`setSelectedRange` override → `setNeedsDisplay(visibleRect)`). A bare caret move only invalidates the thin caret sliver, so the band would smear — lit on the old line, dark on the new. Drawn in `drawBackground` beneath glyphs, and only when the selection is empty (an active selection is its own stronger highlight).
15. **Keyboard nav: fn+arrow arrives as Home/End/PageUp/PageDown (keyCodes 115/119/116/121), NOT as a bare arrow.** Matching a bare arrow (123/124) for the paragraph keys was a real bug — it made plain ←/→ jump a paragraph instead of moving one character. Vertically the scheme is two-tier by heading rank: down the doc `fn`(top-level `#` heading only, the SHALLOWEST rank present via `topHeadingNav`) › `⌘`(every heading, `headingNav`) › `⌥`(page); `fn+⌘` (keyCode 116/121 WITH `.command`, so the `[.command]` cases must precede the catch-all `_`) jumps to document start/end. Across the line `fn`(paragraph) › `⌥`(sentence) › `⌘`(line). ⇧ extends. Unit boundaries come from `TextNavigator`; paragraph/sentence stops also honour block starts (`MDAttr.blockId`) so a heading is never skipped. The page holds still and the cursor moves inside it — scroll follows only when the caret would leave the screen (`revealCaret`), never top-anchored. **The bare single-letter block keys (E/I/D/U/J/T) match by keyCode (e=14·i=34·d=2·u=32·j=38·t=17), NOT by character** — a non-Latin input source (Korean, …) turns `e` into `ㄷ` and silently broke every bare-letter shortcut; keyCode is layout-independent. (⌘-modified equivalents already fall back to the Latin layout, so only the bare keys needed it.)

16. **Every block operation goes through `applySourceEdit` — the single mutation path.** Add/delete/move each compute ONE (range, replacement) pair in `BlockEdit` and hand it over, so re-render, cursor reveal and undo are earned once and nothing can half-apply. A move is deliberately length-preserving (block A + the untouched gap + block B, reordered). Modeless popups and alert sheets re-resolve the block at confirm time — offsets move under them.
17. **Nothing reaches disk until ⌘S.** `applySourceEdit` changes memory and marks the document dirty; `data(ofType:)` is the only writer. Change tracking is left to NSDocument (it watches the undo manager), so undoing back to the original correctly reports clean — note the undo group closes on the NEXT run-loop turn, so a test asking immediately is asking too early. ⌘R warns before discarding unsaved edits.
18. **A file is written back in the encoding it was READ in.** `String(decoding:as:UTF8.self)` never fails — it substitutes replacement characters and reports success — which is how a Windows CP949 file arrived as a wall of "?". Use `TextEncodingDetector`, and accept a guessed encoding only when re-encoding reproduces the original bytes exactly (the system's own guess for arbitrary input is Windows-Cyrillic, which doesn't reverse). Text the file's encoding can't represent is REFUSED with an explanation, never written lossily.
19. **An edit re-renders only the blocks it touched (`spliceRender`), not the document.** Full re-render measured 131ms on a 64k-character file and over a second on 1.2MB — paid again on every undo; the splice is 9–29ms. It is safe because a block renders the same alone as in context (verified per block kind in `FragmentRenderTests`); reference-style link documents are the exception and take the full path. Two things it must keep doing: **lift the fragment's block ids clear of existing ones** (fragments number from zero, and two neighbours sharing an id merge into one stop for the reading cursor), and **run the fragment to where the NEXT block starts** so the separator that follows isn't spliced away. `SpliceRenderTests` asserts the result is identical to a full render after every operation — a divergence there is invisible on screen.
20. **In plain text a block is a LINE, blank ones included; in markdown it is a paragraph/heading/table/fence.** A blank line in a .txt is spacing the author typed, not structure — so it must be selectable, deletable and movable, and "add below" inserts exactly one line (the file's own ending, CRLF preserved) instead of copying the neighbouring gap. Because a blank line is nothing but its terminator, a plain-text block's RENDERED range includes that terminator while its SOURCE range stays content-only. `PlainTextRenderer` must also keep `output.string == source` exactly — a dropped trailing newline is a silent data change on the next save.

21. **Open Recent emptying after a rebuild is the AD-HOC SIGNATURE, not the code.** Measured 2026-07-20: the list survives quitting and relaunching the same binary, and disappears only when a freshly built bundle replaces it. macOS keeps recents in a SharedFileList keyed to the app's signing identity, and an ad-hoc signature's cdhash changes on every build, so each build looks like a different app. A Developer ID / App Store build has a stable identity and keeps its list across updates — don't "fix" this in code. (The store itself is TCC-protected, so a shell can't read it to check; `defaults read ai.ww-w.fast-md-reader` won't show recents either.)
22. **Save is greyed out unless `CFBundleTypeRole` is `Editor`.** With `Viewer`, AppKit decides the app cannot write that type and disables `saveDocument:` — while `save(nil)` called directly still writes the file, so the save path looks fine and only the menu is dead. The two text entries (markdown, plain text) are `Editor`; the office entries (Word, OpenDocument and HWP) are deliberately `Viewer`, which is what greys Save out for the read-only formats — there the disabled menu is the intended behaviour, not the bug. The close-and-save prompt works either way, which makes this easy to misread as "saving is broken".

23. **The table of contents is rebuilt from BOTH render paths.** `spliceRender` changes headings as surely as a full render does (`## typed into a block`, a section moved, a heading deleted), and for a while only the full path called `reloadOutline()` — so the sidebar quietly described the document as it was several edits ago. Anything that changes the text must end at `reloadOutline()`.
24. **Reflow is deferred to the END of a resize / sidebar animation, and the reading position is restored by ANCHOR.** Re-wrapping a long document per animation frame is what made both feel like they were fighting the user (`suspendReflow`). Two things must stay true afterwards: lay the whole document out BEFORE scrolling (a narrower column makes it taller, and until that layout exists the scroll is clamped to the old, shorter height — which is why position held when widening and drifted when narrowing), and restore via `readingAnchor()`/`restore(_:)`, which keeps the CURSOR's line at its old height if it is on screen and otherwise puts the centre character back at the centre. A plain scroll offset means different text once the wrapping changed.
25. **A spinner must be shown BEFORE the work and forced to draw.** `setBusy(true)` + `spinner.display()`, then the work on the next run-loop turn. A delayed show scheduled with `asyncAfter` can never fire: the work owns the main thread, so the timer's turn only comes after the work finished and cancelled it — that version shipped and showed nothing. Gated on document size (>120k chars) so short documents don't flash.
26. **A control next to the traffic lights is a TITLEBAR ACCESSORY, not a toolbar item.** This macOS lays toolbar items out trailing with the title leading, so a toolbar button lands on the far right no matter how the identifiers are ordered — `.flexibleSpace` doesn't move it, and neither does asking for the system `.toggleSidebar`. `NSTitlebarAccessoryViewController` with `layoutAttribute = .leading` puts it where every Mac app keeps it. Centre it with a constraint; the title bar's height is not ours to guess.
27. **The sidebar is a real `NSSplitViewItem(sidebarWithViewController:)`.** That is what supplies the inset rounded panel, the system material and the light/dark behaviour. An `NSVisualEffectView` of our own underneath a real sidebar just hides it.
28. **A local build carries its OWN bundle identifier — `ai.ww-w.fast-md-reader.dev` — and must keep doing so.** `make-app.sh` rewrites `CFBundleIdentifier` and the display name (the Dock shows "Fast Document Reader (Dev)") in the COPY inside the bundle; `Resources/Info.plist` keeps the real identifier. macOS keys per-app state to the identifier, so while they were shared, every local rebuild took the installed release's Open Recent list with it — invariant 21 explains why a rebuild invalidates it, and a shared identifier is what let that reach an app nobody rebuilt. `notarize.sh` and `appstore.sh` pass `DIST_IDENTITY=1` to keep the real identifier **and then verify it survived**, refusing to ship a `.dev` bundle: a flag that protects only when every future caller remembers to set it is not protection. Consequence when testing a cold start — a dev build's sandbox container is `…Containers/ai.ww-w.fast-md-reader.dev`, so invariant 4's cache path shifts with it.
29. **A unit test on a parser cannot tell you the parser is REACHED.** `.odt` shipped registered, parsed and covered by 24 passing tests — and could not be opened at all: both office call sites hard-coded `DocxReader`, so ODF bytes went to the Word parser and threw. Every `OdtReaderTests` case called `OdtReader.read` directly, which proves the parser and says nothing about the application. 266 tests were green with the feature completely dead, and only launching the app found it. Two rules follow. **`DocumentTypes.readOffice` is the single dispatch table** — one place that maps an extension to its reader, throwing on anything unhandled rather than falling through to Word; a second, divergent list is how this recurs. And **any new format needs one test through `MarkdownDocument`'s own read path**, not just through its parser, plus an actual open in the built app. The same blindness applies to `Info.plist` (invariant 6) — both are seams no compiler and no unit test can see.
30. **Measure the corpus before believing it.** All eight contracts ship `word/footnotes.xml`, which read as "footnotes matter here" and ranked a whole sprint — but every one holds ONLY Word's `separator`/`continuationSeparator` boilerplate, which Word writes into nearly every document. Real footnotes: zero. Likewise the claim that filtering those separators is what prevents phantom notes: removing the filter changes nothing, because only CITED notes are ever appended — the filter is a second layer, not the load-bearing one (confirmed by mutation). **When a check passes, break the thing it checks and confirm it fails**; a green assertion whose subject is unreachable proves nothing. Two real defects this session were found by exactly that mutation step, and one "verified" claim was withdrawn because of it.

31. **Setting an `NSTextAttachment`'s `.image` silently discards a custom `attachmentCell` the moment it's set** — AppKit switches to its own bounds-based image layout at that point, replacing whatever cell was there. Found by experiment while building the chart/SmartArt placeholder (`OfficeTextBuilder.appendUnsupportedGraphic`), which is exactly why that placeholder sizes itself through `.bounds` alone rather than through invariant 1's `SizedAttachmentCell` — there is no "not yet loaded" state for a placeholder whose image is never nil to begin with, so nothing can revise its size after the fact.
32. **`NSTextContainer.exclusionPaths` invalidates the WHOLE container's layout — AppKit does no partial invalidation.** Real text-wrap around a floating image was built and measured (`FloatWrapExclusionSpikeTests`, kept as a reproducible spike): N floating images cost N sequential full re-layouts, measured 45ms with none vs. 301ms with twelve on a 400-paragraph document, and it isn't paid once — resizing the window or toggling the sidebar re-runs the whole pass on top of the reflow already happening there. Under the owner's "light and fast is the core" constraint this was measured, found too expensive, and deliberately not shipped; floating images still render inline, on their own line.
33. **A style's ID is not localised even though its NAME is.** The heading reader's own comment argued from a true premise — a Korean Word install shows a style named 제목 1, so matching by name is unsafe — and drew the wrong conclusion from it: that built-in heading styles couldn't be recognised at all. The id (`Heading2`) stays the same in every locale even when the name doesn't, and skipping it left 103 of 188 heading-bearing documents rendering with zero headings. **A true premise can protect a false conclusion** — the fix is to check what the premise actually rules out, not everything nearby it. **HWP is the same lesson from the other side, and must not be "corrected" by this one:** an HWP paragraph has no locale-stable style id at all, so `HwpReader.headingLevel` matches the NAME — the English one first (`Outline 1`, the locale-stable identity HWP does offer), the Korean one as fallback, plus the custom names Korean reports actually title sections with (각 장 제목 → level 1, 각 절 제목 → 2). Its exclusion list is measured, not theorised: 표의 제목 (a table's caption) appeared 112 times in one document and 목차 turned forty-odd contents lines into headings, so a name must say title/chapter/section and must not be about a table, figure, note or running head. Without any of this a real corpus rendered flat — HWP's `head_type == Outline` marks only the paragraphs that use outline NUMBERING, and 13 of 14 real files had no table of contents at all before it (`c46dcfa`).
34. **Measuring document STRUCTURE is not measuring reader BEHAVIOUR, and when they disagree, behaviour wins.** An XML-grep prediction of the same heading gap said 36% of documents render flat; running the reader itself through its own read path said 55% (103/188). The grep undercounted because it treated the mere presence of *some* outline-capable style in `styles.xml` as protection, when what matters is whether the styles the document's headings actually use resolve to one — only executing the real code path can see that. The grep number was briefly recorded as a "correction" of the higher one; it was the wrong turn, not the fix (`docs/06-research/gap-list.md` keeps both, visibly, on purpose).
35. **`FileManager.enumerator` stops silently at the first unreadable subdirectory unless given an explicit error handler.** The corpus probe (`CorpusProbeTests`, invariant 30's tool) under-counted its own input by about a dozen files with no indication anything was skipped — the exact silent-truncation failure this project's working style forbids, caught only because the probe's own count was checked against a second method. Fixed by passing an error handler that counts skips and continues rather than aborting the walk.

36. **The reader's rhythm lives in ONE base design system, never re-inlined per renderer.** `RenderTheme` carries the base tokens (type scale + line-height/spacing/indent ratios + colour); `MarkdownStyle`/`OfficeStyle`/`PlainTextStyle` are thin branches that inherit it and override only what their format needs. The rhythm constants were once duplicated across `MarkdownRenderer`, `OfficeTextBuilder`, `TableBlockBuilder` and `PlainTextRenderer` (a change in one never reached the others); hoisting them was proven byte-identical by `RenderThemeParityTests`, a parity harness that snapshots every layout-affecting attribute. Markdown output must stay identical when a token moves — re-inlining a magic number is the regression that harness exists to catch.

37. **Office paragraph/run/table formatting comes from the DOCUMENT's own styles, resolved into `ParagraphFormat`/`Span`/table `columnWidths` and applied by the one format-neutral `OfficeTextBuilder` — and "the document said nothing → the theme token, byte-identical" is the load-bearing contract.** docx resolves docDefaults → `w:basedOn` chain (cycle-guarded) → direct `w:pPr` per property; ODF resolves the `style:parent-style-name` chain; both feed the SAME builder, and absolute points ride the same `fontSizeScale` (reading-size ÷ document-default) that font size does — `.multiple` line-heights are ratios and don't scale. An office change that alters output for a document declaring NOTHING is a regression (every design-system sprint proved its unspecified case identical). Tables fill width from `w:tblGrid` / `style:rel-column-width` kept as PROPORTIONS and re-solved to ABSOLUTE INTEGER point column widths at the reading column (invariant 39) — never percentages fed to `NSTextTable` (it recomputes those per row → a merged row's boundary drifts a pixel, see invariant 42) and never a raw twip as an absolute width. Named table styles (`w:tblStyle` + `w:tblStylePr` + `w:tblLook`) resolve per-cell UNDER the direct props: cell-direct > table-direct > table-style > theme — a cascade that now runs PER EDGE, with an edge the document silenced told apart from one it never mentioned (invariant 47). Paragraph shading/borders draw via the `CodeCardLayoutManager` block-background path (draw-time, NOT `exclusionPaths`).

38. **Comments are captured but drawn at DRAW-TIME, gated by the panel.** docx `word/comments.xml` and odt `office:annotation` become `MarkdownDocument.officeComments` + `Span.commentIds` on the commented spans (never merged away, like bookmarks — and the office read contract is `OfficeReadResult{blocks,comments}`, one dispatch, invariant 29). The right comment panel is an `NSSplitViewItem` inspector (hidden by default); when open, the commented spans get a faint band + a number badge painted BEHIND already-laid-out glyphs (like the reading-line band), never an inline `NSTextAttachment` — so toggling the panel sets a flag + `setNeedsDisplay` and MUST NOT reflow the document. A comment-free document is byte-identical and the menu item is disabled.

39. **Tables are a REAL `NSTextTable`, so cell text is selectable, copyable and searchable — with columns pinned to ABSOLUTE INTEGER point widths, never percentages.** `TableBlockBuilder` lays every cell into a `GridTextTable` (an `NSTextTable` subclass that remembers its column PROPORTIONS) as ordinary paragraphs carrying an `NSTextTableBlock`, so the text is part of the document — which is the whole point: a custom-drawn attachment, however crisply aligned, is a *picture* the reader can't select, copy or ⌘F. Columns are set as absolute integer point widths (cumulative ROUNDED edges of proportion × reading-column width) — NOT percentages: `NSTextTable` recomputes a percentage per row, so a column boundary lands on a slightly different fractional pixel in a 4-cell row than in a span-merged one (the "열이 살짝 어긋남" drift). `DocumentWindowController.resizeTableColumns` → `TableBlockBuilder.resizeTables` re-solves those absolute widths to the current reading column on every reflow — and an OFFICE table is BUILT at that same width rather than at the `initialColumnWidth` placeholder, so the first paint is the final one (invariant 48). Because cell content (INCLUDING image/diagram/formula attachments) now lives in the TOP-LEVEL storage as ordinary paragraphs, the existing top-level media passes (`presizeKnownMedia`/`prerenderAllDiagrams`/`reconcileMedia`/`measureRemoteImages`) size and paint cell media natively — there is no per-table descent any more. **History (don't rebuild it):** an earlier custom-drawn engine (`TableAttachmentCell` + `TableGeometry` + `CellText`, added `c1173cb`, removed 2026-07-24) computed its own x-edges to kill that drift, but the drift was a wrong-algorithm choice (percentage widths), NOT an `NSTextTable` limitation — absolute integer widths fix it while keeping real text, and cost far less code. `MarkdownRendererTests`/`OfficeTextBuilderTests` inspect the `NSTextTableBlock`s (block span/shading/border + `GridTextTable.columnProportions` + cell text in the top-level string).

40. **`--extract` is a HEADLESS branch of the same binary, gated in `main.swift` BEFORE `NSApplication`.** `FastDocReader --extract <file>` prints Markdown to stdout and `exit()`s without ever constructing `NSApplication` (no window, no Dock icon, no `AppDelegate`) — the arg check must stay first in `main.swift` or the GUI spins up. Its purpose is token economy for an AI reading a `.docx`/`.odt`: it reuses the app's OWN office reader via the SAME `DocumentTypes.readOffice` dispatch (invariant 29), then `OfficeMarkdownSerializer` (`[OfficeBlock] -> String`, pure/view-free, so it is unit-tested without AppKit). The serializer's contract is **conservative + honest**: map to real Markdown only when unambiguous, and degrade anything a GFM pipe table can't hold (merged cells via `colSpan`/`rowSpan` ≠ 1, or non-`.paragraph` block content in a cell) to a `<raw>…</raw>` plain-text dump rather than a fabricated grid that reads as correct — a wrong table is worse than none for the AI consuming it. Escaping is deliberately minimal (only `|` inside a pipe cell, newlines→spaces); an AI tolerates messy text but not a mis-structured table. `stdout` is ONLY the document (errors → stderr, exit 1 read/parse · 2 usage), so a script can trust the pipe. Coverage: docx family + odt (the office readers' scope — legacy `.doc`/`.rtf` are unsupported, same as the reader) plus md/txt verbatim (decoded through `TextEncodingDetector`, invariant 18). Proven both as pure serializer units AND through the real dispatch (`OfficeDocumentTests.testHeadlessExtractSerializesThroughTheRealOfficeDispatch`) — a serializer unit test alone can't prove the reader FEEDS it (invariant 29's lesson again).

41. **A markdown feature can ship DEAD, and only rendering it proves otherwise — `MarkdownFeatureAuditTests` renders every CommonMark+GFM feature through the real `MarkdownRenderer.render` path and asserts its evidence attribute.** Strikethrough (`~~x~~`) shipped for a long time producing PLAIN text: the parser emits a `Strikethrough` node (GFM is on — tables prove it), but `inlineFragment` had no case for it, so it fell through `default` to unstyled children while the README advertised it. GFM task-list `[ ]`/`[x]` had the same fate — swift-markdown consumes the box into `ListItem.checkbox`, and `renderList` ignored it, so the ticks vanished entirely. Both are fixed (strikethrough → `.strikethroughStyle` over the inner span; checkbox → `☐`/`☑` glyph in place of the bullet). The lesson is invariant 30/34's: a parser unit test (or a grep of the visitor) can't see an unREACHED case — only the render path can, so any new inline/block support MUST add an audit assertion. **Footnotes (`[^id]`) are deliberately NOT rendered as footnotes yet** — swift-markdown does not parse them, so a real implementation must source-scan like `scanMathSpans` (superscript refs + a collected section + srcRange/blockId wiring), tracked as a deferred unit; README must not claim footnotes until then (`testFootnotesAreNotYetRenderedButContentSurvives` characterizes the current preserve-but-don't-render behaviour).

42. **When a native API "doesn't align / is slow", suspect your INPUTS before reimplementing it.** Two rounds of this on tables, both resolved by a one-line input choice, not a custom engine: (a) **alignment** — feeding `NSTextTable` PERCENTAGE column widths let it recompute them per row so a boundary drifted a fractional pixel; the "fix" was a whole custom-drawn engine, when the real fix was ABSOLUTE INTEGER widths (invariant 39). The source already stored absolute twips — WE threw the precision away by converting to percent. (b) **speed** — that custom engine measured each cell with `NSAttributedString.boundingRect`, which is ~O(n²) in char count on rich CJK text (a 1000-char patent cell: 53ms; its first 100 chars: 0.8ms — a 10× length for a 67× time), making a 13-table document crawl at ~750ms/reflow; a reused `NSLayoutManager` was O(n) (~4.6ms), but the deeper truth is the engine shouldn't have existed. Both the drift and the O(n²) were self-inflicted by the workaround. `NSTextTable` with absolute integer widths gives selectable/copyable/searchable text AND alignment AND native incremental layout, in far less code. The general rule: percentage-vs-absolute, twip-vs-point, and the layout API you pick are load-bearing — a "native API is inadequate" conclusion should be the LAST resort, after the inputs are proven right.

43. **A regular (non-agent) macOS app MUST present an interactive window on launch — launching to only the menu bar is an App Store 2.1 rejection, however intentional.** This reader deliberately started empty (no window, menu-bar-driven) and it FAILED App Store review 2026-07-23: "No interactive window displayed upon launch." A document reader has no "new document" to open, so `applicationDidFinishLaunching` now presents the Open panel (`openDocumentPanel`) on the next run-loop turn WHEN launched with no document (`NSDocumentController.shared.documents.isEmpty` and no visible window) — matching shipping App Store readers; cancelling returns to the menu-bar state, which is fine. Deferred one turn so a file passed AT launch opens its own window first and suppresses the panel. `applicationShouldOpenUntitledFile` stays `false` (no blank "new" docs); the panel, not that hook, satisfies the rule. `applicationShouldTerminateAfterLastWindowClosed` stays `false` so closing the last document returns to the (now legitimate, post-launch) menu-bar state rather than quitting. Do NOT "restore" the empty launch — it re-earns the rejection.

44. **HWP is parsed from raw bytes by rhwp's FFI, so it branches BEFORE the zip path — and its images are pre-decoded at read time.** A `.hwp` is CFB/OLE binary, not a zip (a `.hwpx` IS a zip, but rhwp reads both from `Data` itself), so `ZipArchive(data:)` would throw on `.hwp`. `MarkdownDocument.read(from:)` AND `HeadlessExtract` check `DocumentTypes.isHwp(ext)` and hand the bytes straight to `HwpReader.read` before ever constructing a `ZipArchive` — one predicate, invariant-29's single-dispatch discipline (HWP is DELIBERATELY absent from `readOffice`'s archive table, which throws as a safety net if HWP ever wrongly reaches it, since HWP can't conform to the `ZipArchive`-taking `OfficeDocumentReader`). No archive means no lazy image source later, so `HwpReader.read` decodes every embedded image inside the ONE rhwp parse handle's lifetime (`imageBase64` needs the SAME live handle the JSON came from) into `OfficeReadResult.images`, keyed `hwpimg:<binDataId>`; `reconcileMedia` looks that map up before the archive. Everything downstream is the shared office engine — the JSON maps to the SAME `OfficeBlock` vocabulary, so `OfficeTextBuilder` renders HWP with no HWP-specific render path (invariant 37's "unspecified → theme token" contract holds for HWP too).
45. **The rhwp parser ships as a statically-linked, dead-stripped xcframework — and SwiftPM does NOT relink on a CONTENT change.** `Vendor/RhwpNative.xcframework` is a prebuilt Rust static library (arm64, tens of MB); static linking lets the final link dead-strip everything the app doesn't call, so the app grows by a FRACTION of the library — most of it, including the svg2pdf/resvg PDF path, never ships. **No size is quoted here on purpose**: every one that was went stale, and one of them was simply wrong for months — it claimed the app grew ~3.3 MB when 3.3 MB was the whole executable BEFORE the parser existed (measured 2026-07-30: 3.3 → 11.0 MB release, i.e. +7.7). Measure it, don't quote it: build `release` at the commit that added the parser and at its parent, and compare `FastDocReader.app/Contents/MacOS/FastDocReader`. Note that `make-app.sh debug` is roughly 3× the release size, so a debug measurement answers a different question. The trap: SwiftPM's `binaryTarget` keys off the xcframework PATH, not its bytes — overwriting the `.a` in place does NOT trigger a relink, so `swift build` silently keeps the OLD parser and new FFI/JSON changes never appear. After replacing the binary: `rm -rf .build` to force the relink, AND verify the copy landed (`stat` the `.a` size against the build you just made). This bit us once — a sub-agent's rebuild left a stale 56 MB binary in `Vendor/` while the correct build was 58.8 MB, and the equation test failed against code that was actually correct. Rebuild + relink procedure: `docs/BUILD-RHWP.md`.

46. **A graphic's size comes from the DOCUMENT's own page width, never from the reading font — and is re-solved on every reflow.** A picture was authored as a fraction of the page it sat on, so the reader reproduces that fraction: the scale is the reading column ÷ `OfficeReadResult.pageContentWidth`, and a picture inside a TABLE divides by that table's own `TableFormat.sourceWidth` and is clamped to its CELL instead — a page-scaled picture sits small in a cell that was stretched to fill the column, and an unclamped one blows apart the fixed column geometry invariant 39 depends on. `nil` page width → scale 1, authored sizes verbatim, byte-identical to before this existed. Fusing this with `fontSizeScale` was tried in both directions and both fail: riding the font scale made ⌘+ inflate photographs and left no way to enlarge type alone, and pinning it at 1.0 left photographs tiny beside 1.6×-enlarged text. Because the scale depends on the COLUMN, the size cannot be frozen at build time — each graphic carries what it was measured against (`MDAttr.officeGraphic` → `OfficeGraphicInfo.authored`/`basisWidth`), and `DocumentWindowController.resizeOfficeGraphics` re-derives it through the SAME `OfficeTextBuilder.graphicSize` the build used, from the AUTHORED size and never from the current on-screen size, which would compound rounding across a hundred resizes. Without that pass a widened window re-wrapped the text and re-solved every table while the pictures stayed the size they were built at, and the page visibly came apart. It does NOT weaken invariant 1: that forbids a reserved size that depends on whether PIXELS are loaded, and this one is identical loaded or not. Alignment rides along in one place too — `OfficeBlock.aligningGraphic(to:)` applies the CONTAINING paragraph's alignment, so all three formats (docx `w:jc`, ODT `fo:text-align`, HWP's own) state it once instead of re-deriving it, and a graphic's own explicit alignment always wins.

47. **A table border edge has THREE states, and an unmentioned one resolves against whether the TABLE drew a box — not against whether anything declared anything.** `BorderDecl` is `.drawn(side)` / `.suppressed` (the document turned this edge off) / `nil` (never mentioned). "Off" and "silent" used to arrive as the same `nil`, so the builder had to guess and guessed differently depending on whether a neighbouring edge happened to speak — a report whose table ruled only its header row and its inner grid lost its outer box entirely. Resolution, per placement: where the table drew at least one real rule (`EdgeBorders.drawsAnyEdge`) an unmentioned edge draws NOTHING, because the table described its own geometry and left this edge out; where the table drew NO box the edge falls back to the ordinary cell-direct > table-direct > table-style > theme cascade. That second arm is the correction two independent reviews found from different angles: keying the decision off "anything was declared" let a single cell carrying one `w:val="nil"` — exactly what Word writes when someone removes one rule from one cell — strip its other three edges of the cascade the rest of the table is using, measured on a 2×2 as 1pt-faint / 0 / 1pt-faint / 0 against neighbours at a solid 1pt. **A faint stand-in outline for the first arm was built and then REMOVED (`22a9758`) — do not propose it again:** measured across one 114-table report, 95 tables turn their outer rules OFF explicitly and only 19 merely never mention them, so a rule keyed on "unspecified" fired on a sixth of the tables and skipped the rest — the reader saw some tables boxed and some open with no way to tell why, which reads worse than honestly showing what is there. A table that declared NOTHING is unchanged, which is every markdown, HWP and ODT table (invariant 37); a table that explicitly turned every edge off draws nothing where it used to get the app's own default rule, which is the same request read consistently and matches Word. What happens where two cells DISAGREE about the boundary between them is invariant 50, which runs after this resolution, not instead of it.

48. **The reflow passes are paid on EVERY render, so they must be cheap, idempotent, and never run against the outgoing document.** Three of them walk the whole storage from `updateTextInset` — `reanchorFillMarginTabs`, `resizeTableColumns`, `resizeOfficeGraphics` — measured at 91 ms per full pass on a 62-table HWP. Three rules, each earned by measurement: (a) a caller about to REPLACE the storage wants `settleReadingColumn()`, the geometry-only half, not `updateTextInset()` — the old code paid the full walk THREE times per ⌘+ press (render, `display`'s opening call, its async tail) when only the last one runs against the new string, and the other two re-solved a document that was about to be thrown away. (b) An OFFICE table is BUILT at the width it will be laid out at — `MarkdownDocument.render` hands `OfficeTextBuilder.build` a `tableWidth` of the column minus one `lineFragmentPadding` per side, the same number `resizeTables` re-solves to — so the first paint is the final one; building at the placeholder and resizing a moment later is the visible "table draws small, then snaps wider", two paints of the same table with the first one wrong. Markdown still uses `TableBlockBuilder.initialColumnWidth`, which is why that placeholder stays. (c) A pass touches only what actually MOVED and invalidates ONCE over the union of the ranges it touched: per-cell invalidation measured 73 ms on a 62-table Korean form (1,702 cell paragraphs) against 5 ms on a 610-cell Word report — a 14× gap on 2.8× the cells, because each `invalidateLayout` re-walks everything after it — and recording every cell unconditionally invalidated the whole document to set widths to the values they already had.

49. **Slicing or deferring `precomputeLayout` was measured twice and rejected twice: the freeze is the REBUILD, not this pass.** Its `chunk = 20_000` really is the wrong bound — characters misread office documents, so a 38-table report is laid out entirely in one uninterruptible turn while a 1.2 MB markdown file gets sixty — and both obvious repairs were built, measured on real documents, and reverted. (1) Slicing by TIME (2k characters per pass to a 10 ms budget) on a 62-table HWP: worst freeze unchanged (216 ms → 194–238 ms) and time to a fully laid-out document roughly doubled (665 ms → 1126–1342 ms). (2) Bounding each step by STRUCTURE as well as length, plus laying the VIEWPORT out first, on a 38-table / 27-image docx: against a baseline of 2 turns / 105–121 ms measured six times, viewport-first alone 2 turns / 121–148 ms, a 256-unit structural cap 3 turns / 155–170 ms, a 64-unit cap 10 turns / 186–192 ms — monotone in turn count, every variant worse, worst freeze improved in none. Both failed for the same reason, which is the part worth keeping: the freeze is `OfficeTextBuilder.build` + `display`, so slicing layout finer cannot shorten it and only adds per-turn cost — and time-to-interactive, the one thing (2) was meant to buy, is already paid: at the instant `precomputeLayout` returns, 451 of the 452 visible characters were ALREADY laid out. What this walk buys is the complete SCROLL BAR, not the visible page. Judge a third attempt by `layoutStepCount` (deterministic) and not by the stopwatch — wall clock on this machine swings up to 3× under load, with one 2825 ms outlier that never reproduced. `OfficeRenderLatencyTests` is the instrument and pins the character bound, so the next attempt has to measure rather than argue.

50. **One boundary, one drawer — `collapsesBorders` is OFF and the winner is OURS, not AppKit's.** With collapsing on, two adjacent cells can each declare a different rule and AppKit silently picks which one shows; a vertically merged cell changes who its neighbour is from row to row, so one vertical rule changed weight — or vanished — partway down a table with nothing in the document asking for it. Off, `TableBlockBuilder.build` resolves every boundary itself, in this order. **Ownership:** an interior vertical boundary belongs to the cell on its LEFT (drawn on `.maxX`), the table's own left perimeter to the column-0 cell (`.minX`); an interior horizontal boundary to the cell ABOVE (`.maxY`), the top perimeter to the row-0 cell (`.minY`). Every other side is set to 0 and costs no `setWidth` call at all — a fresh `NSTextTableBlock` is already 0 — so exactly one rule is drawn per boundary, never two and never none. **Winner:** an EXPLICIT suppression beats a bare theme FALLBACK first, because that fallback is our invented default (reached only when `tableDrewABox` is false, invariant 47) and a reader-invented rule must not override an author who deliberately turned an edge off; then wider wins (`nil` counts as 0, so `.suppressed` loses to a GENUINELY declared rule, which is what Word does — removing one cell's border still leaves the neighbour's own visible); then equal widths defer to whichever side was actually declared; then the owner's own colour, so nothing depends on scan order. **A merged cell takes the WIDEST winner across its whole span** — one block carries one width per edge, so per-segment fidelity is not available to us, and the widest is the choice that keeps the rule consistent down the merge instead of making it disappear mid-table. Fold that over a **SORTED** neighbour order: a bare `Set<Int>` iterates in a per-process hash-randomised order, and the same document's merged rule came back red 6/14, blue 5/14, green 3/14 across 14 launches — the very fault this pipeline removes, reintroduced from a different direction. **Geometry follows:** `contentWidth = cellWidth − 2·padding − its own two widths, in FULL` (the interior halving modelled collapsing and is gone), and `edges(forWidth:)` solves across `width`, not `width − 1` — measured through `NSLayoutManager.usedRect` in a container 200pt wider than target (a container sized AT the target silently clips an overshoot into looking exact), **exactly 600.0000 at 2/3/5/9/13 columns, merged and mixed**, where the collapsing formula gave 599.5. The LAST edge is floored to `usable.rounded(.down)`: a fractional reading column (705.5) would otherwise round to 706 and put the final rule back outside the container. **Padding shrinks before a border does**, floored to an integer — a column too narrow for `defaultCellPadding` on both sides is ours to compress, a rule the document asked for is not; only a column narrower than its own two borders still overshoots, boundedly. **`rowSpan` is UNTRUSTED input:** `OdtReader`/`HwpReader` pass `table:number-rows-spanned` and HWP's own span through verbatim and only `DocxReader` clamps at its source, so EVERY walk of `p.row..<(p.row + p.rowSpan)` against the neighbour grid must clamp to `rowCount` — one unclamped read trapped `Index out of range` and killed the app on opening an ordinary `.odt`, while all 832 tests stayed green because the docx path clamps first. Cost, four interleaved paired runs on the 2,489-cell report: `OfficeTextBuilder.build` 118.5 ms median against HEAD's 118.5, a warm ⌘+ press 391 against 397 — indistinguishable end to end (an isolated 30-sample measurement of the build stage alone did find ~+12 ms, which the single-neighbour fast path halved). Parity holds: `resizeTables` subtracts both widths in full too, and `cells the resize pass still moves after a render: 0 of 2489`.


51. **A table cell's terminating newline carries the CELL's own attributes, so a cell costs ONE attribute run and not two.** `TableBlockBuilder` appends a `"\n"` after each cell; appending it bare let the `enumerateAttribute(.paragraphStyle)` pass below stamp a fresh default `NSMutableParagraphStyle` on it — default alignment, no font, no colour — which can never equal the cell's own run. Dumped verbatim: `{1,6} "발간등록번호" keys=[NSColor,NSFont,NSParagraphStyle,mdBlockId] align=1` then `{7,1} "\n" keys=[NSParagraphStyle,mdBlockId] align=4`, 53,522 times on one report. **Every document with a table paid it**, and it was the single biggest cost in this reader: attribute runs 107,937 → 56,563 (−48%) on that report and 17,389 → 15,308 on the reference, `display` 3,595 → 1,051 ms (−71%), worst freeze 7,620 → 3,304 ms, and the reference's own ⌘+ 1,903 → 1,031 ms. Installing into a LIVE text view costs ~50 µs per run and is indifferent to what the runs contain — measured at 1 run/13 ms, 19,655/913 ms, 108,353/5,585 ms — so run count is the knob and half the runs were these newlines. Inheritance is an ALLOW-list (font, colour, paragraph style, baseline offset, block id, bookmark, srcRange): anything that DRAWS or is clicked (attachment, background, underline, strikethrough, link) keeps the bare terminator, so a future attribute degrades to the old behaviour instead of silently riding along. An EMPTY cell keeps the bare terminator too — it has no attributes of its own and the preceding character's belong to the PREVIOUS cell. Laid-out height is identical to five decimals on ten real documents, `--extract` is byte-identical over 1.4 MB, and `resizeTables` still moves 0 of 51,968 cells; the same bug then turned out to exist one layer up, in `OfficeTextBuilder.cellContent`'s INTERIOR separators between the blocks of a multi-paragraph cell, and is fixed the same way: that function already re-applied each paragraph's STYLE across its terminator (TextKit reads spacing and line height from a paragraph's last character), so `unifyTerminator` extends that existing pass to the rest of the allow-list rather than adding a second mechanism — 12 lines, reusing `TableBlockBuilder.inheritableTerminatorAttributes` rather than copying it, because a divergent second list is how the two halves would drift apart. The separator belongs to the paragraph it TERMINATES, which is forced rather than preferred: the style pass already stamped the preceding paragraph on that character, so taking the FOLLOWING block's font would leave it matching neither neighbour. Interior separators reference 2,323 → 374, report 271 → 7, and total attribute runs fall by MORE than the separators removed (−2,548 against −1,999 on the reference) because identically-styled paragraphs then coalesce end to end. **The residue is irreducible and worth knowing before anyone chases it: 268 of the reference's remaining 374 terminate an EMPTY paragraph**, which has no attributes of its own to inherit — invariant 51's empty-cell rule reaching one layer up. Laid-out height stayed identical to five decimals on both real HWPs and every fixture, `--extract` byte-identical over 1.4 MB, `resizeTables` still 0 of 51,755 cells.

52. **Font substitution is resolved once per DECLARED FONT, gated on a sample character, and NEVER splits a span.** The earlier design asked CoreText per span and split each span into maximal same-substitute runs; that cost 2,209 CoreText calls and 17,910 spans on the reference HWP where the current one costs **22 calls and 9,328 spans** — built font runs 19,088 → 9,239, installed 23,097 → 15,516, warm ⌘+ −19%, worst freeze −34%, and `FontSubstitutionResolver` got 95 lines SHORTER. The rule: for each distinct declared font, take the most common character under it that is neither absorbing (Common/Inherited/Grapheme_Extend) nor Private Use, ties broken on the lower codepoint; ask CoreText once whether the declared font draws it; if not, stamp that answer across every span using that font. Each exclusion is load-bearing and was found by a real document: restricting the census to non-ASCII put 5,177 Latin characters onto Lucida Grande because a stray `Ⅴ` won; not excluding absorbing classes made every census answer "space"; not excluding PUA and not refusing LastResort put 450 characters of drawable Korean out as boxes. Gate on COVERAGE, never on availability — Times New Roman, Arial, Helvetica and Georgia are all installed here and none draws Hangul, which is exactly what Word writes into a Korean document's ascii slot. The cost is honest and recorded: `nil` in `Span.resolvedFontDescriptor` now means "draws the SAMPLE character", so a stray glyph inside an otherwise-covered paragraph is still substituted by AppKit at draw time. **Flattening every font to one family was measured and is WORSE, not better — do not propose it as a speed setting:** installed runs 108,353 → 160,626 (+48%) on a real report, because the system font has no Hangul and AppKit then substitutes per character. Even flattening font AND colour AND paragraph style together lands at 70,042 installed against 1,654 built — the residual is all Korean substitution, so no amount of uniformity escapes it.

53. **Per-script fonts: each format keeps its OWN slot vocabulary and its OWN classifier table, and a run breaks on the resolved FAMILY NAME — never on the slot index.** A document names a family per script (docx `w:rFonts` 4 slots + theme refs, ODF 3, HWP's `CharShape.font_ids[7]`), and reading only the Latin one drew Korean in the face chosen for English. **Measured, 1,557 real HWP/HWPX: 53.6% declare different fonts across their slots** — one row is `["휴먼명조", "Palatino Linotype", "HY신명조", …]`, i.e. Latin really is meant to differ. Do NOT unify the three classifiers: Word's table is keyed on Unicode BLOCKS and its `cs` slot is reachable ONLY by a run-level `w:cs`/`w:rtl` (Hebrew, Arabic, Syriac and Thaana all go to **ascii**); ODF §20.358 Table 22 is its own normative range table whose 22 GAPS — space, all General Punctuation, PUA, everything above U+FFF0 — are WEAK and absorb; HWP maps the shared UCD script table onto seven slots. Merging any two silently mis-renders the third. `ScriptRunSplitter` is shared, and the family-not-slot rule is what makes invariant 37 structural: two slots naming one family produce ONE piece, i.e. the original span. **A slot the document never DECLARED states no opinion and must not break a run either** — three independent reviews found that from three directions, because comparing `nil` as though it were a family name reintroduced slot-splitting through the back door: an ODT under a western-only style turned a 167-character Korean paragraph into 50 spans (`제1항` became 제 / 1 / 항), and a docx carrying `w:asciiTheme="minorEastAsia"` split every sentence in two and left the Latin half family-less, 1,189 spans becoming 2,186. Same reason, two more rules: a theme role whose own default is empty falls through to `a:latin` (`a:ea`/`a:cs` are empty in FIVE of five real themes, and Word only reaches the family there through the document's LANGUAGE, which this reader may not consult), and a docx run of pure separators takes its NEIGHBOUR's family before the block table's, because Word stores a Korean sentence as one `w:r` per word so the space between two words is its own run and absorption structurally cannot reach it — keeping the table first measured 5,396 spans averaging 2.3 characters. Swift has no `Script` property (verified: 58 members of `Unicode.Scalar.Properties`, none of them script), so `ScriptRanges.swift` is GENERATED from the UCD by `Scripts/gen-script-ranges.py` with the licence notice travelling with the data; ICU is reachable via `-licucore` and is used ONLY as a test-time oracle, never linked into the app, because Apple has never documented that C API.

54. **A picture whose format has no decoder names its format; it never shows a stretched broken-image glyph — and the reconcile gate must know that decision is final.** `NSImage(data:)` returns nil for WMF, and the old `att.image = image ?? brokenImage()` stretched a 22×22 SF Symbol across a 700×465 pt frame, which reads as "this file is corrupt" when the truth is "this reader cannot draw this format". Measured: the reported document is 8 of 11 pictures WMF, the reference manual 1 of 60 — which is the whole reason one was reported and the other never was — and across 340 HWP files, 95 of 1,825 pictures (5.2%) are undecodable, all WMF or PCX, but BIMODALLY so (some documents lose 13 of 13). The pixels usually exist: LibreOffice rendered one of those blobs to a correct 794×1123 chart matching the caption we draw beneath it, and rhwp itself vendors a WMF→SVG converter that is `pub(crate)` and behind a feature flag. The label is decided at READ time and drawn by `SizedAttachmentCell`, never by assigning an image, because an attachment built as `.image` carries no `placeholderLabel` and `resizeOfficeGraphics` would stretch a labelled card on every window resize. **`reconcileMedia`'s on-screen gate must test the label as well as `att.image == nil`**: the old broken icon was what closed that gate, so without the second half every undrawable picture is re-read, re-decoded and re-failed on every scroll for as long as the document is open.

55. **A table too big to build without freezing the open is left out of the FIRST PAINT only, spliced back afterwards, and the document is then walked exactly as any other render walks it.** `OfficeTextBuilder.giantTableIndices` draws the line at `rows >= 50 AND rows × columns >= 500` — measured over 1,280 documents / 11,207 tables it fires on **0.68% of tables and 1.4% of documents while removing 30.9% of all grid cells**, and on **zero** of the reference manual's 388, which must therefore come out unchanged (250,088 characters both ways). Both halves are load-bearing: row count alone catches a 103×2 prose table that costs nothing. First paint on a 51,816-cell report goes **3,130 → 628 ms**, three interleaved repeats at 628/641/620. The work is MOVED, not saved — 398 ms of deferred build plus 1,736 ms of payback is one full build within 1%. **Two rules were learned by shipping them wrong, and both are counter-intuitive.**

    **(a) The document MUST still be walked after the splice.** The original design skipped `precomputeLayout` on the theory that TextKit settles the giants by itself in ~7.5 s at a 45 ms worst slice — which is TRUE while the reader sits still, and worthless, because a reader scrolls. Arriving at an unlaid region forces every character in between in one call: **69,460 and 80,008 ms**, measured twice, which is what a reader calls an infinite loop. With the walk the same scroll costs **3.2 and 5.1 ms**, and the walk's own slices (274–682 ms) are no worse than what the undeferred shipping build already produces on the same document (1,367 ms). The prototype rejected this walk on its worst slice alone and never priced arrival, which is exactly how the comparison came out backwards.

    **(b) A RE-render must never defer — first paint only (`hasPaintedOnce`).** Deferring on ⌘+/⌘−/⌘R takes the reader's anchor against the FULL document and then replaces the storage with a string a third as long, so `restore` clamps that character to the deferred string's LAST one and parks the viewport at its bottom. The splice then inserts 273,016 characters ABOVE that point, leaving the viewport inside a grid nothing has laid out — and from there it is DRAWING, not scrolling, that pays: filling the layout hole under the visible rect advances ~800 characters per pass at 150–300 ms a pass. Same document, same process, only the anchor differs: at character 0 a press costs a 498 ms worst turn and settles in 1,275 ms; at character 326,797, **9,038 ms and 181 turns over 100 ms**. The prize was always a first-paint prize, so confining it there costs nothing measured. Reviving re-render deferral needs an anchor that survives the swap — mapped through `MDAttr.blockId`, the one identity both strings share — and it must be measured with the reader DEEP in the document, because at the top every version of this looks perfect.

    Everything else follows from those. The judgement lives in the RENDER layer, so `--extract` cannot see it (proven byte-identical at 725,535 and 604,800 bytes — invariant 40). The payback builds run **one per run-loop turn** (25/156/154/695/706 ms); all five in one turn would trade the freeze away for a 1.7 s one, and building them off the main thread was measured (876 ms, worst main slice 32 ms, output equivalent) and rejected because `NSTextTable`/`NSParagraphStyle` construction is not documented as thread-safe. The rebuilt grid inherits the stand-in's **block id** or two blocks merge into one stop for the reading cursor (invariant 19). The anchor is restored FROM the walk's completion, never before it — restoring first clamps the scroll to a height that does not exist yet and put a reader 75% down at character 298 (invariant 24, from a new direction). Rejected with numbers: permanently flattening these tables reaches the same first paint (691 vs 664 ms) but loses the grid forever and makes the document 1.5× taller; deferring layout without deferring the build buys nothing, because the freeze IS the build.

56. **Two measured things about the deep-⌘+ freeze, one of them a fix that had to be REVERTED — read the second before trying the first again.**

    **(a) The storage swap forces a full layout, and the obvious fix breaks the reading position.** `display` replaces the text while the clip view is still parked wherever the reader scrolled to, so AppKit lays the INCOMING document out that far just to satisfy the offset — inside `setAttributedString`, one uninterruptible call. Measured with the reader 75% into the 401,765-character report: **`display` alone 87,638 ms**, returning with 290,394 characters laid out; scrolling to zero first makes it **937.9 ms** and 192. That part is real and worth having. It was committed (`2dea892`) **and reverted the same session**, because that forced layout was propping something up: `restore` scrolls to `min(y, textView.bounds.height − clip.height)`, and with nothing laid out the view's HEIGHT is still stale, so the clamp threw a reader who was 75% down to character 282 — the top. Generating glyphs inside `restore` is NOT enough (tried): glyphs are not what sets the frame height. Anyone re-attempting this must establish the HEIGHT before scrolling — lay out to the anchor and `sizeToFit`, or restore from a completion after the walk. **The `restore` half of that commit was KEPT and is correct**: asking for the glyph you want BEFORE asking how many exist, because the old `numberOfGlyphs > 0` pre-guard made restore a silent no-op whenever nothing was laid out. **NEITHER property has a test, and that is deliberate** — six attempts across three shapes each produced tests that passed with the fix removed. "A re-render never defers" shows itself only as the storage briefly shrinking, and on any fixture small enough to ship that window is under one run-loop turn; "restore works before anything is laid out" cannot be staged because `display` lays out enough that the old guard passes anyway. Both were verified by measurement on the real 401,765-character document (reader at 41,370 → 282 with the fix out, correct with it in) and the gap is written into `GiantTableDeferralTests` where a future author will look. Check any new test here against a mutation before trusting it (invariant 30).

    **(b) The freeze itself is AppKit's, and it is quadratic.** Sampled during a 64 s freeze, the whole main thread sits under `CA::Transaction::flush` → `NSTextView drawRect:` → `_glyphRangeForBoundingRect:…okToFillHoles:` → `_NSFastFillAllLayoutHolesForGlyphRange` → `NSATSTypesetter` → **`NSTextTable rectForBlock:` → `NSTextBlockLayoutHelper init` → `characterRangeForGlyphRange:` → `_NSFastFillAllGlyphHolesForGlyphRange`**. Laying out ONE LINE inside an `NSTextTable` fills holes across the WHOLE document, so a 2,196-row table pays it per line — which is why it scales with depth (12.6 s at 25%, 64 s at 75%). Two candidate fixes were measured NOT to help: pre-generating every glyph (`ensureGlyphs` over 401,765 characters is only 22 ms — the holes are LAYOUT holes), and taking our own `drawBackground` off the layout-forcing query (AppKit's `drawRect:` makes the same call itself). Flipping `allowsNonContiguousLayout` DOES fix it — ⌘+ at 75% goes **65,853 → 5,073 ms worst turn**, suite green, and the scroll-bar fear does not materialise (+0.0% height error) — but it costs invariant 1's territory: `demo/math.md` jumps **1,366 pt** when its formula lands (42 pt today) and `demo/images.md` lays out **7,982 pt against 12,124**, because less space is reserved when the visible range is computed non-contiguously.

    **The owner's chosen direction supersedes all of it.** A paged document (docx/odt/HWP — anything with `officePageContentWidth`) should be ZOOMED like every real viewer rather than re-typeset at a new font size; markdown and plain text keep the font-size model because they have no page. That removes the rebuild entirely instead of optimising it, retires the three whole-storage reflow passes for office (the column stops changing), and collapses invariant 46's graphic scaling. Design, build order and the numbers to beat: `docs/02-planned/paged-zoom-design.md`.

57. **PAGED MEANS THE DOCUMENT IS THE TRUTH AND THE APP CONTRIBUTES NOTHING — and four of the five things that broke that rule were the app "helpfully" filling in a value the document HAD stated.** A paged document (`officePageContentWidth != nil`, never `kind == .office`) is reproduced, not re-typeset: ⌘+/⌘−/⌘0 are `NSScrollView.magnification` and rebuild nothing, and every absolute the renderer needs comes from the file. The owner stated the rule as *"우리 자체 판단을 버리고, 파싱하는 정보 그대로 다 보여지게 하자 (정의되지 않은 값들만 디폴트를 뭘로 지정할지만 옵션)"*. What that costs in practice was measured by opening one real Korean report side by side with Word, Pages and Hancom's HWP Viewer at matched scale, and every number below is from that comparison.

    **(a) "The document said nothing" is a claim that has to be EARNED, and four times it was false.** Each of these read as unspecified and was not: Word keeps a table's cell margin in the **default table STYLE** (`w:style[@w:type="table"][@w:default="1"]`), not on the table, so reading `w:tblPr/w:tblCellMar` alone turned an explicit `top=0 bottom=0` into 7pt of app padding on all four edges — 14pt of a 28.3pt row where Word draws 18.5pt. A Korean/Japanese document states its line height ONCE, section-wide, as `w:sectPr/w:docGrid@w:linePitch` (360 twips = 18pt) rather than per paragraph; unread, every unstated line fell to the font's natural 13pt, five points short. A docx that omits `w:sz` from `w:docDefaults` is not asking for 11pt — 11 is what modern Word WRITES into a new file, 10 is what it ASSUMES when the element is absent, and under this model that constant is the theme base size, so it decided **99.1% of that document's characters** (9,567 of 9,657). And heading numbering (`1.`, `1.1.`, `가.`) lives in the heading STYLE's `w:numPr`, not on the paragraph. The pattern is invariant 33's, from a fourth direction: **before adding a fallback, find where the format actually keeps that value.** **HWP was the FIFTH, and it was the largest of them:** the parser exported no cell margin at all, so every HWP table cell fell to `TableBlockBuilder.defaultCellPadding` — 7pt, invented, on all four edges. Measured by sweeping that one constant on a real 490-page 행정업무운영편람 against the official viewer's **429** pages: **7pt → 495 · 4 → 471 · 2 → 449 · 1 → 439**, i.e. the whole 66-page gap was that number. The fix is upstream, in the parser: rhwp's `Cell::effective_padding(&table.padding)` already resolves the `aim` flag, the table-wide fallback and the preserved-pad hygiene limit against Hancom's own PDFs, so the FFI exports THAT (four `padLeft/Right/Top/Bottom` in points) and `HwpReader` maps it to `Cell.edgePadding` — one rule, in the place that already earned it, rather than a second one here. Real values arrive per cell (1.41 / 0.00 / 2.83 / 5.10 / 8.50pt over 5,494 cells), and the document goes **495 → 455** pages, its `.hwpx` twin 160 → 148. The remaining 26 pages are NOT this: rhwp's own pagination of the same file is **393**, i.e. 8% SHORT of the viewer while we are 6% long, so the residue is a different quantity and must not be "fixed" by tuning padding back up. **Two candidates for that residue were then measured and BOTH are dead ends, so nobody re-derives them.** (1) A declared row height does not exist: rhwp's `Table.row_sizes` is the CELL COUNT per row (`UINT16[NRows]`, `rebuild_row_sizes()`), not a height, and the model carries no row-height field at all. (2) Line-height overshoot is real but nearly free to remove: swapping the paged percent arm from `.atLeast` to `.exact` — which clamps every inflated line back to the requested height — moved the file **455 → 452** pages and the `.hwpx` twin not at all, against a predicted ~34 page-equivalents. That prediction came from summing excess height over every line and dividing by the page height, and the reason it is wrong is worth keeping: **summed excess is not page-equivalents.** 10,021 of this document's 14,545 lines are inside TABLES, a row's height is its TALLEST cell, so shrinking most lines in a row changes the row by nothing. Judge a candidate by moving the number it claims to explain — one release build and one `--pdf` run — not by an integral. The remaining ~26 pages are honestly unexplained. Together these took the measured row 28.5 → 19.17pt against Word's 18.48.

    **(b) The opening zoom is NOT 1.0, and "Word opens at 100%" was a guess that shipped.** Measured on the owner's machine: **Word 120%, Pages 125%, Hancom's HWP Viewer ~115%** (its status bar reads "86%" in 96-dpi units — 0.86 × 96/72 = 1.147, confirmed off its own ruler at 1 cm = 65.4 px on a 2× display against 56.7 px at actual size). This value has now moved twice, both times because it was reasoned about rather than measured: fit-to-window opened documents 1.5×–2.9× oversized and the owner called the type too large; 1.0 then made this the smallest reader of the four and the owner said so again. `DocumentWindowController.defaultPageZoom` has since moved once more, to **1.8**, on the owner's reading of a real report on this display — the peer band is the floor, not the target, because Word's 120% is measured on Word's own 10–11pt body while a Korean report set in 10pt at a 481pt column is smaller on screen than that comparison suggests. ⌘0 returns there — the menu says "Default Zoom" because "Actual Size" and "Zoom to Fit" were each a lie in turn.

    **(c) What is NOT ours to fix, so nobody re-derives it.** AppKit CEILS an `NSTextTableBlock` border to a whole point — measured, declared 0.1/0.25/0.5/0.75/1.0pt ALL draw 2px, 1.25–2.0 draw 4px — so a document's 0.5pt rule cannot be honoured through `setWidth(for: .border)` at all. **And the cost is LAYOUT, not just pixels — measured through the reader's own builder, which is the only way this number means anything** (`SubPointRuleSpikeTests`). At a 600pt target, a WHOLE-point rule lands EXACTLY (1.0 and 2.0 both hit 600.00 at 2/3/5/9/13 columns — invariant 50's arithmetic is right), while EVERY fractional width overshoots by about a point per column boundary, growing linearly: 0.5pt gives **+2 / +3 / +5 / +9 / +13**, so a 13-column table of Word's ordinary half-point rules ends 13pt past its column. The size of the fraction barely matters (0.10 and 0.25 behave alike; 0.50 and 0.75 behave alike), so no friendlier number tunes it away. **Two earlier figures are withdrawn — 594.0 (an underrun) and 609.0 (an overrun) — both came from a HAND-ROLLED `NSTextTable` rather than `TableBlockBuilder`; the spike's own first draft was hand-rolled and reproduced 594.0 at a plain 1.0pt border, where the shipping builder is exact to 0.01.** **The GEOMETRY half is fixed**: `TableBlockBuilder.laidOutBorderWidth` rounds a declared width UP to a whole point and BOTH the `setWidth` call and the content-width subtraction go through it, so all eight widths now land exactly at every column count (0.0 overshoot across the board). What that does NOT do is make the rule thinner — a half point still DRAWS as one, which is what AppKit does with it. **The INK half is CLOSED, not deferred — do not propose the custom block again:** the owner read a real report at 1pt and said "1pt는 괜찮아 어색하지 않음", so stroking genuine sub-point rules ourselves is not wanted. The measurement above stays so nobody re-derives it; `TableWidthIndependenceTests` and `SubPointRuleSpikeTests` guard the geometry that WAS fixed. A substituted font's line height is NOT the inflater (refuted by measurement: `.AppleSystemUIFont` at 11pt and Apple SD Gothic Neo at 11pt both report 13.0pt, well under Word's 18).

    **(d) The non-paged half must not move, and that is testable.** Every change above is inside `if paged`, and the whole-suite evidence is that the row-height and grid work broke **zero** existing tests — the in-suite fixtures declare no page width, so they stay on the fill-the-window model (invariant 37's contract). A change here that turns any existing test red without a paged fixture in it is a regression, not a specification.

    **(e) The band between two pages is the document's own two margins, and this is where "the app contributes nothing" was hardest to notice.** A running header/footer is drawn into a band reserved at each page boundary (`PageBandGeometry`/`PageBandLayoutDelegate`/`PageBandPainter`), and that band was `header + footer + 12pt`, the 12 being a "space between pages" the reader invented because no `RenderTheme` token names one. The document states it: **bottom margin + the next page's top margin**, which is precisely where a header and a footer live in all three formats — so the band is `max(declared margins, what we actually draw)`, expanding past the paper only when this reader's rendering would otherwise cover the body. On a real `.odt` the two agree to within a point (85.10 declared against 84.15 invented), which is exactly why a made-up constant survived review. HWP is the format that says this most clearly: its exported top margin already INCLUDES the header strip (measured 163.00 = declared 120.48 + 42.52 of 머리말), so the paper itself tells the reader how much room the header gets.

58. **A running header/footer is RESERVED by moving line fragments and PAINTED at draw time — it never enters the document string, and every format's live page number is substituted at the moment of painting.** `PageBandLayoutDelegate` (the documented `NSLayoutManagerDelegate` hook `shouldSetLineFragmentRect`, NOT an `NSLayoutManager` subclass — overriding `setLineFragmentRect` only RECORDS a rect the typesetter has already decided, so the next line lands on top of it) pushes each page's first line down by one band; `PageBandPainter` draws into that space from `drawBackground`, like the reading-line band and the comment highlights. Inserting the header into storage was rejected for the reasons that keep recurring: a page boundary lands mid-paragraph and would split it, and ⌘F would answer nineteen times for one header. **What each half must keep doing.** The band's height is invariant 57(e)'s, and the two outer edges are NOT `textContainerInset` — that can only give the top and bottom the same value, so leading room comes from the same line-shift mechanism and trailing room from `setExtraLineFragmentRect`; the trailing effect is ABSOLUTE (`baseline + trailing`), not incremental, because AppKit already reserves one default line height past the last character whether or not anything overrides it. The "snap to top" thresholds in `restore(_:)` and `scrollCharToTop(_:)` must add `leadingBand` or ⌘-Home scrolls straight past a reserved header. A blank entry and an ABSENT one are the same answer — reserve nothing — which is why `w:titlePg` with no first-page part synthesizes an EMPTY entry rather than falling back to the default header (invariant 47's three-state lesson, in a second place). **Page numbers are three separate mechanisms and only one was ever wired:** Word marks a `PAGE` field with `w:fldChar`/`w:instrText`, ODF caches the last computed number as the field ELEMENT'S OWN TEXT (so an unmarked `.odt` footer reads "- 2 -" on every page), and HWP stores no characters at all (`Control::AutoNumber(Page)` — an unmarked `.hwp` reads "-   -"). All three now set `Span.pageNumberField`, which merge guards must exclude exactly like bookmarks and comment ids, and `PageBandPainter.substitutingPageFields` replaces them per page. HWP's own run lands wherever the vendored parser's control-position fallback puts it — correct for a right-aligned header, at the END of the line for a number centred between dashes. **WHERE each side is drawn is the SHEET's own grid, not a fraction of the gap:** the gap layout opens is the document's margin PLUS whatever room the previous page's last line left unused, so centring in halves of it moved the header and footer a few points per page — measured at 5.5 / 11.125 / 18.25pt above the sheet edge on three consecutive pages, which the owner read as "홀수쪽, 짝수쪽의 여백이 다름". docx states both distances (`w:pgMar/@w:header`/`@w:footer`) and they are used from the sheet edge, clamped into the real gap so an overrunning table still cannot be painted over; ODT and HWP state neither yet and keep the halves fallback (ODF measures its top margin TO the header rather than to the body, so it needs its own analysis, not this mapping).

59. **⌘P on a paged document prints the reader's OWN pages — there is no second pagination engine, because `pitch` IS the paper.** Measured on the reference report: body 671.75pt with margins 99.25/70.90, and the band is exactly those two margins (invariant 57e), so `pageContentHeight + band == 841.90 == A4`, and its width `56.7 + 481.9 + 56.7 == 595.30`. So printing needs one subtraction — `PagePagination.sheetTop` — and `ReaderTextView.knowsPageRange`/`rectForPage` hand AppKit those rects. Letting `NSTextView` paginate instead puts the reader's page 3 across two sheets; mutation-checked, the printout collapses to **1 page against the reader's 4**. Paper is the document's own sheet with printer margins at **ZERO** (the document's margins are already inside the laid-out text — as `textContainerInset` sideways and as the band vertically), `scalingFactor` 1, both paginations `.clip`; `.fit` would scale the sheet to the printer's imageable width and silently void every measurement invariant 57 exists to protect.

    **Everything below was found by printing and then measured; three of the five are bugs that were also wrong on screen.**

    **(a) Page 0's sheet top is NEGATIVE and must stay that way** (−71.25 on the reference). The reader shows its own 28pt inset above the first line while the paper wants a full 99.25pt margin; the difference is blank paper the view has nothing to draw in, and a print rect may reach past `bounds`. Clamping to 0 prints page 1 with a 28pt top margin and every other page with 99.25.

    **(b) The reading zoom does NOT reach the paper, and that was measured, not assumed.** `scrollView.magnification` is a transform on the CLIP view; the text view's own `bounds`/`frame` are identical at 1.0 and 1.8 (595.3 × 6493.9 both times), so `NSPrintOperation(view: textView)` prints at actual size with nothing to save and restore. `PrintPaginationTests` pins it, so a future zoom that DID move the view's own geometry is caught here rather than on paper.

    **(c) `NSPrintInfo.shared` must be COPIED, never configured.** The old code set `horizontalPagination` on the shared object, which was self-correcting only because it re-set the same two fields every time; adding paper size and margins to that would leak A4-with-no-margins into the next document printed — a markdown file on a page with no margins at all.

    **(d) A header is authored against the PAGE's body width, not the reading column — the reference report printed with NO running header at all because of this.** `configurePageBand` took its `columnWidth` from the live text container, which for a paged document only equals the page body once the window has been laid out; the first render can precede that, leaving the container at its 600pt starting size, and nothing re-runs the band afterwards. The header is `w:jc="right"`, so it was built into a 600pt box laid at the page's own left margin and its text ended at x=656 on a 595.3pt sheet — off the paper. Taking the width from `officePageContentWidth` makes it a constant of the FILE (invariant 57's rule) and removes the timing dependence; Word's own PDF shows the header 42 times, ours now 7 of 8 pages (page 1 is a `w:titlePg` cover, correctly bare).

    **(e) A footer belongs to its own sheet, and when it cannot fit there it is SKIPPED, not moved.** `sheetEdge` clamps into the gap layout actually opened so an overrunning table is not painted over — and when the overrun passes the paper's edge that clamp pushes the footer onto the NEXT sheet. Measured: a table overran by **1.12pt** and printed `- 5 -` at the top of page 6. `PageBandPainter.footerFitsOnItsSheet` judges it against the UNCLAMPED grid position, which is exact — the delegate always shifts a page's first line to precisely `page × pitch + leadingBand`, verified on all 8 pages of the reference (841.90, 1683.80, 2525.70, … to the hundredth), so page boundaries never drift even though the gaps between them do. Skipping follows `bandExists`'s existing judgement: a missing page number reads as a short page, a misplaced one reads as a corrupt document. Task 2's page outline would surface the same fault on screen, so this is not a print-only correction.

    **PDF export is FREE and must not be built** — macOS's print panel has "Save as PDF", so the moment ⌘P works, so does PDF export. An "Export as PDF…" item would be a second, worse path to the same file. (It is also what makes this testable: the operation runs headless to a file, so page count and paper size are ordinary assertions rather than something judged by looking at a printout.)

    **THE LIMIT, measured, and NOT a print defect: the reader paginates the reference report to 8 pages where Word makes 19.** Ruled out by measurement, so nobody re-derives them: content is complete (7,314 characters in `word/document.xml` against 7,321 in the storage — an earlier "193,094" was a regex that let `<w:t[^>]*>` match `<w:tbl>`), the line count is right (689 line fragments), the 18pt `w:docGrid` line pitch is parsed and applied, images are not it (2 attachments, 202pt, none zero-height), deferred giant tables are not it (storage identical after the splice), and explicit page breaks are not it (ONE `w:br w:type="page"`, zero `w:pageBreakBefore` in the document AND in `styles.xml`). What remains is concentrated in Word's own front matter — its pages 1–6 hold 51 lines between them — plus tables that this reader cannot split across a page (invariant 55/58's known edge), which is why 3 of our 8 printed pages carry table rows inside the margins. That is a paged-fidelity item (`docs/06-research/2026-07-29-paged-fidelity/`), not something printing can fix.

60. **The View menu's three page toggles — page outline / header / footer — are a LAYOUT switch, not a visibility flag, and the sheets they draw are the same rectangles printing puts on paper.** `PageViewOptions` (global, in `UserDefaults`, all three ON by default) decides three things at once: which entries `MarkdownDocument.applyPageBand` passes on (a hidden header is passed as NO ENTRIES, so it is neither measured nor painted — one mechanism, not a flag each consumer re-checks), whether the band exists at all with nothing drawn in it (`separatesPages`), and whether the page-break hairline is drawn (`drawsDivider` — a real sheet edge says it better, so the rule yields to the outline). `applyPageBand` is called from BOTH the render and `reapplyPageBand`, deliberately one function: a toggle that re-derived the band with its own copy of that arithmetic would drift from the render's the first time either was touched.

    **(a) "쭉 연결되어 보이고" means the band must not be RESERVED.** The comments panel can set a bool and repaint (invariant 38) because its marks sit on glyphs that do not move. This cannot — so a toggle re-solves the band and re-lays out, in invariant 56's order: scroll to the top FIRST (invalidating with the clip parked deep makes the next draw fill every hole in one call — 87,638 ms against 937.9), then invalidate, then restore the reading position from the layout walk's completion, never before it. It must never reach `MarkdownDocument.render`: nothing is rebuilt, `renderGeneration` does not move, and the reading column of a paged document never shifts by a point.

    **(b) The restore is PARKED, not a completion closure — `precomputeLayout` cancels an in-flight walk whenever a new one starts (`layoutToken`), and a cancelled walk's completion never runs.** Measured while building this: a toggle whose walk was superseded by the render's own opening tail silently lost the reader's place, landing them at character 0 from 75% down. `pendingAnchor` is applied by whichever walk reaches the end, so supersession becomes a later restore instead of a lost one.

    **(c) The desk between two sheets is `RenderTheme.pageDeskGap`, and it is the one number here no document declares.** Two stacked sheets of paper TOUCH — so the space you see between them on screen is a property of the desk, not of the page, and there is nothing to read it from. This is NOT invariant 57(e)'s invented constant returning: that one claimed to be the document's own inter-page space, which the document HAD stated. Reserved only while the outline is on, and never printed — `PagePagination.sheets` takes it back off, so the paper is exactly the document's own sheet and `makePrintOperation` reads its height from the sheet rather than from the pitch. **Getting this wrong looked like nothing had happened:** the first version had no desk, the sheets tiled edge to edge, the desk fill was covered by the very sheets it sat behind, and the feature drew as a hairline indistinguishable from the page-break rule it replaces. Confirmed by pixel-sampling the capture — gap and paper both `(255,254,255)`.

    **(d) With the outline on, the FIRST and LAST pages get their full margins** (`leading = max(headerLeading, marginTop)`, and the mirror for the footer). Otherwise page 1's sheet begins one top margin above the first line, which with only a header's worth of leading room is ABOVE the view — so page 1 draws with no top border and a visibly shorter margin than every page after it. The two outer PAINT arms then place their content at the document's own header/footer distance INTO that room, reducing to the previous `top: 0` whenever the reservation is only as tall as the header itself.

    **(e) Owner decisions, settled here rather than asked.** GLOBAL rather than per window (a reader who wants continuous flow wants it for every document, and the choice has to survive a relaunch); all three ON by default (the owner's own framing was *"페이지 외곽 모양(그럼 선이 필요 없어짐)"* — the outline REPLACES the rule, so shipping it off would hide the feature); NO drop shadow (it costs a blur per sheet on every scroll pass and the desk plus a hairline already reads as paper). The default is one menu click to change.

    **(f) A page is CENTRED on the paper's width, and four separate things kept undoing that.** All four
    were reported by the owner looking at the screen, and each is a different mechanism: (1) `sizeToFit`
    widens a text view's frame back to its clip view, so `PageCenteringClipView`'s `frame < clip` test
    silently stopped firing — measured at 727.2pt of frame around a 595.3pt sheet, and 909.0pt after a
    zoom press, which also drove the magnification to `clipFrame ÷ frame` = 0.8876 (a zoom-IN that
    zoomed OUT, two feedback loops solving for each other). Fixed at the root: the clip view reads
    `ReaderTextView.pagedPaperWidth`, a constant of the DOCUMENT, so no frame drift can reach it; the
    frame is additionally pinned by `pinPagedFrameWidth` after every `sizeToFit` and every
    magnification change, because the frame is the SCROLLABLE area and a wrong one lets a reader scroll
    into empty desk. (2) AppKit calls `constrainBoundsRect` when the bounds ORIGIN changes, not when the
    clip's FRAME does — so opening the table of contents narrowed the reading area and left the old
    origin, and `recentrePage()` now asks for the constraint explicitly. (3) THREE scroll call sites
    hard-coded `x: 0` (`restore`, `scrollCharToTop`, and the reveal in the outline jump); each meant
    "scroll vertically to here" and each undid the centring on every reflow, which is why the page
    snapped left on opening AND closing the panel. They now preserve `clip.bounds.origin.x`. (4) The
    desk BESIDE the page is the scroll view's background (`syncDeskBackground`) — the text view cannot
    paint outside its own bounds, so without it a centred page sat on the same white as the paper and
    read as no page at all.

    **(f2) ONE function applies the whole paged view state, and that is the fix for the CLASS rather
    than for the four bugs.** Five rules describe a paged view — which width is the paper, how wide the
    scrollable frame is, what colour the space beside the page is, whether the page is centred, whether
    a sideways scroller is needed — and they were applied by FIVE paths each handling a different
    subset. Audited: the reading-column settle did all five, a magnification change three, `sizeToFit`
    one, and the View-menu page toggle **none**, which is why switching the outline off left the desk
    colour behind. `applyPagedViewState()` does all five and every path calls only that; it is a no-op
    for a document with no page, so the non-paged branch goes through the SAME function rather than a
    second divergent one. Two more single-source repairs came out of the same audit: `pageSheets` is now
    DERIVED from `printSheets` (two copies of the sheet arithmetic is how screen and paper would come to
    disagree), and the desk gap is carried on `PageBandLayoutDelegate.deskGap` — the layout that
    RESERVED it — rather than re-read from the preference at draw time, which left a window where a
    paint would take the new answer against the old band and mis-tile every sheet by 12pt.
    **Testing this needs care:** a toggle's own layout walk ends in `sizeTextViewToFit`, which applies
    the same state, so a test that waits for the async tail passes whether or not the TOGGLE did it —
    fake-green, confirmed by mutation. Assert IMMEDIATELY after the toggle, which is also what a reader
    sees.

    **(g) A panel that takes width away shrinks the page to fit; nothing ever enlarges it.**
    `shrinkPageZoomToFit` is one-directional by instruction — *"무리하게 줄이진 말고, 창이 우측으로
    삐져나가지 않도록 축소해서 맞추라는 뜻"* — so the sidebar and the comments inspector call it and a
    manual window resize still just reveals more desk (the removed "zoom follows the window" rule stays
    removed). Side margins are kept: it fits `paper × zoom` into the reading area MINUS
    `pageWindowSideMargin` on each side.

    **(h) A page break is never drawn through a table.** A line inside a table cannot be shifted
    (invariant 55/58), so a table crossing a boundary overruns it and layout opens no band — and a
    sheet drawn on the arithmetic grid put its edge, and the desk behind it, in the middle of the
    table's rows. `PagePagination.joiningUnopenedBoundaries` unions those sheets, which says the true
    thing: this page ran longer than its paper. SCREEN ONLY — paper cannot stretch, so `rectForPage`
    keeps the paper-sized grid, and that divergence is the medium's rather than two implementations
    disagreeing.

    **(f) A stored global preference makes any test that measures the band depend on it.** `PageBandReservationTests` pins the pre-feature shape in `setUp` (outline off, header and footer on) — otherwise nine of its assertions move with the shipped default and the suite reads differently for a developer who had switched the outline off. Every new test here resets the store on both sides.

61. **A table that will not fit on the rest of its page is MOVED WHOLE to the next one — decided by measuring a layout that already happened, and carried out by shifting exactly ONE line.** Until this existed a table simply ran past its page's text bottom, so its rows printed inside the margin: on the reference report 4 of 16 tables overran by 71 / 139 / 145 / 236pt, three of its eight sheets. The screen could tell that truth (`PagePagination.joiningUnopenedBoundaries` unions the sheets), paper cannot.

    **(a) SPLITTING was built and measured here, and invariant 64 later shipped it under a menu — read both.** What follows is why it is not the DEFAULT and why it can never be unconditional. Letting the ordinary between-page rule shift table lines produces a real Word-like split, and on a table of single-line rows it is flawless: rows stay whole, each page's segment keeps its own border box, the header and footer land in the gap (`docs/fixtures/office/paged-visual/tablepage.docx`, captured). On a real report it TEARS. A vertically merged cell spans the boundary, so the half of the row that moved leaves that cell stretched across the gap — with this reader's own running header and page number painted inside the table — and the row's two halves end up a page apart. Splitting honestly needs `NSTextTableBlock` geometry we deliberately do not own (invariants 39/42). The safe-row-boundary variant — break only where no `rowSpan` crosses — is what invariant 64 built; it does not save the reference report's first table, whose left column is merged across the very boundary in question, so that one is still carried whole.

    **(b) ONE line is enough, and that is measured, not assumed.** The typesetter positions each line after the previous one, so shifting a table's first line carries every later line with it — the same property the between-page rule already relies on. Pushing the reference report's table #0 left its height identical (438.45pt both ways) and landed its visual top exactly on target. **But the first line in TEXT order is not the table's top**: a vertically merged cell is centred in its own span, measured 21.35pt below the table's top edge on that same table, so `TableMetrics.topInset` carries that distance. Moving by the naive `target - rect.minY` would land the table's visible top that far into the page.

    **(c) MEASURE, then place — the height does not exist when the typesetter asks.** At the moment `shouldSetLineFragmentRect` is called for a table's first line nothing has measured that table, so `DocumentWindowController.settlePagedTables` walks the COMPLETED layout, decides (`PagePagination.tablesToPush`), and re-solves. That extra pass rides `precomputeLayout`'s existing chunked walk, so no single turn grows. Cost on real documents (10k–27k characters, 8–13 tables moved): **2–3 rounds, 85–260ms total**, of which the measuring step itself is **1–4ms** — the cost is entirely the re-layouts. A document with nothing to move pays one line-fragment walk and stops.

    **(d) The two refusals are load-bearing.** A table TALLER than the page body is never moved: it would overrun the next page just as far, having emptied the one it left (a 660pt table on a 220pt page — moving it adds a near-empty page and changes nothing else). And an already-decided entry is kept VERBATIM rather than re-derived: a moved table now fits, so re-deriving would drop it, which would move it back, which would make it not fit — the settle would never converge. Because the record only ever grows and the layout rule is idempotent (a table sitting at a page top declines to move again), the loop terminates on its own; `maxPagedTableSettles` is a backstop, not the mechanism.

    **(e) The whole document is invalidated each round, deliberately.** Moving a table changes which boundaries LAYOUT opened, and `openedBoundaries` is what the painter and the page outline read — keeping the earlier half of that record while re-deriving the rest would leave the two halves describing different layouts. Re-deriving all of it is one honest pass and (c) says it is affordable.

    **(f) Printing settles SYNCHRONOUSLY first.** ⌘P straight after opening is exactly when the asynchronous settle has not finished, and paper has no honest way to show an overrun. `makePrintOperation` calls `settlePagedTablesFully` before it decides anything.

    **(g) The async seam needs its own test, and it must wait on the RESULT.** Every other check in `PagedTableOverrunTests` calls the settle itself, which proves the rule and says nothing about whether opening a document REACHES it (invariant 29's lesson) — a version whose walk never settled would leave them all green while every reader still printed rows in the margin. That test cannot use a completion callback (`precomputeLayout` cancels an in-flight walk and a cancelled walk's completion never runs — invariant 60b), and it cannot stop at the first sign of life: one round only moves what overran where it stood, and moving it makes later tables overrun, so a wait that stopped there caught the document mid-repagination with three tables still in a margin. It polls until no table ends in a margin.

    **Numbers, and one honest limit.** Reference report 4 overruns → **0**, 8 tables moved, **8 → 11 pages**; its ODT twin 1 → 0; `tago-tables.odt` 5 → 0. `--extract` is byte-identical (13,914 bytes — this lives in the RENDER layer, invariant 40), and a document with no page width is never touched (invariant 57d). The page count moving toward Word's 19 is a coincidence of direction, NOT convergence: Word SPLITS tables by default (`w:cantSplit` absent), so a reader that moves them will never reproduce Word's pagination. That gap stays a paged-fidelity item (invariant 59's closing note), not a printing defect.

62. **A header or footer that BUILDS to nothing must reserve nothing — "the entry has blocks" is the wrong question, and 28% of real Korean documents answer it wrongly.** `w:titlePg`'s deliberately blank cover header arrives with NO blocks and was always handled; an entry made of nothing but EMPTY PARAGRAPHS arrives with blocks, measured a full line height, and opened a band on every page with nothing in it. Measured over 548 real `.hwp`/`.hwpx`: 94 declare a header or footer at all, and **26 of those 94 (28%) declare one that draws nothing** — and the reference report's own `.odt` declares exactly such a first-page header, which is why it reserved 42.55pt above its first line for a blank. `PageBandGeometry.drawsSomething` decides it from what the entry BUILDS, and `entryDraws` is the single predicate both the band measurement and `DocumentWindowController.configurePageBand`'s leading-band gate ask (they had drifted: fixing only the measurement left the leading gate still asking `blocks.isEmpty`). Two things it must keep allowing: a picture-only header (an attachment is `U+FFFC`, which is not whitespace, so the text test passes it) and a header that draws only a RULE or a shaded band (no glyph reaches the built string at all, so the BLOCKS are asked for `shading`/`borderEdges` directly). This is invariant 47's three-state lesson one level deeper: present, present-but-empty, absent. Found by running `FMD_HEADER_FOOTER_PROBE` across real HWP — which also **closed the "HWP printing unverified" gap**: `.hwp`, `.hwpx`, `.odt` and `.docx` now all pass it, header and footer built to real glyphs with live page numbers and a PDF whose page count matches the reader's (140 / 45 / 450 / 8 pages). The probe itself had to be corrected twice to get there — it pinned no page options, so invariant 60(d)'s full-margin first page read as a failure, and it asked `blocks.isEmpty` too.

63. **`NSWindowController.document` is `unowned(unsafe)`, and this reader asks for it FROM THE DRAW PATH — so every read goes through `DocumentWindowController.mdDocument`, never `document as? MarkdownDocument`.** A window can outlive its document by a run-loop turn, and CoreAnimation commits the next draw inside that turn: `ReaderTextView.drawBackground` → `drawPageSheets` → `pageSheets` → `printSheets` → `pagedDocumentWidth` → `pagedWidth` → `objc_retain` on freed memory. The cast is what does it — an `unowned(unsafe)` read that produces a `+1` reference walks the dead object. It killed the WHOLE SUITE with SIGSEGV, deterministically, and two crash reports a day apart show that identical frame; what made it deterministic was a new test that pumps the run loop, which is an ordinary thing for a test to do. A `weak` mirror kept in step by overriding the setter answers `nil` instead, which is the same answer every non-paged document already gives, so no caller changed. **Note `swift test` HIDES this**: it reports the suite as merely "failed" with truncated output and no crash report. Run the bundle directly to see the signal — `swift build --build-tests` then `$DEVELOPER_DIR/usr/bin/xctest .build/arm64-apple-macosx/debug/FastDocReaderPackageTests.xctest`, which exits 139. **There is deliberately no unit test** (invariant 56's reason — every shape tried was fake-green: nil-ing the local reference does not release the document because the window keeps it alive, and `removeWindowController` clears the controller's own pointer so the UNFIXED code answers nil too); it is verified by that mutation, and the gap is written into `PagedZoomTests` where a future author will look.

64. **A table that will not finish on its page is either BROKEN at a row boundary or carried whole — the reader's choice, except that a table taller than the page is always broken.** The View menu's "Split Tables Across Pages" (`PageViewOptions.splitTables`, global, OFF by default) picks between them; the owner's rule *"표가 한장이 넘을때... 이런 경우는 무조건 쪼개야 해"* overrides it, because a table with no whole page to be carried to could only ever be left with rows in a margin.

    **(a) THE PIECE THAT MOVES IS NOT A ROW — it is the run of rows no merged cell spans.** Breaking above row `R` is safe only when no block has `startingRow < R < startingRow + rowSpan`; break where one does and the merged cell stretches across the gap between two pages with this reader's own header painted inside it, and the row's halves end up a page apart (rendered and looked at — invariant 61a). Rows welded by a merge therefore travel together (`PagePagination.unbreakableGroups`). Registering plain ROWS instead was built and measured on the reference report, which is merged nearly everywhere: the safe rows moved, the merged stretches between them did not, and twenty lines still landed in margins. A table nothing can be broken inside falls back to being carried whole even with breaking ON — better whole on the next page than half in a margin.

    **(b) Both answers are correct pagination, and neither is Word's.** Measured: reference report 11 pages carried / 10 broken, its `.odt` 8 / 7, a 39-page HWP 39 / 38, a 483-page HWPX 496 / 483 — and ZERO rows in a margin either way on every in-repo fixture. Word splits by default (`w:cantSplit` absent), so its page count will not be reproduced by carrying; that gap stays a paged-fidelity item (invariant 59).

    **(c) The settle re-measures every round, and the metrics are ROUNDED to a hundredth of a point so it can stop.** A piece's height comes back as `161.70000000000002` one round and `161.7` the next, and the loop compares the whole record — without rounding it would never converge. Measured convergence: 2–4 rounds, 95–427ms, on documents from 7k to 100k characters.

    **(d) The page a point sits on needs a hair of TOLERANCE, and this is not tidiness.** A piece moved to a page top lands at exactly `page × pitch + leadingBand`, and that number does not survive the division — measured, a line placed at page 6's top came back as `5051.279999999` against a pitch product of `5051.28`, so a bare `floor` called it page 5, judged it against page 5's bottom, and reported a piece that had just been moved correctly as still overrunning. `PageBandLayoutDelegate.page(of:leadingBand:pitch:)` owns the tolerance and `PagePagination`'s own check uses the same one — the two must agree exactly or the decision keeps asking for a move the rule has already made.

    **(e) THE LIMIT, measured and NOT closed.** On very large real Korean documents rows still land in margins: 205 lines of a 38-page HWP and 771 of a 483-page HWPX. **192 and 556 of those are inside a single unbreakable piece TALLER THAN THE PAGE** — a one-row table used as a text box, holding a page and more of prose — which cannot be placed anywhere without breaking a row, i.e. splitting one cell's text across two pages, which is the tear this whole design exists to avoid. That part is honest. The REST (13 and 215 lines) is unexplained and should not be re-derived blind: the settle converges (4 rounds, and raising the cap from 8 to 40 changes nothing), the delegate SEES every registered piece (1040 of 1040), and it declines them because the recorded height says they fit — traced on one, `visualTop 24446.62 + height 161.70 = 24608.32` against a page bottom of `24636.04`, while that piece's own lines reach `24682`. So a piece's measured extent is smaller than what is drawn inside it, by about the size of its own `topInset`; the row bookkeeping in `DocumentWindowController.laidOutTables` (which keys a merged cell's whole extent to its STARTING row) is the place to look. In-repo fixtures show zero, which is exactly why this needs a real document to reproduce. **And breaking makes that residue WORSE, not better, which is the opposite of what the toggle promises** — measured independently twice, on the two documents the owner uses as the release gate: `2025_행정업무운영편람_최종.hwp` **723 → 807** lines in a margin (off → on) and `1790387_prep_final_report.hwpx` **23 → 30**, while the WORST overrun is identical to the hundredth of a point either way (354.68pt / ~175pt), i.e. the dominant offender is the same over-tall unbreakable piece in both configurations and breaking merely adds new boundaries that overrun. So the toggle is not a repair for this residue and must not be recommended as one; it stays OFF by default, which is the configuration these numbers say is better on real Korean documents.

65. **Decoded pixels outlive the document that needed them, and that is what "the app never gives memory back" actually was.** Measured on the release build: freshly launched the app is **15 MB**; open a 20 MB HWPX and it is 161 MB; open a 10.7 MB HWP and a 14.4 MB DOCX after it, close every window, and it sat at **224 MB with nothing open at all** — which is why an instance left running 44 hours held **471 MB** with a single markdown file on screen. It reads as a leak and is not one: `leaks` reported **287 leaks / 14 KB**, while `heap` found **1,374 live 160 KB blocks** — decoded images, still legitimately referenced from `MarkdownDocument.imageCache`/`officeImageCache`, which are keyed per document (path + id, so nothing collides) but scoped to the PROCESS. `purgeImageCaches()` drops them when the LAST document closes and returns 34–97 MB per close; while anything is open they stay, because that is what makes scrolling back to a picture instant, and `NSCache` already evicts under real pressure. **Three things this cost, in order.** (a) The hook is `MarkdownDocument.close()` AFTER `super.close()`, deferred one run-loop turn — read the count at window-close time and the closing document is still registered, so it never fires. (b) `malloc_zone_pressure_relief` was built and REMOVED: measured in BOTH orders — before the purge it returned 0 MB immediately and 0 MB three seconds later (correct: the memory was still referenced), and after the purge, on a close that demonstrably gave back 97 MB, it still returned 0 MB. (c) The first diagnosis was WRONG and stood on one sample: an early `heap` run reporting 16.6 MB live was read as "nothing is retained, the allocator is just holding pages", and the next run on the same shape said 264 MB. One sample of a process's heap is not a measurement. What does NOT come back is ~110 MB of AppKit/CoreText caches, which is not ours to drop.

66. **Paper has no viewport — printing must load every picture first, and only the count of them proves it.** Pixels are held for a window either side of the reader (invariant 1), which is right for reading and silently wrong for printing: a 14.4 MB report carrying 28 PNGs, printed straight after opening, produced a 50-page PDF holding **ONE image object** and weighing 1.9 MB — every other picture came out as blank reserved space with nothing to say so, and this was true of ⌘P as much as of the CLI. `makePrintOperation` now asks for the whole document (`reconcileMedia(in:loadingEverything:)`), which fixes both paths at once because both come through it: 43 image objects and 14.1 MB, about a second added. The load there is SYNCHRONOUS (`loadOfficeImageSync`) and that is the load-bearing part — the print operation is built and run on the same turn, so the ordinary callback lands after the PDF has already been written; the first fix used the async path and changed nothing, which is exactly what a passing-looking non-fix looks like. `--pdf` itself introduces no pagination: it builds a real off-screen window controller, settles the same asynchronous pipeline, and hands the SAME operation ⌘P builds to a `.save` disposition — verified on `.docx` (11 pages), `.hwp` (490), `.odt` (9) and `.md` (423). Sandboxing note: the App Store build cannot write to an arbitrary path, so `--pdf` belongs to the direct build and must not be advertised in store copy.

67. **A Swift value carried as a text attribute must be `Hashable`, not merely `Equatable`.** `NSMutableAttributedString` hashes attribute values when it decides whether two adjacent runs can coalesce, so an `Equatable`-only Swift struct makes the runtime print "Obj-C `-hash` invoked on a Swift value of type … that is Equatable but not Hashable; this can lead to severe performance problems" — which this app did on every office document, for `OfficeGraphicInfo` and `FillMarginTabInfo` (and therefore `TabStop`/`TabAlignment`/`TabLeader`). Adding the conformance is free and mechanical. **Measuring it is not, and the method is the part worth keeping:** rebuilding the app twice and comparing wall clocks was useless, because this machine's load moved the same measurement by 3× between the two arms (a run at load 7.8 against one at load 26.9 reversed the answer). `AttributeHashingSpikeTests` declares both shapes in ONE file and times them back to back in a single process, alternating, so whatever the machine is doing is done to both — **8.1 ms against 6.0 ms over 4,000 attribute runs**. The gain is real and modest; the spike asserts only the direction, never a millisecond figure.

68. **ONE binary serves three shapes — reader, headless flags, and the Finder's preview — and the branch that separates the third is the FIRST line of `main.swift`.** `Contents/PlugIns/QuickLookPreview.appex` holds a COPY of the app's own executable; `Bundle.main.bundlePath.hasSuffix(".appex")` routes it to `NSExtensionMain` and never returns, so the preview shares 100% of the reader with **no module split** — which is the whole point, because splitting the package into a library would mean annotating hundreds of symbols and touching all 1,345 tests, and a preview-only renderer would make "the preview IS the reader" a lie (the alternatives and their costs are in `docs/02-planned/quick-look-extension-design.md`). **`NSExtensionMain` is a `main` and really reads `argc`/`argv`**: declared with no parameters it inherits whatever is in those registers and dies in `strlen` inside `EXExtensionMain` (`EXC_BAD_ACCESS`, read off the crash report) — and the only symptom from outside is "the extension registers but no preview appears", which looks like a packaging problem and is not. Measured format by format, by watching WHICH extension process runs: `.md`, `.hwp` and our own config types come to us — Mocha Drop's competing markdown/HWP extension included — while `.docx`/`.odt` stay with Apple's built-in. `QLSupportedContentTypes` deliberately omits `public.plain-text`/csv/tsv/log: macOS previews those fine and claiming them would take over every plain-text preview on the machine for nothing. It DOES claim `public.toml` and `com.microsoft.ini`, which is the other half of invariant 69(a): our own exported `config-text` covers `.conf`/`.env`/`.vars`, but `.cfg` really resolves to `public.toml` and `.ini` to `com.microsoft.ini` — types someone else owns, so no tag of ours reaches them and those two previewed as somebody else's while the app opened them. Claiming the owner's type is the only route, and it takes `.toml` along with `.cfg`; that is accepted rather than accidental, and it is consistent — the app opens `.toml` too. Cost, release: the app goes **17 MB → 27 MB**, because the copy is a copy (the size card, if it is ever needed, is a shared framework — i.e. the module split above). `SKIP_QUICKLOOK=1` builds without it, and the store copy must then drop the claim. **A PREVIEW IS NOT A READ, and the reader's own two best properties are wrong here.** (a) Laying the whole document out for an honest scrollbar (invariant 49) costs **3,022 ms** on a real 523 KB / 292,868-character Markdown file before anything can be seen — so the preview renders the HEAD of the source and says so. The bound is measured, same file, same run: **1,000 chars → 79 ms · 10,000 → 170 · 20,000 → 168 · 40,000 → 288 · 80,000 → 814**, i.e. 79 ms is the floor of building a window controller at all and 20,000 costs what 10,000 does — hence `previewSourceLimit`. A cut is taken back to a blank line and CLOSES an open code fence, or every remaining line renders as code. (b) An office document cannot be cut by its bytes, so it is cut by BLOCKS after reading, and the split says why that is worth doing: on a 20 MB HWPX the parse is 1,220 ms and the BUILD 1,998 ms — the typography, not the parser, is what a glance was paying for (3,973 → 1,727 ms end to end; the parse is irreducible, rhwp returns a whole document or nothing). (c) The page model is thrown away for the preview (`flattenPagesForPreview`) — the owner's instruction, *"좌우 페이지 여백 이런 게 안 보이고 오히려 콘텐츠만 보이면 돼"*, and correct: reproducing the author's paper spends a small panel on margins, and a table reflowing a little rougher was explicitly accepted. Both shortenings name themselves on screen (`shortenedNote`); a preview that silently stops early reads as a broken document. (d) The reading-line band is OFF in the preview (`ReaderTextView.showsReadingCursor`, set false by `QuickLookPreviewController`). It is the reader's "you are here", and a preview has no place to keep — on a real `.hwp` the caret sits at character 0, so the band landed across the document's TITLE and read as a highlight the file does not have. Same judgement `isDrawingToScreen` already makes for paper, made for the other medium that is not the reader; the flag defaults true so the reader is untouched, and the test asserts BOTH directions (mutation-checked: removing the one line turns it red). Which removed the only way to tell WHICH extension drew a preview, so (e) puts it back deliberately, and (f) uses the same mechanism for the other thing a preview must say about itself. **(e)** `PreviewBadgeView` lays translucent text over the panel — "⚡️FastDoc" top-right — installed as a SIBLING of the document's content view, never in the text storage, or ⌘F would answer it and a selection would copy it. It exists only on this path, so the reader, paper and `--pdf` are untouched by construction rather than by a flag. Two things it was WRONG about first: a filled capsule reads as a control and, at the panel's edge, drew clipped under the vertical scroller (hence text alone, and a 22pt right margin that clears it); and its test asserted the STRING, which is fake-green because `demo/code-blocks.md`'s own prose contains "FastDocReader" — it asserts the view hierarchy instead. **(f)** A shortened preview says so IN THE CONTENT — `shortenedNote` is `[ ... more in the full document ]`, appended as the last paragraph — and nowhere else. A pinned bottom-centre mark saying the same thing was built and REMOVED on sight: it does not move when the reader scrolls, so it reads as chrome rather than as the end of the text. The office budget is SHORTER than the text one (`previewOfficeCharacterBudget` 8,000 against 20,000), and it is in CHARACTERS on purpose even though the request was "five pages": measured through `--pdf`, a table-heavy `.docx` holds **233 characters per page** while Korean prose runs past a thousand, so a page-counting rule would cut one document at 1,200 characters and another at 9,000. Both marks are mutation-checked. **A rejected fix, so nobody re-derives it:** a narrow column-view panel showed a giant clipped heading, which looked exactly like the document staying at the placeholder 820pt width — measured, and it is NOT: resizing the controller's view to 300pt re-solves the container to 219pt with no help from us (`viewDidLayout` re-wrapping was built, measured to change nothing, and removed). What that panel actually showed was an H1 whose single word `Moby-Dick;` is wider than the column.

69. **A file type macOS was never told about cannot be bound to this app at all — and `DocumentTypes` alone tells it nothing.** `.conf`/`.cfg`/`.ini`/`.env` were in `plainTextExtensions` for a long time while `Info.plist` named no extension for them, so the panel opened them happily and the Finder could not: with no declaration anywhere, macOS types the file as a throwaway `dyn.…` and REFUSES to make any app its handler (`duti -s … vars all` → error -50, which is what surfaced the whole thing). `.txt`/`.csv`/`.log` escaped it only because OTHER apps register them as public types. The fix is a declaration we own — `UTExportedTypeDeclarations` (**exported**, not imported: the identifier `ai.ww-w.fast-md-reader.config-text` is in our namespace) — plus that identifier in a `CFBundleDocumentTypes` entry, because declaring a type only says it EXISTS while the document-type entry is what says we open it. Verified end to end, not by reading the plist: `duti -x vars` now answers this app, the previously failing `duti -s` succeeds, and a `.vars` file double-clicked in the Finder opens in a window of this build (`.ini` still goes to whichever editor the user already made default — correct, we are `Alternate`). `DocumentTypeDeclarationTests` reads the REAL `Info.plist` and fails in BOTH directions (an opened extension that is undeclared; a declared extension the app would refuse), which is the CONVENTION §3 mirror made mechanical — mutation-checked in both directions. **Three more things were measured while making the app the default handler for everything it opens, and all three contradicted what the plist assumed.** (a) The type a file really gets is not the one the name suggests: `.log` is `com.apple.log` (NOT `public.log`), `.cfg` is `public.toml`, `.ini` is `com.microsoft.ini` — read them with `UTType(filenameExtension:)` and claim THOSE, because a type someone else owns will not take our tags. (b) An office format has to be claimed as the **viewer** role (`duti -s … <ext> viewer`): the office entries are `Viewer` by invariant 22, so asking for the editor role is refused, silently. (c) `.mdown`/`.mkd`/`.mdtext` resolve to a throwaway `dyn.…` and were therefore **dropped from the app** rather than kept alive with an exported type of our own — the owner's call, and the right one: do not re-add a declaration to keep three aliases nothing writes. And `.hwp` cannot be taken programmatically at all — `LSSetDefaultRoleHandlerForContentType` returns `noErr` and writes NOTHING to `com.apple.launchservices.secure.plist` when another installed app owns the type (Hancom here), so that one is the user's own Get Info ▸ Change All — which DOES work and was verified from the other side (after the owner did it, `duti -x hwp`/`hwpx` both answer `/Applications/FastDocReader.app`). The refusal is programmatic-only; do not read it as "HWP cannot be taken".

70. **A sandboxed headless run reaches a file ONLY through a restored folder grant, and the restore has to happen before any entry point looks at a path.** The App Store build attaches no access to a path handed in on the command line, so `--extract`/`--pdf` were dead there — the fix is one line, `FolderAccess.restoreGrants()` at the top of `main.swift` (it used to sit in `applicationDidFinishLaunching`, which the headless flags never reach). Measured on a SANDBOX=1 build: with `~/Downloads` granted through the app's own panel, `--extract` reads a file **never opened before** and `--pdf` writes into that folder (21 pages); outside the granted folder both still refuse, now with a message that says what would fix it (`FolderAccess.annotatingHeadlessDenial`, the one place both CLIs compose it). Mutation-checked — comment that line out and the same file is denied again. So the honest claim for the store is "works in folders you have granted", NOT "does not work". Two things this cost: the grant panel's own menu item is named ONCE (`FolderAccess.grantMenuTitle`) so the headless hint cannot name a menu item that no longer exists, and **verifying any of this through System Events is a trap while two identically-named apps are running** — `first process whose unix id is N` returned the OTHER process (the installed release, unsandboxed), so three separate menu readings disagreed and all of them were wrong; the app dumping its own `NSApp.mainMenu` to a log settled it in one run.

## Debugging discipline (this app specifically)

- **Synthetic scroll is blocked by accessibility** — CGEvent scroll doesn't reach the window. You cannot drive scrolling programmatically; **the user reproduces, you read logs.** Log total height / frame height / scrollY per reconcile and read them.
- Temporary instrumentation goes to `/tmp/fmd-*.log`. **Remove all of it (delete `DebugLog.swift`, strip log calls) before committing** and clean `/tmp/fmd-*`.
- Verify visual/pixel behavior with a screenshot only when the judgment is truly visual; deterministic size assertions are proven by the logs/code, not screenshots.

## Commit / distribution

- **Solo local app → commit directly to `main`** (established pattern: `a80271e`, `57b485b`, `bce0ead`). No dev branch. Stage by filename (exclude `.bkit/`).
- **`docs/` is gitignored — local only, NOT on GitHub** (this repo is public and the AI collaboration logs quote internal discussion verbatim; GitHub can't keep a folder private inside a public repo). The distribution playbooks (`docs/NOTARIZATION.md`, `docs/APP-STORE.md`, `docs/APP-STORE-METADATA.md`) live there too, so they exist on this machine only — **don't link to them from README** (public readers would hit a dead path), and don't assume a fresh clone has them. (The `.gitignore` line is now `docs/`, not just `docs/commit-log/` — for a while only commit-log was ignored and the rest was merely untracked, one `git add .` from being public.)
- **`demo/` and `licenses/` ARE public** (committed): `demo/` = the four sample docs shipped for users (code-blocks, math, images, moby-dick — Moby-Dick is public-domain, PG boilerplate stripped; demo photos are PD/CC0, credited in `demo/assets/CREDITS.md`). `licenses/` = the OFL text the fonts require.
- **Two distribution tracks, both arm64-only, both from this SwiftPM build — no Xcode project:**
  - **Direct (`./Scripts/notarize.sh`)** — Developer ID + hardened runtime + Apple notarization → stapled `FastDocReader.zip`. **Unsandboxed.** Recipients double-click; no quarantine step. Run it only when shipping a build to someone, not per build. → `docs/NOTARIZATION.md` (local)
  - **Mac App Store (`./Scripts/appstore.sh`)** — Apple Distribution + embedded profile → signed `.pkg` → `altool`. **Sandboxed** (the store's price). Defaults to validate-only; `--upload` submits. The store notarizes during review, so this track never calls notarytool. → `docs/APP-STORE.md` (local)
- **The bundle is no longer a single binary** — `Contents/PlugIns/QuickLookPreview.appex` is separate code with its own identity, so both distribution scripts sign **inside-out** (extension first, app second; `--deep` is deprecated for distribution). The store needs more than a signature: an extension is its own app for provisioning, so `ai.ww-w.fast-md-reader.quicklook` needs its OWN App ID and Mac App Store profile, embedded in the `.appex`. `appstore.sh` refuses to submit without `QUICKLOOK_PROVISION_PROFILE` rather than being rejected at ingest hours later; `SKIP_QUICKLOOK=1` ships a build without the preview (and the store copy must then not claim it).
- **The builds differ ONLY in the sandbox, deliberately** (invariant 9) — don't "unify" them.
- **Signing identity / key ids are NOT in the repo** — scripts source `$KEYCHAIN_DIR/signing.env` (default `~/Documents/DEV/ww-w-ai/.keychains/`, chmod 600) and fail loudly naming the missing variable. Never re-add them as script defaults.
- `make-app.sh` alone is ad-hoc signed — runs on the building machine only. Never ship that bundle. It matches the direct build (unsandboxed); `SANDBOX=1 ./Scripts/make-app.sh` builds the sandboxed shape to exercise the folder grant.
- **A build carrying the App Store entitlements won't launch locally** (RBS error 163, "Launchd job spawn failed") — those identifiers require store installation. Hence `Resources/FastDocReader.entitlements` = same sandbox, no store identifiers, local testing only.
- Intel support needs a universal build (`swift build --arch arm64 --arch x86_64`) before packaging.
